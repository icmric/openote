# v1.0.2 — the accessibility tree, and the focus it moves

> Deferred out of v1.0.1 on purpose. The bug it causes is fixed; the cause is
> not. Written down now, while the evidence is fresh, so the next person to
> look at it does not start from nothing.

## What is actually wrong

The Windows engine cannot apply the semantics updates this app produces:

```
[ERROR:flutter/shell/platform/common/accessibility_bridge.cc(114)]
Failed to update ui::AXTree, error: 335 will not be in the tree and is not the new root
```

It prints constantly in normal use. We treated it as console noise for months.
It is not. Three things follow from it:

1. **Screen readers cannot use the editor.** If the tree will not build, there
   is nothing for Narrator or NVDA to read. Openote is for students, some of
   whom need this, so the honest status today is that it does not work.
2. **It moves the caret.** Having lost track of the tree, the bridge reports
   `didLoseAccessibilityFocus` for whatever node it thinks went away.
   `TextField` answers that by unfocusing the field — which, for a paragraph
   that contains a table, throws the caret out of the cell. That is the bug
   users saw, and v1.0.1 refuses it in `_ParagraphFocusNode`
   (`live_markdown_engine.dart`). **The refusal is correct on its own terms**
   — a field that contains fields is not finished just because accessibility
   focus moved into one of them — so it stays whatever happens here.
3. **The window loses and regains focus.** From a trace taken on 2026-09-30,
   after the refusal was in place:

   ```
   VIEW unfocused → PRIMARY -> Root Focus Scope
   VIEW focused   → VIEW unfocused → VIEW focused → PRIMARY -> paragraph
   VIEW unfocused → PRIMARY -> Root Focus Scope
   ```

   `ViewFocusState.unfocused` makes Flutter park the focus on the root scope
   (`widgets/view.dart`, the only caller of `requestScopeFocus` in the
   framework). This is why the caret is still seen to leave and come back even
   with the fix in. Whether it shares the cause above is **unproven**.

## Why it is not a quick fix

- **The check that fails is in the engine, in C++, at runtime, on Windows.**
  `flutter test` has no accessibility bridge, so no unit or widget test can
  see this — the whole existing suite is blind to it by construction. Every
  hypothesis costs a full rebuild and a manual reproduction.
- **It may not be ours.** The same error has upstream reports with unrelated
  triggers (tooltips inside scrolling lists; a `Slider` in a pushed route). If
  it is a framework or engine bug, the fix here is restructuring to avoid it,
  not a patch — and that has to be found by bisection.
- **The two prime suspects are both load-bearing architecture.**
  - The command bar disables ~18 tooltipped `IconButton`s in a single frame
    whenever `canFormatText` goes false, which is *exactly* when the caret
    enters a cell. Tooltips in a rebuilding list are a known trigger shape.
  - A paragraph is an `EditableText` whose spans contain more `EditableText`s.
    `RenderEditable.assembleSemanticsNode` does support placeholder children,
    so this is not unsupported outright — but it is a rare shape, and the atom
    span geometry (one `WidgetSpan` for the first code unit, the rest as
    hairline text) is rarer still.

  Neither can be ripped out to test a theory; both need a narrowed repro.

## What would settle it, in order

1. **Get a minimal reproduction outside Openote** — a `TextField` whose spans
   hold a `TextField`, plus a row of tooltipped buttons that disable together.
   If that alone prints the error, it is upstream, and the work becomes "file
   it, then find the smallest thing we can change on our side".
2. **Otherwise bisect ours**: wrap candidates in `ExcludeSemantics` one at a
   time until the error stops. That names the subtree; it is not the fix,
   because excluding a subtree from semantics is giving up on reading it.
3. **Then decide what correct semantics for a table in a sentence looks like**
   — which is a design question, not only a bug fix, and the reason this is a
   version of its own rather than a patch.

## Do not

- Do not "fix" it by turning semantics off. That trades a visible bug for an
  invisible one and closes the door on screen readers.
- Do not remove the `_ParagraphFocusNode` refusal if this turns out to be an
  engine bug that gets fixed upstream. A screen reader moving focus into a
  cell fires that action *legitimately*; the refusal is right either way.
