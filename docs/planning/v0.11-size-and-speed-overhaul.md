## 0. The report

> *"Go through and figure out our file size and file structure, making sure
> it's as efficient and small as possible. I am aware that some of the earlier
> design specs stated the constant mirror copy — consider those types of design
> specs we currently have and decide if they are actually good and make sense,
> or if they are bad or now redundant. No real users yet so we don't have to
> worry about compatibility. Optimise first for file size and minimal
> redundancy (while ensuring file integrity) and for speed. If we need a full
> structural overhaul or to switch languages/frameworks entirely, don't be
> afraid to suggest that."*

Two standing constraints are explicitly **lifted** by that instruction and this
plan uses both liberties: the format-v1 freeze (spec §2, "frozen from v0.2.0")
and any migration obligation. The spec gets a v2 when this lands, and v1
notebooks get a one-way upgrade on open.

Everything below is **measured on this machine**, on the real workspace —
not the synthetic probe v0.10 used. The real notebook changed the diagnosis.

# Part 1 — Where the bytes actually are

## 1.1 The workspace

`%APPDATA%\org.openote\openote\Openote` holds **586 MB**. Its composition:

| Size | What |
|---:|---|
| 97.5 MB | `Eric - Computing Science Honours-2.onote` (container) |
| 94.0 MB | `Eric - Computing Science Honours-2.onotebook` (log dir) |
| 94.0 MB | `…Honoursonepkg-2.onote` + 7.4 MB WAL |
| 94.0 MB | `…Honoursonepkg-2.onotebook` |
| 94.0 MB | `…Honoursonepkg-3.onote` + 7.4 MB WAL |
| 94.0 MB | `…Honoursonepkg-3.onotebook` |
| 92.6 MB | `…Honoursonepkg.onote` + 8.1 MB WAL (no log dir) |
| 9.9 MB | `My Notebook` (2.8 container + 4.1 WAL + 2.9 log dir) |

Three observations before any format work:

1. **~380 MB is duplicate copies of one import.** The same OneNote notebook
   was imported four times (each import rightly mints fresh ids, so no dedupe
   can see them as one). This is user-clearable today; the product's job is a
   duplicates surface that notices "same source, same page count, same title
   prefix" and offers the cleanup.
2. **WALs sit at 4–8 MB indefinitely** — `My Notebook`'s WAL is *larger than
   its database*. Nothing checkpoints on close. `PRAGMA
   wal_checkpoint(TRUNCATE)` at shutdown is nearly free and permanent.
3. One stray `…Honours 2.onote-shm/-wal` pair has no `.onote` — orphan cleanup
   for the storage panel's leftovers scan.

## 1.2 Inside the real notebook — the discovery that changes the plan

The container (97.5 MB), apportioned by SQL:

| Bytes | Table |
|---:|---|
| **67.0 MB** | `page_mirror` JSON — 328 pages, top pages **2–3 MB each** |
| 26.3 MB | `blobs` (378 images, original bytes) |
| 0.2 MB | `page_versions` (6 rows) |
| ~4 MB | indexes, nodes, freelist (742 pages ≈ 3 MB reclaimable) |

The log dir (94.0 MB): 67.7 MB `ops/` + 26.3 MB `blobs/` — the same content
again, as ADR-0006 shadow mode intends.

The op log (67.7 MB, **one file**, 2,700 ops), by composition:

| Bytes | Kind | Count |
|---:|---|---:|
| **64.26 MB** | `block.set` | 1,630 |
| 0.13 MB | `node.upsert` | 361 |
| 0.08 MB | `blob.put` | 378 |
| 0.08 MB | `page.props` | 328 |

And inside `block.set`: **63.14 MB is 113 ink blocks** — imported handwriting
serialised as JSON stroke arrays, individual ops up to **3.1 MB of text on one
line**. Superseded (dead) history is **0.10 MB** — noise.

> **The finding:** v0.10 diagnosed image double-storage as the dominant cost
> (true on its synthetic probe). On the real notebook the dominant cost is
> **ink stored as JSON text, twice** — ~64 MB in `page_mirror` + ~63 MB in the
> log = **~127 MB of the 191 MB total is one notebook's handwriting as ASCII
> decimal floats**. Images-stored-twice is the second cost (26 MB). Log
> compaction — the thing append-only designs usually owe — is worth 0.1 MB
> here and is *not* where the bytes are.

gzip on the real log runs at **27.2%** — but compression is the lesser fix;
the representation is the problem. A stroke point costs ~25–40 JSON characters
(`[123.45678901234567,456.78901234567890],`) for what is two float32s and a
pressure byte ≈ 9–12 bytes binary, before any delta/varint packing.

## 1.3 What this costs beyond disk

The same bytes are the speed story:

- **Open** replays the whole log: read + JSON-decode 67.7 MB (the "~0.5 s per
  14 MB" doc-comment scales to **~2.5 s** here, on a fast machine, per open).
- **Every save of an ink page** re-serialises multi-MB JSON into
  `page_mirror` (plus WAL amplification), and any touched ink block appends
  megabytes to the log unless the per-stroke diff path catches it.
- **Every pull** (`pendingForeignOps`) re-reads foreign device files in full.
- **Git**: a 3 MB single-line JSON op makes delta/pack slow; the single
  67.7 MB `.oplog` is two-thirds of the way to **GitHub's 100 MB hard reject**;
  and — time-sensitive — **whatever is pushed before the format shrinks is
  baked into clone history forever**. Compacting later shrinks the checkout,
  never the history every future device clones.

# Part 2 — Verdicts on the standing design specs

The instruction was to judge them, so, one at a time:

| Spec | Verdict |
|---|---|
| **Container is authoritative; log shadows it** (ADR-0006 shadow mode) | **Was right, now redundant.** It existed to make rebuild-from-log provable before anything depended on it. The join-from-git flow now *ships* rebuild-from-log as a user feature — an empty container is materialised from ops on every join. The training wheels are load-bearing nowhere. Complete the ADR's own endgame: demote to `cache.onote` (wave 2 / task #39). |
| **Blob bytes in the container AND `blobs/`** | **Redundant once the container is a cache.** v0.10's wave 1a already stopped it for local-only notebooks; a git-synced notebook (the user's, now) still pays 2×. Demotion removes the container copy structurally. |
| **Ink as JSON stroke arrays in block content** | **Bad — the single largest cost in the system** (§1.2). No wave covers it. New work, and the centrepiece of this plan: binary stroke encoding, stored content-addressed like images. |
| **One `.oplog` per device, append-only, unbounded, uncompressed** | **Half right.** One-writer-per-file is the whole merge story — keep forever. One *unbounded uncompressed* file is wrong in the git era (100 MB reject, full-file re-reads). Segment it, compress closed segments, snapshot for replay. |
| **"Constant mirror copy"** — mirrors re-copy `.onotebook/` per run; backup targets also snapshot the whole container | **Half redundant.** The container snapshot inside backups dies with demotion (a cache is rebuildable; copying 97.5 MB per backup run buys nothing). The mirror *feature* survives — "copy to a USB stick / network share on a schedule" is genuinely distinct from git and folder sync — but becomes incremental: blobs and media are content-addressed/immutable (copy-if-absent), segments are immutable once closed (copy-if-absent), only the active tail and manifest re-copy. |
| **30 full-page version snapshots, 10-min gap** | **Fine — measured 0.2 MB — but only by luck.** The policy stores whole-page JSON, so one ink page can legally hoard 30 × 3 MB. Once ink leaves the page JSON (Phase 1), snapshots become structurally small and the policy is genuinely fine. Keep. |
| **Import writes everything through the op log** | **Right**, and it is why join-from-URL works. The cost (67 MB of import ops) is the ink representation, not the principle. |
| **Videos as loose files in `media/`** | **Right locally** (never doubled, streams straight from disk). **Unhandled in git**: `media/` is committed, so one lecture recording > 100 MB makes every future push fail. Policy needed (Phase 0). |
| **JSON page mirror in SQLite** | **Keep.** With ink extracted, `page_mirror` collapses to ~3 MB for this notebook — the open format, third-party readability, and FTS home are worth far more than the residual bytes. |

# Part 3 — The app bundle (101.4 MB on Windows)

[install-size findings](install-size-findings.md) stands; new facts from this
pass, then the consolidated actions in Phase 0/5:

- `media_kit`'s footprint is not just `libmpv-2.dll` (29.8 MB): the ANGLE/GL
  stack it brings (`libGLESv2` 7.4 + `d3dcompiler_47` 4.9 + `vk_swiftshader`
  4.8 + `vulkan-1` 0.9 + `libEGL` 0.5) is another **~18.4 MB**. Video playback
  is **~48 MB ≈ 47% of the bundle**.
- `pdfrx/assets/pdfium.wasm` (4.0 MB) ships in release; it is the web build,
  inert on desktop, and its own README documents excluding it. The debug
  banner now nags about exactly this.
- `MaterialIcons-Regular.otf` ships **whole** (1.6 MB). `lib/` has no
  non-const `IconData`, so a *dependency* is defeating tree-shaking — the next
  release build's log names the culprit (it prints a tree-shake warning).
  Likely `media_kit`'s default controls; verify, then force or fix.
- `media_kit/assets/web/hls1.4.10.js` (375 KB) — a web-only JS asset in a
  desktop bundle.
- Fonts: Inter × 8 static faces (3.3 MB) + JetBrains Mono × 4 (1.1 MB);
  variable Inter + a mono subset ≈ −2.5 MB (findings doc, item 2).
- `en_us.txt` 1.7 MB uncompressed; gzip in bundle, inflate on the existing
  background-isolate load ≈ −1.1 MB.

## The framework question, answered with the numbers

Flutter's irreducible share is `flutter_windows.dll` 21.3 + `app.so` 12.6 +
`icudtl` 0.9 ≈ **35 MB**. Everything else is deps and assets we control.
After Phase 0 + Phase 5 the bundle is **~45–50 MB** (or ~95 MB with video
bundled), of which Flutter is ~70%.

A rewrite (Tauri/egui/native) could reach a 10–15 MB shell. It would also
re-implement the live-Markdown editor, the ink canvas and gesture arena, the
importer UI, PDF annotation, flashcards, three platforms of packaging — months
of work to save ~25 MB, while **the data-format work above is a 5–10× win on
the files users actually accumulate and is framework-independent**. A student's
notebook collection will dwarf the install within a term either way.

**Verdict: no framework switch, no rewrite.** The Rust core stays where it is
(parsing/import); Dart stays the app. Re-ask only if a future requirement
(mobile budgets, embedded) changes the constants.

# Part 4 — The plan

Phases are ordered so each ships alone, each is measured on the real notebook
before/after, and the riskiest format work lands **before** git history bakes
the old giants in. A synthetic fixture generator reproducing §1.2's measured
distribution (113 ink blocks at ~570 KB JSON mean, 3 MB max; 378 images;
328 pages) goes in first so tests never need the user's data.

## Phase 0 — Free wins, no format change ✅ *shipped 2026-08-08*

**Measured, clean release build on Windows: 101.4 MB → 94.06 MB (98,631,485
bytes).** The four bundle items landed exactly as costed; the storage items are
user-facing actions whose effect depends on the notebook.

| Saving | Item | Mechanism |
|---:|---|---|
| 4.06 MB | `pdfium.wasm` + two pdfrx web JS files | `dart run pdfrx:remove_wasm_modules`, the package's own documented step |
| 1.58 MB | `MaterialIcons-Regular.otf` 1,645,184 → 24,848 B | `tool/shake_icons.dart` — see below |
| 1.23 MB | `en_us.txt` → `en_us.txt.gz` (1,743,363 → 453,697 B) | inflate on the isolate that already parsed it |
| 0.54 MB | JetBrains Mono italic + bold-italic | dropped; synthesised oblique is indistinguishable at body size |
| 0.37 MB | `media_kit/assets/web/hls1.4.10.js` | `tool/strip_web_assets.dart` |
| 0.01 MB | `wakelock_plus/assets/no_sleep.js` | same |

**The icon finding is worth recording in full, because the plan guessed wrong.**
§Part 3 said "a *dependency* is defeating tree-shaking". It is not — nothing in
`lib/` or in any dependency constructs a non-const `IconData`. Flutter's own
desktop build never *attempts* it: `flutter_tools/bin/tool_backend.dart:94`
emits

```
'-dTreeShakeIcons="$treeShakeIcons"',
```

with literal quotation marks, while every sibling define on the surrounding
lines is unquoted. The value reaches `flutter assemble` as `"true"`, and
`IconTreeShaker` gates on `== 'true'`, so the subsetter is skipped silently and
the build prints nothing about it. macOS goes through `xcode_backend.dart`,
which passes the same define unquoted, so macOS releases were always correct.
`--no-tree-shake-icons` is therefore inert on Windows and Linux today.
`tool/shake_icons.dart` re-runs the asset bundling with the define spelled
properly and copies the one font it produces into the bundle; it refuses to
copy anything if the font did not actually shrink, so it cannot silently
succeed at nothing.

Storage-side items also shipped: WAL checkpoint on close (`checkpointAndClose`),
`auto_vacuum=INCREMENTAL` on new containers, **Reclaim space** in the storage
panel (`Repository.reclaimFreeSpace` — checkpoint, VACUUM, checkpoint, reporting
bytes returned), stray `-wal`/`-shm` orphans in the leftovers scan, `media/`
ignored by git by default, and a **duplicates finder** in the notebook manager.

Not done, deferred with reasons: **variable Inter** (−2.5 MB) needs
`TextStyle.fontVariations` plumbed through every weight in `tokens.dart` because
`fontWeight` alone does not drive a `wght` axis — a real change to the type
system rather than a pubspec line, so it belongs with a typography pass, not
here.

### Phase 0 as planned

2. **Icon tree-shake**: read the release build log, fix/force (−1.5 MB).

**~180 MB** without touching the format.

## Phase 1 — Ink becomes binary *(the centrepiece; ~a week)*

New content-addressed blob type `ink/strokes-v1`:

- **Encoding**: per stroke — header (tool, width, colour, flags) then points
  as **delta-encoded varint** x/y/pressure at fixed sub-pixel scale (canvas is
  already a 120-dpi integer-friendly space). Expected 10–20× under the JSON
  representation *before* deflate; deflate the blob (it is written once).
  Decision point during the spike: if delta+varint complicates the eraser's
  per-stroke diff, fall back to float32 frames + deflate — still ~8×.
- **Block schema**: `type: ink` keeps geometry/props in JSON but strokes move
  to `strokesRef: sha256`, plus a small `bbox` so layout never decodes ink.
- **The eraser/diff path** (`_diffInk`, `ink.strokes` ops) reworks to emit
  add/remove against the referenced blob — a new small blob + tiny op per
  gesture, GC'd later like any blob (ADR-0007 machinery).
- **Migration on open** (one-way, spec v2): rewrite each ink block to a blob +
  ref, rewrite `page_mirror`, append the *small* `block.set`. The old giant
  ops die in Phase 2's compaction, not here.
- **Tests**: byte-exact round-trip on the fixture; eraser fidelity against the
  existing ink tests; import writes binary directly (no JSON detour);
  `verifyPage` (currently dead code — wire it into the fixture tests as the
  independent check that rebuild == container).

Real-notebook projection: container 97.5 → **~33 MB** (26 images + ~3 ink +
~3 mirror/index); log 67.7 → **~5 MB**. Open-time replay drops with it.

## Phase 2 — Log segments, snapshots, compaction *(with Phase 1's fixture)*

- **Rotate** the active `<device>.oplog` at ~8 MB into immutable
  `<device>-<n>.oplog`; **gzip closed segments** (27% measured). Immutable
  closed segments are exactly what git packs well and what incremental mirrors
  copy-if-absent.
- **Snapshot**: a periodic materialised-state file (`snapshots/<lamport>.gz`);
  open = newest snapshot + segments after it. Kills the read-everything replay
  — target open under ~150 ms for the real notebook.
- **Compaction**: each device may rewrite **its own** closed segments older
  than the snapshot horizon (one writer per file makes this race-free by
  construction). This is where the 63 MB of superseded import ink physically
  leaves the disk. Watermarks stay per-device-seq (unchanged semantics).
- **Git note**: compaction shrinks the checkout, not remote history. Ship a
  "shrink sync history" action later (fresh orphan branch + force push) if
  repos age badly; **the real mitigation is Phases 1–2 landing before big
  notebooks are first pushed**, which is now.

## Phase 3 — Demote the container (wave 2 / task #39, unchanged in intent)

- Rename concept to `cache.onote`; bytes leave the container's `blobs` table
  (hash → `blobs/` file); backups stop snapshotting the container
  (§Part 2 mirrors verdict); missing/corrupt cache rebuilds via the join
  path's materialiser, which ships today.
- Mirrors become incremental (copy-if-absent on blobs/media/segments).
- The revert-bug guard (`foreignPending`) stays; demotion makes its failure
  mode strictly cache-staleness, never data loss.

Shared-notebook overhead after Phase 3: **2.23× → ~1.05×**.

## Phase 4 — The speed pass on what remains

Mostly falls out of 1–3 (open, save, pull are the same bytes), plus:

- Import chunking (task #41) — the one v0.9/v0.10 item still open.
- `pendingForeignOps` reads per-segment from the watermark offset instead of
  whole files.
- Spell dictionary: lazy-load stays on its isolate; ship gzipped (Phase 0).
- Re-measure v0.9's instrumented paths on the fixture; fix what the numbers
  name, not what intuition does.

## Phase 5 — Video playback becomes a component *(decision recorded)*

**Default: ship without the mpv/ANGLE stack (−48 MB); first video play offers
a one-click ~30 MB download** (hash-pinned, into app data), same UX shape as
the existing Linux "install mpv-libs" card — which is why this is credible:
the fallback card and the detection already exist. Linux keeps system libmpv
(already the case). A "full" installer variant remains for offline installs.
This is the one call in this plan worth revisiting if it tests badly — it
trades first-video friction for a 45 MB install, and it is cheap to flip back.

Bundle after Phase 5: **~45 MB** installed, ~25 MB download.

# Part 5 — What this does *not* do

- No framework or language change (Part 3).
- No CRDT revival, no server, no new sync transport — ADR-0006's shape
  (per-device append-only files + content-addressed blobs) is *why* segments,
  compaction and incremental mirrors are safe at all. The overhaul keeps the
  architecture and fixes the two encodings (ink, log) that betrayed it.
- No migration burden carried: v1 notebooks upgrade one-way on first open,
  the spec bumps to v2, and the freeze note is superseded with a pointer here.
