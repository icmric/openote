# Everything in one box — a design note on inline atoms

## A. What already works, precisely

Three things inline in a text block today. All three use **one trick**, and it is worth naming exactly, because it is the whole existence proof.

**The trick.** `LiveMarkdownController.buildTextSpan` (`app/lib/editor/live_markdown_controller.dart:470`) rebuilds the buffer as spans and then *proves* the spans concatenate back to the raw text (`:486–500`). A `WidgetSpan` occupies exactly **one** code unit (`U+FFFC`) in the laid-out paragraph, so an atom is emitted as a `_SourceSpan` (`:1358`) standing for the construct's **first character**, followed by the remaining N−1 characters at `fontSize: 0.01` with zeroed letter/word spacing (`_hidden`, `:934`). N code units of source, N code units laid out. No caret offset moves; the coverage check re-proves it on every keystroke.

| Inlines today | Where | Level | What it cost |
|---|---|---|---|
| Image `![](sha256:…)` | `_buildLine` `:1002`, regex `:210` | **line-anchored only** | The dialect is now written out in *four* places that must agree: `live_markdown_controller.dart:210`, `md_render.dart:34`, `pdf_vector_export.dart:502`, and a fifth inline copy inside `TextBlockView.autoWidth` (`text_block_view.dart:143`) that strips references before measuring width. Plus `_EditImage` (`:1405–1640`, ~245 lines) and `spliceImageOnOwnLine` + `_rebaseTags` in `media_drop.dart:186/219`, because inserting a picture inserts *lines* and every line-indexed tag below must be re-based. |
| Flashcard `?[front](back)` | `_buildLine` `:969` | line-anchored | Cheapest of the three: one shared regex (`study/flashcards.dart:95`), `_InlineCard` (`:1299–1350`), `replaceCardLine` with a stale-offset guard (`:150`). The study system reads the same lines, so decks came free — and MCP `create_flashcards` writes that line form directly (`api/mcp_tools.dart:282`). |
| Maths `$…$` | `_inline` `:1189` | **true mid-line** | The dearest. A shared grammar (`markdown/md_syntax.dart:176`) after two renderers drifted; a dollar-guard rewrite; `_lineRuns` had to record the whole equation as one hidden run (`:290`) or arrows died a dozen times inside an invisible fraction; and, because drawing the equation makes the caret unable to enter it, an entire click-in editor (`editor/inline_math_editor.dart`, 270 lines) had to ship in the same breath. |

Two supporting facts, both measured:

- **The non-forced strut is load-bearing.** With `TextField`'s default strut, a 120px-tall atom leaves the paragraph at 24px and is drawn outside the field. With `StrutStyle.fromTextStyle(..., forceStrutHeight: false)` (`live_markdown_engine.dart:422`) the same atom gives a 127px field. Atom height works *only* because of that one argument.
- **Block auto-height already copes.** `_MeasureSize` writes `app.renderSizes[b.id]` (`canvas/block_view.dart:664`), and every consumer reads `b.h ?? renderSizes[...]`. A taller line grows the box with no new machinery.

## B. The general mechanism

**Yes — one pipeline can carry every type, and it should. But not one syntax.**

Two measurements set the shape of the answer:

1. **An atom cannot swallow a newline.** A placeholder standing for a 3-line source construct measured **136px** against **94px** for the same atom over one line — exactly 2 × 21px of blank line, one per hidden `\n`. A newline is a hard break; no font size hides it. So any construct whose source is multi-line (table, fenced code, board, embed) **cannot** be an atom in its native Markdown form. It needs a one-line reference.
2. **A too-wide atom demotes itself.** Asked for 560px in a 400px box, the child is drawn at 400px starting at x=0 — its own visual line — while a 200px child stays inline at x=102. The mechanism already does "inline if it fits, own line if it doesn't", for free.

### The dialect

```
![label](onote://atom/0198f3c2-7b1e-7cc3-9f10-3d2a8c41e977)
```

with the payload stored in the **host text block's own content**:

```jsonc
"content": {
  "text": "Results: ![](onote://atom/0198…) and it holds.",
  "atoms": {
    "0198…": { "id": "0198…", "type": "table", "content": { "cells": [...] } }
  }
}
```

Why this and not something else:

- **It is CommonMark.** Foreign readers show the alt text, not a syntax error. It is the same `![…](…)` shape the image dialect already uses, so `_imageLineRe`'s successor is one grammar, not two.
- **`onote://` already exists** in the codebase: `md_common.markdownInline` (`export/md_common.dart:47`) exports wiki-links as `[title](onote://page/id)`. The scheme is ours and unclaimed by `_link` (`md_syntax.dart:121` matches only `https?:` and `mailto:`).
- **The payload is Block JSON**, which answers spec 14 §7's checklist item 1 by itself: it flows through `Block.toJson`/`fromJson`, so `read_page`, `append_blocks`, `page.json`, the op log (`sync_recorder` records `block.set` with `Block.toJson()`) and the open-folder export all carry it with **no new schema and no new tool** — which item 4 forbids anyway.
- **Payload in the host block, not as a sibling block.** Cut/copy/paste, undo (`pushUndo` snapshots blocks) and sync all move the text and its atoms as one unit; there are no orphans, and the canvas paths that iterate `app.blocks` (culling, marquee, z-order, `pageMarkdownOf`'s y/x sort) need no "skip inline blocks" clause. A sibling-block model would touch `page_canvas.dart`, `app_state.dart:6544/6711/6730` and every exporter.
- **Stable identity is not decoration — it is measured.** Today's image atom is keyed `ValueKey('${src}@$lineStart')` (`:838`). Probe: typing one character on the line *above* an atom keyed by offset destroyed and recreated its State (2 inits, 1 dispose, in-flight state lost); with a stable id the same edit kept the State. A video's playback position, a drag in progress, a table's selected cell all die on a keystroke elsewhere in the block unless the atom carries an id.

**Keep `$…$` and `![](sha256:…)` exactly as they are.** They are already CommonMark-native, already round-trip, already understood by the importer and OneNote. Adding an `onote://atom/` form is additive; rewriting the existing two would churn every note on disk for zero user-visible gain. One *mechanism* (`_atomSpan` + an atom registry), three *parsers*.

**Export projection.** `page.md` stays the lossy convenience path per spec 10 §8: each atom projects to its native Markdown (`$…$`, `![](assets/<hash>.<ext>)`, a GFM table, a fenced block, a link). `page.json` is the fidelity path and keeps the reference. That is the spec's own contract, honoured rather than bent.

## C. What can truly inline, and what wants a line

Measured on the real field, 600px wide, 14px text.

| Type | Verdict | Evidence |
|---|---|---|
| **Maths** | Mid-sentence. Done. | Inline `$\frac{}{}$` = 21px line; a 2×2 `pmatrix` grows only its line to 34px. |
| **Image** | Mid-sentence for small ones; auto-demotes when wide. | Same span mechanism as maths; the 560px-in-400px probe shows the demotion is automatic. Today it is line-anchored **by regex only** (`:210`) — a mid-line reference prints as source (probe: 0 widget spans). Nothing mechanical stops it. |
| **Table** | Own line, but *in the box*. | A 170×68 table mid-sentence renders fine (field 89px, prose continues after). It's legibility, not mechanism, that argues for its own line. |
| **Code (fenced)** | Own line, in the box, read-only until clicked. | Multi-line source ⇒ needs the reference form (B.1). |
| **Flashcard** | Own line. | The card measures 132–148px tall. A 148px-tall "word" inside a sentence is absurd. |
| **File / video / PDF** | Own line, in the box. | A player is a stateful child; identity (B) is a correctness requirement, not an optimisation. |
| **Board, embed** | Own line, preview + click-to-open. | Embeds additionally need a recursion depth cap. |
| **Ink** | **Never inline.** | Strokes are page-absolute coordinates (`_scaleInk`, `block_view.dart:452`), not characters. Spec 11 §5.1 already calls this the deliberate exception. Layer it above the box. |

**What actually breaks, concretely:**

- **Nested live editors.** A `TextField` inside a `WidgetSpan` inside a `TextField` does mount, take taps and take text — the probe typed into it successfully. But the host field's caret stayed at 0 the whole time: two carets, one keyboard, and none of the host's `WrapSelectionFormatter`, `markerAwareDelete`, Tab/Escape or maths-bar key handling sees those keystrokes. **Do not nest editors.** Every editable atom uses the choreography `InlineMathPopover` already proved: draw read-only in the flow, one click opens an editing card anchored under it, writes stream back through a `replaceXAt`-style guarded splice.
- **Caret hit-testing is lumpy.** Tapping across a 32.7px equation atom returned offsets 2, 2, 3, 2, 3 — non-monotonic, because `_snapOutOfHiddenMarkers` (`:333`) pushes back out. The caret can never land inside, which is correct; but a bigger atom makes the wobble a bigger target.
- **Two shape-changes exist right now.** A GFM table renders as a real `Table` when read (66px) and as raw pipes when the caret enters (63px of text, 0 `Table` widgets). And `$$\sum x$$` renders as centred display maths when read (65px) but in the live field draws as a **literal `$`, an inline-size atom, and a literal `$`** at 21px — a 44px jump and two visible dollar signs, because `_buildLine` has no display-maths branch while `md_render.dart:37` does.

## D. Order of work

**Step 0 — one atom pipeline (no user-visible change except speed).**
Extract the four hand-written copies of "placeholder for char 0 + hidden remainder" (`:969`, `:1002`, `:1125`, `:1189`) into `_atomSpan(source, child, {required String id})`, with a widget-instance cache keyed by that id. *Delivers on its own:* atoms stop being rebuilt from scratch every keystroke. Measured, 100 inline equations in one block: **220.8ms → 24.8ms per keystroke** (plain 100-word block: 4.3ms; 100 cheap `SizedBox` atoms uncached: 46.1ms — so the atom *widgets*, not the span builder, are the cost; `buildTextSpan` itself is 660µs, 0.3% of the frame). Realistic counts cached: 20 atoms 10.9ms, 40 atoms 12.9ms. And atom State survives typing elsewhere in the block.

**Step 1 — the atom grammar and storage.** `onote://atom/<id>` in `md_syntax.dart` (one branch, one classifier case — it reaches both renderers in one commit by construction), `content.atoms` in the block envelope, `Block.fromJson` reuse for the payload. *Delivers:* nothing visible; it is the contract, and it is where the round-trip property tests land.

**Step 2 — tables as atoms.** Read renderer already draws them (`md_render.dart:186`); the live editor gets the same widget through `_atomSpan`, and a click opens the existing table editor in a popover. *Delivers:* **a table stops turning into pipes when you click the box** — the single most visible shape-change left.

**Step 3 — the export/print surfaces.** In order of blast radius:
- *Markdown export*: refactor `pageMarkdownOf`'s per-type switch (`markdown_export.dart:107–190`) into `blockMarkdown(Block)`, then call it for atoms too. `writeExportedMedia` already copies blobs and rewrites to `assets/<hash>.<ext>`.
- *PDF*: `pdf_vector_export._blockShape`/`_mixedFlow` (`:232`, `:441`) already decompose a text block into `text | image | card` runs — add an `atom` run and one rasteriser per type, reusing the cache-by-value trick from `_renderMaths` (`:509`).
- *Read renderer*: `_renderLine` gains one branch.
- *Auto-width*: `TextBlockView.autoWidth` (`text_block_view.dart:143`) currently strips image lines with a private regex so a 64-hex reference doesn't pin the box wide. It must learn atoms generally, and substitute each atom's *rendered* width — a 36-character UUID is otherwise the same bug.
- *Importer*: nothing until it wants to emit atoms; `md_import.dart` and `onenote_import.dart` already produce `$…$` and `![](sha256:…)` and keep working unchanged.
- *MCP*: **nothing.** `read_page` json carries `content.atoms`; `append_blocks` validates it via `Block.fromJson`. Spec 14 §7 item 4 forbids a tool-specific schema, and item 2 does not fire — this is not a new operation. The one honest line for §5's table: `read_page format:"markdown"` projects atoms to their native Markdown, as page.md does.

**Step 4 — mid-line images.** Drop the `^…$` anchor for references that fit; keep the width-based demotion. `spliceImageOnOwnLine` and `_rebaseTags` (`media_drop.dart:186/219`) get simpler, because an inline atom adds no lines.

**Step 5 — code, file/video, board, embed** as read-only atoms with click-to-open. Each is one row in the atom registry once Steps 0–3 exist.

## E. The honest costs

- **Caret arithmetic (#81)** is the invariant everything rests on, and it gets *more* load-bearing, not less: every atom must stand on exactly one code unit with the remainder hidden, and every hidden run must be registered in `_lineRuns` (`:266`) or arrows die inside it. The mutation-proof standard from the maths work must extend to each new atom kind. The coverage check (`:498`) makes failure a silent fallback to unstyled text, not a crash — good, and worth keeping in mind when a bug is reported as "the styling just stopped".
- **Selection.** Copying works by construction — the buffer is the source, so a selection over an atom copies its reference text. What is *not* free: dragging a selection across an atom visually, and Backspace-into. Today backspacing into an image breaks the reference and the source reappears, which is at least self-explanatory. For a table that would print six lines of pipes; atoms therefore need `markerAwareDelete`'s treatment — one Backspace deletes the whole reference, or converts it to something legible.
- **Undo** is block-granular (`pushUndo`, `text_block_view.dart:196`). `content.atoms` rides in the same snapshot, so undo of a table edit is correct — but coarse: one undo step reverts the whole block, exactly as today. Fine now; it is the same coarseness ADR-0006 already flags as the reason for the §5.1 migration.
- **Performance.** Numbers above. The rule to write down: **an atom widget must be constructed once per id, never per keystroke.** Without it, 40 equations in a paragraph is ~88ms per keystroke — visible lag on a real machine, and reachable by a maths student today.
- **Canvas model.** Height is already fine (`renderSizes`). Width is the sharp edge: `requestExtraWidth`/`onNeedWidth` grows `Block.w` mid-drag, and `autoWidth` measures raw source. Both need the atom's rendered width, not its reference length.
- **Hit-testing** gets a bigger wobble zone (C), and pointer events inside an atom compete with the block's `Listener`-driven drag-selection (`block_view.dart:456`).

**What I would not do:**
1. **No nested live editors.** Measured: two carets, one keyboard, and the host's key handling bypassed.
2. **No replacing `$…$` or `![](sha256:…)`** with the generic form. Churn on disk, breaks the shared grammar's one-copy property, gains nothing.
3. **No multi-line atom source.** 21px of dead space per swallowed newline, measured. This is *why* the reference form exists.
4. **No §5.1 structured-`nodes` migration as a prerequisite.** It is the right end state and it is a quarter of work; atoms do not need it, and blocking on it would stop everything.
5. **No inline ink.** Page-absolute strokes; layering is correct.

## F. The smaller first slice, felt next week

**Ship Step 0 plus one branch: display maths in the live editor.**

Both live in `live_markdown_controller.dart`. The visible half is a `$$…$$` branch in `_buildLine`, drawing `OnoteMath(compact: false)` through the same placeholder as the inline case, with the remainder hidden — matching `md_render.dart:37` so the two agree. The measured defect it removes: a student who writes an equation on its own line and clicks back into their notes sees it shrink from 65px to 21px with a stray `$` on either side. After: it does not move.

The invisible half is the atom-instance cache from Step 0, which the student feels as *typing that stopped stuttering* in a page of maths (12.9ms vs 87.7ms per keystroke at 40 equations) and as *the picture they were resizing not forgetting the drag* when a word is typed above it.

Two changes, one file, one afternoon each, and both are prerequisites for everything in D — which is the test of whether a first slice is the right one.
