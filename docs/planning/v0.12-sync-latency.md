# Openote v0.12 — making sync feel live

> **Document status:** design note, nothing built · 2026-08-09
> **Owner:** Eric · **Related:** [ADR-0006](../adr/ADR-0006-sync-transport-and-text-model.md)

## 0. The report

> *"Ive gotten the sync working with github. Its a bit slow but its working …
> Getting onenote sync speeds (near live, updates reflected within 2-5s) is
> likely not possible with git … The only constraint is that i dont want to
> have to personally run a centeralised server/database for everyone … i want
> to keep syncing as easy as possible, im thinking a year 10 student at school
> can figure out how to sign into a microsoft account and create a notebook,
> but if i sudenly told them to set up a cloudflare account and an r2 bucket …
> they will get lost very quickly."*

## 1. Where the time actually goes

Git is not the slow part. **Openote's own scheduling is**, and inbound has no
signal at all.

| Cost | Seconds | Whose |
|---|---:|---|
| `scheduleGitSync` debounce | **60** | ours |
| `git pull` (TLS + auth + ref negotiation) | 1–3 | git |
| `git commit` | <0.1 | git |
| `git push` | 1–3 | git |
| **Inbound: the other device learning anything happened** | **up to 60 + its own cycle** | ours |

So a change can take two minutes to appear, and almost all of that is a timer
we chose. Git itself, for a notebook that is now ~5 MB, is a few seconds.

**The structural point:** git gives you *storage*, not *notification*. Nothing
tells device B that device A pushed. Every near-live system has a signal
channel; git has none, and no amount of tuning invents one.

## 2. What already works, and is being overlooked

**Cloud-folder sync is already the near-live path.** `OpFolderWatcher` watches
`ops/` and fires ~900 ms after a file changes; the save debounce is 700 ms.
Drive, OneDrive, Dropbox and Syncthing each propagate a small file in a few
seconds and carry their own push infrastructure — which is precisely the
notification channel git lacks.

End to end that is roughly **2–6 s**, today, with no server, no account beyond
one the student already has, and no setup past "install Drive".

That reframes the problem: git is not the transport to make fast. It is the
*version-history and no-cloud-provider* option. The product should say so —
folder sync recommended, git offered beside it — and the sync window currently
presents them as equals.

## 3. The options, ranked by (value ÷ setup a 15-year-old must do)

### 3.1 Tighten what exists — hours, no new concepts

* **Split the debounce.** Commit locally on a short timer, push on another.
  A push is cheap; the 60 s exists to avoid commit noise, and the two do not
  have to share a number. Target ~3–5 s to push.
* **Poll with `git ls-remote` instead of `git pull`.** One round trip, one ref
  SHA, ~200–500 ms, no working-tree touch. Pull only when the SHA moved. Cheap
  enough to run every 5–10 s.
* **Coalesce the cycle.** Today `syncOnce` always pulls, commits and pushes.
  With `ls-remote` first, an idle notebook costs one request.

Realistic outcome: **outbound 3–5 s, inbound 5–10 s.** Not OneNote, but a
different product from two minutes — and it needs nothing from the user.

### 3.2 Local-network peer sync — the biggest genuine win

Two devices on the same wifi is the *common* student case: laptop and tablet at
home, or laptop and desktop on campus. mDNS discovery plus a direct transfer of
op-log files gives **sub-second** propagation with **no server, no account, no
cost and no setup** — it simply works when both are awake, and falls back to
git or the cloud folder when they are not.

This is what makes Syncthing feel instant, and it is the one option that is
both the fastest and the easiest. The op logs are already append-only and
one-file-per-device, so a peer transfer is "send the files you don't have" —
the same primitive the whole design rests on. **This is where I would spend the
effort.**

Costs: mDNS on three platforms, a pairing step (show a code on one device, type
it on the other, once), and firewall prompts on Windows.

### 3.3 A notification relay — small, cheap, optional

The insight that resolves the user's constraint: **you do not have to host the
data to make sync live. You only have to host the doorbell.**

A tiny fanout service carrying `{notebook-hash, revision-counter}` — no note
content, ever — turns git from polling into push. Device A pushes to GitHub,
then tells the relay; device B is holding a connection and pulls within a
second.

* **Cost**: a Cloudflare Worker with a Durable Object per notebook. Messages
  are tens of bytes. Free at your scale; single-digit dollars at thousands of
  users. It stores nothing.
* **Not a dependency**: if it vanishes, sync degrades to §3.1 polling. Nothing
  is lost, nothing is stuck.
* **Not a privacy hole**: the id is a hash of the notebook id salted per
  notebook, so the relay cannot enumerate or correlate. Content stays in git.
* **Self-hostable** for anyone who wants to, precisely because it is trivial —
  and irrelevant to everyone else, because they never see it.

This is the honest way to have "no centralised server for your data" and
near-live sync at once. It is worth being explicit in the UI that a doorbell
exists and what it carries.

### 3.4 What to refuse

* **Hosting the notebooks.** Named for completeness; it is the thing the user
  ruled out and the thing that would make Openote a service.
* **Making the user create an R2 bucket / API key.** Correctly identified as
  where a 15-year-old gives up. Keep as a documented advanced route only.

## 4. Recommendation

1. **Reposition folder sync as the default fast path** and say so in the sync
   window. It already meets 2–6 s. (Hours.)
2. **Do §3.1.** Git goes from ~120 s worst case to ~5–10 s. (Hours.)
3. **Build §3.2, LAN peer sync.** Sub-second, zero setup, zero cost, no server
   — the best answer to the actual question. (Days.)
4. **Then §3.3 if still wanted**, as the thing that makes git live when the
   devices are never on together.

Order matters: 1 and 2 are nearly free and may be enough, and 3 is worth more
than 4 for a student with a laptop and a tablet.
