# Openote v0.8 — making a timetable worth subscribing to

> **Document status:** v1.0 · stage 1 built · 2026-08-05
> **Owner:** Eric · **Related:** [v0.5 dates & reminders](v0.5-dates-and-reminders.md) · [ROADMAP](../../ROADMAP.md) · [TESTING](../../TESTING.md)

## 0. The report

> *"The whole events thing feels kinda clunky and like an afterthought. Not
> intending to replace people's entire calendars with this, but would be nice to
> be able to see my timetable and stuff in there so I know what classes are
> coming up, maybe be able to configure if there is a popup for certain types to
> remind me to join the online lecture or whatever."*

Plus three defects reported in the same breath, which turn out to be the same
problem wearing three hats:

1. A reminder fires and **nothing pops up** — just a dot on a toolbar button.
2. **"Done" does not dismiss** anything.
3. A real university feed **would not load at all**.

## 1. Why it felt like an afterthought

It was one. v0.5 §4 subscribed to a calendar, parsed it carefully (54 tests,
recurrence, overrides, malformed feeds) and then **dropped every event into the
agenda as an undifferentiated bullet**. That is the shape of a feature built
from the data outwards: the hard part — the parser — was done properly, and the
part the student touches was the last five per cent.

The specific failures, named:

| Symptom | Cause |
|---|---|
| A wall of near-identical rows | Every event rendered the same. A semester is ~34 events a week and they all say the unit code twice. |
| "What have I got on" needed scrolling | The agenda is ordered by *day*. The question is about the *next hour*. |
| The join link was invisible | It is in `URL`, or `LOCATION`, or three paragraphs into `DESCRIPTION`. Nothing looked. |
| Nothing ever told you anything | Reminders had a fire path; events had none at all. |
| The feed would not load | See §4. |

The through-line: **Openote knew about the events but had no opinion about
them.** A calendar you can only read is a worse calendar than the one you
already have open in a browser tab, so there was no reason to use this one.

## 2. What was built

### 2.1 Events have a kind

`event_kinds.dart` classifies each event from its own text into one of eight
kinds — lecture, tutorial, lab, workshop, seminar, exam, meeting, other.

This is a heuristic and the code is explicit that it is one. Three rules keep it
honest:

- **Whole-word matching only.** The first attempt used substrings and was wrong
  inside one real feed: `lab` matches *Syllabus* and *Collaborative Practice*,
  `tut` matches *Institute*, `lec` matches *Electronics*.
- **Summary first, then description, never the location.** *"Lecture Theatre
  3"* is where the tutorial is.
- **Ordered, not a map.** `exam` is tested before everything else so that
  *"Final Exam — Lecture Theatre 2"* is an exam.

A wrong guess can put a row under the wrong heading or fail to offer a button.
It can never hide an event, change a time, or open anything.

### 2.2 Alerts you configure per kind

**The thing that was asked for.** One switch for "alert me about my timetable"
is useless in both positions: off is silence, on is thirty-four interruptions a
week, and thirty-four interruptions is silence a week later once they have been
switched off wholesale. Per-kind lead times make the useful configuration
expressible in one row — *lectures, ten minutes* — which is also the preset
button.

Three decisions worth recording:

- **Off by default.** An app that starts interrupting on install gets its
  notifications killed before it earns any.
- **Turning a rule on does not fire a burst.** Everything already inside its
  alert window is marked seen. "From now on" means from now on.
- **Nothing replays a missed event alert.** A reminder you set for 2pm is worth
  hearing about at 4pm; *"your lecture was starting soon, four hours ago"* is
  noise — and noise on every launch for the rest of the day. Reminders catch
  up, event alerts do not. They are different promises and the code makes the
  distinction rather than inheriting one behaviour for both.

### 2.3 A Join button

`joinLink` searches `URL`, then `LOCATION`, then `DESCRIPTION`, and a
recognised provider (Zoom, Teams, Meet, Webex, Blackboard Collaborate, Echo360,
…) always beats an unrecognised link found earlier. A bare link in a
description is **not** offered: it is overwhelmingly the unit outline or the
reading list, and a Join button that opens the reading list at 9:01 is worse
than no button.

This is the payoff for classification. "Ten minutes before a lecture, a card
appears with the Zoom link on it" is a complete answer to a real morning.

### 2.4 "Up next"

A pinned strip at the top of the planner: what is on now (with its end time),
and what is next (with how long you have), each with a Join button when there
is one. Renders nothing without a subscription.

The agenda answers *"what have I got on"*. This answers *"what do I do in the
next ten minutes"*, which is the question a timetable is actually subscribed
for, and it is one row rather than a scroll.

## 3. The popup, and why it is in-app

Reminders fired correctly and the only evidence was a coloured dot. If the
panel was closed — which it is, most of the time — a 2pm reminder produced no
visible event at 2pm.

`alert_popup.dart` is a floating stack, bottom-right, over the canvas rather
than pushing it (an alert that reflows the page moves the line you are typing
on). It never auto-dismisses; a nudge that vanished while you were looking at
the other monitor is exactly the failure this feature exists to prevent.

**Why not an OS notification.** The same reasoning that made Openote own the
schedule in v0.5 §1 applies to the display. `flutter_local_notifications` cannot
schedule on Linux at all, and on Windows a toast needs MSIX package identity
that the portable build does not have. An overlay behaves identically on all
three desktops with no new dependency and no packaging constraint.

Its limitation is real and is **stated in the settings dialog rather than
discovered**: it cannot reach you when Openote is not running. An OS toast,
where one can be had, is a second channel to add later — never a replacement
for the catch-up list.

### 3.1 "Done" now means done

`clearAlerts` emptied the on-screen list and left every reminder live. So the
badge stayed lit, the row stayed in the agenda, and the button read as broken —
which is precisely what was reported. `dismissAlert` resolves the reminder in
the store.

The two behaviours are both still there, because they are genuinely different
promises, and now they are different methods with different buttons:

| | Means | Where |
|---|---|---|
| `dismissAlert` / `dismissAllAlerts` | Finished with it | **Done**, the ✕, **Dismiss all** |
| `clearAlerts` | Not now, I am reading it in the panel | Nothing user-facing yet; kept for the panel |

Reminders also gained a visible tick on every agenda row. Delete was always on
the right-click menu, and that was not enough: nobody right-clicks a list they
have just been shown, so the honest report was *"there is no way to dismiss
one"*.

## 4. Why the UTS feed would not load

The reported URL failed with `HttpException: Connection closed while receiving
data` — a mid-stream drop, not a refusal. A plain `HttpClient.getUrl` has three
ways to provoke that against a hardened institutional server, and Dart's
defaults make two of them likely:

1. **No `User-Agent` worth the name.** `dart:io` sends `Dart/3.x (dart:io)`.
   Several WAF rule sets treat that as a scraper and drop the connection *after*
   the response line, so the client sees truncation rather than a 403 it could
   report.
2. **`Accept-Encoding: gzip`, added automatically.** If an intermediary
   compresses and then miscounts the length, auto-inflate throws exactly the
   observed error.
3. **Connection reuse** racing a server that has already decided to close.

None is diagnosable from the client, so `calendar_fetch.dart` does not try:
it **retries with progressively more conservative requests** (identity
encoding, `Connection: close`, longer timeouts). A timetable is fetched a
handful of times a day, so the cost is nothing and it fixes all three without
knowing which applied.

Four other fixes rode along, each a real failure mode:

- **`Accept: …, */*`.** The URL has no `.ics` extension, so servers commonly
  return `application/octet-stream`; a strict `Accept` gets a 406.
- **Bytes, decoded with `allowMalformed`.** One Latin-1 byte in a room name
  should not lose a semester.
- **BOM stripped.** Three invisible bytes in front of `BEGIN:VCALENDAR` read to
  the user as *"Openote says my timetable is not a calendar"*.
- **Messages you can act on.** A 401/403 now says to look for the *secret
  address in iCal format* — which is also the answer to the Google Calendar
  half of the report, where a private calendar's public URL 403s.

**A status the server chose is never retried.** Making someone wait three times
as long to read the same sentence is not resilience.

> **Note on the format.** The reported URL is not named `.ics`, and that was
> never the problem — Openote sniffs `BEGIN:VCALENDAR` in the body and ignores
> the extension entirely. `webcal://` is also accepted, and a downloaded file
> can be chosen instead of a URL.

## 5. Exams can carry a time

Stored in a **separate map** from the date rather than as a richer value, for
one load-bearing reason: the countdown, the revision plan and the day bucketing
are all *day* arithmetic and must stay that way. `examDate` (midnight) and
`examAt` (the moment) are two methods so that the choice is made at each call
site rather than inherited. The agenda row becomes timed; nothing else changes.

The picker is one dialog rather than a date picker chained into a time picker,
because cancelling the second has no unambiguous meaning — "no time" and "keep
what was there" are both reasonable readings, and whichever is chosen is wrong
half the time.

## 6. Deliberately not done

- **Multiple calendar subscriptions.** Still one feed. Two is a manager — add,
  remove, rename, colour, enable — and the v0.5 brakes say anything needing a
  schema of its own is out of scope. When someone genuinely has two timetables,
  that is the trigger.
- **Writing to a calendar.** Never. Openote has no account and no credentials,
  and a re-date control that appeared to work until the next refresh is the
  wrong answer to "read-only".
- **A week/day grid view.** The month grid already exists and is off by default
  because the agenda is what gets read daily. A timetable grid is a genuinely
  nice thing to have and is not the same feature as knowing what is next.
- **Attaching notes to an event.** "Open my notes for this lecture" is the
  obvious next step and wants a mapping between a feed's UID and a section.
  Worth doing; wants the two-machine sync testing done first, because the
  mapping is per-workspace state of exactly the kind that has bitten before.
- **Timezone conversion.** Still the documented v0.5 limitation: Dart ships no
  IANA database, so a `TZID` is read as floating local time. Correct for a
  student's own timetable on their own machine, wrong abroad, and said out loud
  in the calendar warnings rather than guessed at.

## 7. What to watch for

The classifier is the only part of this that can be *quietly* wrong, and the
way it will show up is an alert that does not arrive for something you expected
it to. If that happens, the event's summary is the evidence — the fix is a word
in `_kindWords`, not a redesign.
