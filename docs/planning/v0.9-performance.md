# Openote v0.9 — the performance pass

> **Document status:** v1.0 · built · 2026-08-06
> **Owner:** Eric · **Related:** [PLANNING.md](../../PLANNING.md) · [TESTING](../../TESTING.md) · [ADR-0006](../adr/ADR-0006-sync-transport-and-text-model.md)

## 0. The reports

> *"There are a few areas where the app will just lock up… imports are slower
> than I'd expect. We also seem to have lost the popup when importing a OneNote
> notebook… the whole app completely locks up while that's happening."*
>
> *"Opening the [flashcards] tab is very slow, I believe this is likely because
> it's scanning through the entire notebook… there has to be a more efficient
> way of doing this."* — PLANNING.md

Both reports were correct, and both had the same root shape: **work on the UI
thread that either belonged on another thread or did not need doing at all.**

## 1. The import

### What was actually happening

Three separate faults stacked on one flow:

1. **The popup was lost to a one-line bug.** Onboarding popped its own dialog
   and then passed *the popped dialog's* context as the progress dialog's
   parent. The `mounted` check inside the dialog helper — correct code —
   quietly declined to show anything. A first-run user picked their `.onepkg`
   and watched a frozen app do apparently nothing for a minute.
2. **The parse was off the UI thread; nothing else was.** `jsonDecode` of the
   parser's result (a string that can run to hundreds of MB), a
   `base64Decode` per image, and every database write all ran on the UI
   isolate.
3. **One yield per section.** A hundred-page section was one uninterrupted
   stall; the event loop — input, paint, everything — waited for the whole
   transaction.

### The shape now (`export/import_job.dart`)

The import is a **background job**, not a modal wait:

- The isolate does the Rust parse **and** the JSON decode **and** the image
  base64, returning the finished structure. `compute` hands it back via
  `Isolate.exit`, which is O(1) — no copy ever lands on the UI thread.
- Writes stay on the UI isolate (SQLite handles and `AppState` live there)
  but run in **batches of four pages per transaction, yielding to the event
  loop between batches**. The stall between yields is milliseconds; the test
  suite asserts the property directly by requiring a 1 ms timer to keep
  firing during a 40-page import.
- Progress lives on a **floating card** (bottom-left; alerts own
  bottom-right): live page counts, Cancel at any moment — honoured at the
  next batch boundary, tearing down the half-built notebook — and **Open
  notebook** on completion. The import never navigates anywhere by itself.
- **Onboarding starts the import and stays open.** This is the requested
  flow, verbatim: *"get them to import at the start, then do the onboarding
  while that's working away in the background and is hopefully finished by
  the time they are ready to use it."* The dialog shows an inline echo of the
  progress; closing it leaves the card carrying it.

### What was deliberately not changed

- **The op-log shadow write.** Every imported page and image is also recorded
  into the notebook's op log (ADR-0006 shadow mode), which roughly doubles
  import I/O — the blobs are written twice, once into the container and once
  into the log's content-addressed store. That is the durability contract
  that makes "rebuild from the log" checkable, and turning it off for imports
  is a data-architecture decision, not a performance tweak. It is the next
  big lever if import speed still matters after this pass; it halves the
  write volume the day it is pulled.
- **The single `.one` section import** keeps its modal — a section is small,
  and its parse now includes the decode work in the isolate too.

## 2. The study tab, the tags rollup, and the planner

`deck()` and `allTags()` read and JSON-decoded **every page in the notebook**
on the UI thread. Both memoise, but the memo key includes `docRevision`, which
bumps on *any* page save — so the multi-second rebuild recurred constantly on
a big notebook. The planner's agenda sits on `allTags()`, so it paid too.

Two structures fix it **without a maintained index** — the "one source of
truth beats an index that can drift" rule survives this pass:

1. **A SQL prefilter** (`Repository.pageIdsWithTags`). Tags are stored in
   block content as a literal `"tags":` key, so
   `json LIKE '%"tags":%'` — evaluated inside SQLite, in C — finds every page
   that can matter without decoding anything. Better than designed: because
   JSON escapes quotes inside strings, a page whose *text* mentions `"tags":`
   cannot match — only a real key can. The filter is exact, and the suite
   pins that. Most pages carry no tags and are now never read at all.
2. **A shared decoded-page cache** (`Repository.readPageShared`), evicted per
   page inside `writePage` — the single funnel every page change goes
   through, saves, imports, sync pulls and restores alike. A rebuild after an
   edit re-decodes only what changed. The cache hands out shared, read-only
   instances; editors keep using `readPage`, which returns fresh objects.

The one consumer that genuinely needs *every* block id — the card-state prune
guard, which must never mistake a living card for a dead one — gets them from
a raw regex scan of the stored JSON (`allBlockIds`). A scan can only
over-collect, and over-collection there is the safe direction: an extra id
keeps a dead schedule a little longer; a missing one deletes review history.

## 3. What did not need fixing

Checked and left alone, so the next person does not re-investigate them:

- **Search** already cheap-rejects on the raw JSON before decoding, and the
  brute-force-by-design reasoning on `searchPageContent` still holds.
- **Import plumbing does not notify per page** — the shell repaints on the
  job's own notifier, so a running import rebuilds one card, not the app.
- **The navigator, deck counts and agenda** already memoise on revision
  counters; this pass made the *misses* cheap rather than adding more layers.
- **Per-notebook SQLite handles** mean a background import contends with the
  user's edits on the workspace registry only, which is debounced and
  chained.

## 4. Still open, and honestly

- **PDF import renders slides as images** (PLANNING.md) — a feature gap, not
  a performance one; text selection inside imported PDFs is its own piece of
  work on top of the pdfrx text layer.
- **The op-log double-write** above.
- **`restackFlows` text measurement** runs per imported page on the UI thread
  (TextPainter needs the framework); it is bounded per batch and has not been
  observed to matter, but it is the residual UI-thread cost of an import.
