> waves 1b–1e and 2 planned · 2026-08-06

One release, two threads that turned out to be the same thread. The disk-space
work halved what an import writes, which halved what the import had to stall on;
and chasing the last of the stall found a freeze that was never the import's at
all. They are documented together because neither was fixable alone.

## 0. The reports

Four, in the order they arrived. Each one was accurate, and each one moved the
diagnosis somewhere the previous fix had not looked.

> **(1)** *"We are currently using a huge amount of space for no reason… figure
> out what's causing all the bloating, and identify a fix. Don't be afraid to
> suggest a major overhaul if it's going to bring significant improvements."*

> **(2)** *"The UI still locks up. Visually it updates with the popup, however
> interactions with the page aren't completed until the import is finished."*

> **(3)** *"The import stuff is better and does stuff before locking up, but
> still locks up when it starts displaying all the pages in the popup."*

> **(4)** *"Still the same issue. I also noticed the app is locked up for the
> first few seconds after launching."*

Report 2's split — paint works, interaction doesn't — was the diagnostic for
§2. Report 3's *timing* was the diagnostic for §2.4. Report 4's launch clue was
what finally identified §2.5, and in hindsight it was the largest of the three
by an order of magnitude.

# Part 1 — Storage

## 1.1 Where the bytes actually go — measured

A probe built a synthetic imported notebook — 40 pages, 20 images of 400 KB
(random bytes, i.e. already-compressed media), text and ink besides — and
measured the split:

| Where | Size | What it is |
|---|---|---|
| `Notebook.onote` (container) | **8.37 MB** | SQLite: page JSON mirror, `blobs` table, versions, FTS |
| `Notebook.onotebook/blobs/` | **7.81 MB** | the same image bytes again, content-addressed files |
| `Notebook.onotebook/ops/` | 0.47 MB | one op per imported block |
| **Total** | **16.65 MB** | for **7.81 MB** of actual media |

**Overhead factor: 2.13×.** And a second probe, 100 one-block edits of a
60-line page: the op log grew 0.24 MB (the recorder's block-level diff writes
the whole edited block per save), the container stayed flat, and
`page_versions` is capped at 30 per page with a 10-minute gap — bounded, not
a problem.

## 1.2 The causes, ranked

### 1.2.1 Every image is stored twice *(the dominant cost — exactly 2×)*

`AppState.importBlob` and every image paste write the bytes into the
container's `blobs` table **and** hand them to the sync recorder, which
writes them again as `.onotebook/blobs/<sha256>` (plus, for pre-log
notebooks, `backfillBlobs` copies the whole `blobs` table out on first open).
This is ADR-0006's shadow mode working as designed: the log must be complete
enough to rebuild from, so it must hold the bytes.

The design reason is real. The cost is also real, it is paid by **every**
notebook including the majority that never sync, and it doubles precisely the
largest data class.

### 1.2.2 PDF slides are stored as full-page raster PNGs

`pdf_import.dart` renders each page to a PNG at import. A rendered slide PNG
is routinely 10–20× the size of the PDF page it came from (a page of a
lecture PDF is ~50–200 KB of vector text; its 1600-px raster is 0.5–2 MB) —
and then §1.2.1 doubles it. This is the anatomy of "a 60-slide deck costs
~240 MB". It is also the exact opposite of what PLANNING.md asks for: the
imported PDF should *be* a PDF — selectable, copyable — not a picture of one.

### 1.2.3 The op log only ever grows

Append-only by design, compaction deliberately deferred ("compaction never
deletes log prefixes in v1", ADR-0006). The recorder already diffs saves down
to changed blocks — which is why 100 edits cost 0.24 MB and not 24 — but the
growth is monotonic and lasts as long as the notebook does.

### 1.2.4 Nothing is ever garbage-collected

ADR-0007 designed blob GC (30-day grace, recompute-by-scan); it was never
built. Deleted pages' images, replaced pastes, and cancelled experiments stay
in **both** stores forever.

### 1.2.5 The container never shrinks

No `auto_vacuum`. SQLite reuses freed pages internally but the file holds its
high-water mark, so a notebook that once held a big deck stays big after the
deck is deleted.

### 1.2.6 Footnote, no size cost

Imported images keep their **original** bytes (the Rust parser does not
transcode; a JPEG stays a JPEG) — good — but the importer labels every blob
`image/png`. Wrong metadata, right bytes. Fix in passing.

## 1.3 Wave 1 — targeted, no format change, most of the win

### 1a. Single-copy blobs ✅ *shipped 2026-08-06*

**Materialise the log's blob store only when a notebook actually syncs.** The op
*stream* stays as it is (cheap, §1.1), but `blobs/` — the expensive half — is
written only when the notebook is in a sync folder or is mirrored. The machinery
for late materialisation **already existed and already ran**: `backfillBlobs`
copies the container's blobs out incrementally when a recorder opens against an
existing notebook. This makes that the *normal* path instead of the migration
path.

Measured, same probe run twice, at rest (WAL checkpointed):

| | container | `blobs/` | `ops/` | total | overhead |
|---|---|---|---|---|---|
| Shared (unchanged) | 8.76 MB | 7.81 MB | 0.82 MB | **17.39 MB** | **2.23×** |
| Local-only (after 1a) | 8.76 MB | — | 0.82 MB | **9.57 MB** | **1.23×** |

Exactly the media size comes off, which is what "stored twice" predicts. The
residual 1.23× is the container's own page-JSON mirror, indexes and the op log
— 1c and 1d are what move that.

- Local-only notebooks (most notebooks): **2.23× → 1.23×** immediately.
- Synced notebooks: still 2×, priced honestly as the cost of sync until wave 2.
- Risk: low, and the reason is that **deferred is not lost** — the container
  still holds every byte, so becoming shared materialises the whole set from it.
  Rebuild-from-log verification loses shadow *content* for local notebooks, but
  a log that will never leave the machine verifies nothing an enabled one
  wouldn't.

Three transitions had to be wired, and the third is the one that would have
bitten: moving a notebook into a sync folder, remembering a folder the notebook
already sits in (self-hosted Nextcloud, relocated OneDrive — the notebook never
moves), and **adding a mirror**. A plain mirror copies `.onotebook/` and *not*
the container, so mirroring an unmaterialised notebook would have produced a
backup with no images in it — which is worse than no backup, because it looks
like one.

The user-visible invariant that falls out: **a hollow ring on the sync dot
("This computer only") means exactly one copy on disk.** The predicate behind
the dot and the predicate behind materialisation are deliberately the same rule.

### 1b. Blob GC, both stores

ADR-0007 as written: sweep hashes referenced by no live page (`blob_refs` is
already maintained) and older than the 30-day grace, in the container and in
`blobs/`. Unblocked, designed, just unbuilt.

### 1c. Import PDFs as PDFs

Store the source PDF once as a blob; render page images **on demand** through
pdfrx (the same engine the importer already uses to rasterise at import), with a
small in-memory/thumbnail cache. The printout look stays identical; the storage
cost drops from "raster of every page, twice" to "the PDF, once"; and it is the
load-bearing half of two PLANNING.md asks (selectable/copyable text in imported
PDFs, and the PDF/PPTX thumbnail element). Keep the raster path as a fallback
option for odd PDFs.

### 1d. `auto_vacuum=INCREMENTAL`

On new containers; a one-shot `VACUUM` folded into the existing Repair surface
for old ones (the dialog machinery is already there, and `VACUUM INTO` is
already proven in `duplicateNotebook`).

### 1e. The mime fix

From §1.2.6, while the importer file is open.

**Expected outcome for the probe notebook: 16.65 MB → ~8.6 MB (1.06×)**, and a
60-slide deck from ~240 MB to roughly the size of the PDF itself. (1a alone
delivered 17.39 MB → 9.57 MB on a re-run of the probe; the absolute figures
differ from §1.1's because that measurement excluded the WAL and this one
checkpoints first. The *ratio* is the comparable number, and the delta is
exactly the media size either way.)

## 1.4 Wave 2 — the overhaul: demote the container (ADR-0006's own endgame)

The ADR already names the destination: once rebuild-from-log is trusted, the
**log + blob store become the single source of truth** and the `.onote`
container becomes a rebuildable cache. Then:

- single-copy blobs fall out *structurally* for synced notebooks too (the
  container's `blobs` table empties; readers follow the hash to `blobs/`);
- compaction stops being a protocol problem — a compacted state is just a
  fresh cache plus a checkpoint;
- sync transports exactly one artefact.

**What it costs:** trusting the rebuild (the shadow-mode verifier exists; the
two-machine testing in TESTING.md is the gate), a migration for existing
notebooks (non-destructive: build beside, compare, swap), and a revision of
the File Format Spec — the `.onote`-is-self-contained promise becomes
"`.onotebook/` is the notebook; `.onote` is its fast cache", which is a real
change to the public story and should be versioned as format 1.1, not slipped
in.

**What it does *not* require:** blocking wave 1 on it. 1a–1e are compatible
with the demotion and shrink the problem now.

## 1.5 Storage: considered and rejected

- **Compressing the page-JSON mirror** (zstd the `json` column): breaks the
  spec's core promise — open the container in any SQLite browser and *read*
  it. The mirror is ~4 % of the probe's total; not where the bytes are.
- **Own-log compaction in v1** (a device rewriting its own log's history):
  single-writer makes the rewrite itself safe, but other devices' sync
  cursors are sequence-based, so it needs a generation marker in the manifest
  — protocol surface for a growth rate of ~2.4 KB per edit. Wave 2 makes it
  moot.
- **Character-level text ops** (CRDT deltas instead of whole-block sets):
  the right long-term shape (ADR-0006 reserves it), disproportionate to the
  measured cost today.

# Part 2 — Responsiveness

## 2.1 What was actually happening

### Measured

A probe importing a synthetic 40-page notebook (20 images × 400 KB, text and
ink besides) through the v0.9 batch writer, on the fast dev container:

| | |
|---|---|
| batches (4 pages each) | 10 |
| median batch | **57 ms** |
| p90 / max batch | 136 ms |
| whole write phase | 615 ms |

That is the *friendly* case: small images, Linux, warm disk, no antivirus. A
real notebook with 2–5 MB photos on Windows — where every flush pays Defender
tax — plausibly runs **200–800 ms per batch**, for minutes.

### The mechanism

The v0.9 rework yields between batches with `await Future.delayed(Duration.zero)`.
That buys **one event-loop turn**, not a frame budget. Two consequences:

- **Paint survives.** The engine's frame callbacks are scheduled events; a
  vsync that lands in the gap gets its frame. Hence "visually it updates" —
  the progress card animates.
- **Interaction starves.** A click is not one event; it is a conversation:
  pointer-down, pointer-up, gesture-recognizer resolution, the handler, a
  state change, a rebuild, a paint — and for anything real (clicking into a
  text box, switching pages) an async continuation that reads the database.
  Every leg of that conversation must fit into one of the slivers between
  batches, and each sliver is followed immediately by the next 57–136 ms
  chunk. The legs queue; the interaction completes when the import does.
  Which is report 2, verbatim.

### What a batch spent its time on

In descending order, all on the UI thread:

1. **fsync'd op-log writes.** `OpLogStore.writeBlob` is
   `writeAsBytesSync(flush: true)` per image, and every op append is
   open → write → `flushSync` → close. An fsync is the single most expensive
   thing a UI thread can be asked to do, and the blob double-store (§1.2.1)
   means each image's bytes were written — and synced — **twice** inside the
   batch.
2. **SQLite inserts** — page JSON and blob bytes into the container
   (WAL, `synchronous=NORMAL`, so cheaper than the log writes, but multi-MB
   inserts are still tens of ms).
3. **`restackFlows`** — TextPainter measurement per imported box. Genuinely
   UI-thread-bound (text layout needs the framework), but small next to 1–2.
4. JSON encodes of every page.

## 2.2 The options

### Option A — pace by time, not by page count *(small; a day)*

Replace "4 pages per batch" with a time budget: write until ~8 ms have
elapsed, then `await SchedulerBinding.instance.endOfFrame` — which, unlike a
zero-delay timer, doesn't continue until a frame has actually been produced —
plus one extra event-loop turn for input.

- **Gets:** the common case feels alive; the gap between chunks is a real
  frame, every frame.
- **Cannot get:** atomicity of the indivisible steps. A single 5 MB image is
  one `writeBlob` + one SQLite insert; you cannot split an fsync. Image-heavy
  pages still hiccup 50–200 ms each.
- **Risk:** low. Same code path, different pacing.

### Option B — take the fsyncs off the synchronous path *(medium; 1–2 days)*

The op-log writes don't have to be synchronous *or* inside the batch:
`dart:io`'s async file APIs run on internal worker threads. Restructure the
batch to do SQLite work synchronously, collect the log writes, and `await`
them (async, flushed) between chunks.

- **Gets:** removes the single biggest cost from the blocking span.
- **Cost:** the recorder's calls become awaitable on the import path, and the
  log lands *after* the container commit rather than beside it — acceptable
  in shadow mode, but it is a loosened ordering and the docs must say so.
- **Risk:** medium-low. Ordering reasoning, no new architecture.

### Option C — a writer isolate *(the real fix; 2–4 days)* ✅ chosen

Move the entire write phase off the UI thread. The import target is a **brand
new notebook** — no other code holds its SQLite handle, its log files, or any
in-memory state — so a second isolate can own it outright.

- **Gets:** the UI thread does *nothing* during import except receive
  progress messages. Typing during a 300-page import is indistinguishable
  from typing while idle — which is the promise the feature made.
- **Risk:** medium. New seam, but a clean one — the isolate owns files nothing
  else has open, which is the property that makes it safe.

### Considered and rejected

- **Lowering fsync guarantees** (`flush: false`, `synchronous=OFF`) — buys
  speed by making the durability promise quietly false. No.

**Sequencing:** storage wave 1a first, because it halves the write volume every
batch has to get through before C even lands. That is exactly what happened —
the same 40-page probe went from **57 ms median batch to 18.3 ms**, whole write
phase 615 → 257 ms, purely from the fsync'd `blobs/` write per image no longer
happening for local-only notebooks.

## 2.3 What shipped — the writer isolate

**C, as built, differs from the plan in one place.** The plan had the main
isolate parse and hand a structure to the writer. It doesn't: **one isolate
reads the file, parses it, and writes**, so the images are born there and never
cross a port. The reason is a precondition a probe settled — `TextPainter`
throws *"UI actions are only available on root isolate"*, so `restackFlows` is
stuck main-side. Rather than keep the parse output main-side for its sake, the
writer **asks** the main isolate to lay pages out and waits for the corrected
y-coordinates. Measured at **1.2 ms per page**, that is the entire main-thread
cost of an import.

Two supporting refactors, each its own commit: `NotebookWriter` (the six
container writes, against a bare `Database`, so Repository and the isolate share
one implementation) and `ImportSink` (the seam the translation writes through —
six methods, which is all it ever needed from `AppState`).

### What it measured

Same 200-page synthetic notebook, same instrument: count how long each **leg**
of an interaction waits to be scheduled — a timer hop plus a microtask drain,
which is what every step of a gesture → handler → setState chain costs.

| | before (in-process) | after (writer isolate) |
|---|---|---|
| legs completed during the import | 50 | **2349** |
| median leg | 12.8 ms | **0.1 ms** |
| p99 leg | 19.3 ms | **1.6 ms** |
| worst leg | 19.3 ms | 9.3 ms |

Fifty legs for fifty batches is the mechanism in §2.1 reproduced exactly: one
event-loop turn per batch, which a frame can use and a conversation cannot.

Three faults fell out of building it, all fixed:

- **Cancelling an import could keep the notebook.** Teardown soft-deleted then
  purged, and `deleteNotebook` refuses the *last* notebook — so in a workspace
  with nothing else in it, a cancelled import stayed in the list. Discarding a
  never-really-a-notebook now bypasses the recycle bin entirely.
- **The handover had a race.** The writer sent "done" and then disposed its
  SQLite handle; the main isolate reopened on the message and won, with
  `database is locked`. Handing a file over is not finished until the handle is
  gone, so the terminal message is now sent after the close.
- **Imported notebooks were named `Whatever.onepkg`.** The single-section path
  stripped the extension; the package path never did.

## 2.4 Round two — the layout request was itself a freeze

Report 3's timing named the bug. The progress card first shows a page total when
the writer's `parsed` message arrives — and the very next thing the first build
sent was **one measurement request covering every page in the notebook**.

Two faults in one message:

1. **Receiving is uninterruptible.** An isolate message is deep-copied by the
   receiver in a single go. The frame pacing inside the restack loop could not
   help, because the block was over before the loop started. Measured: 200 pages
   cost a 6 ms stall, 1000 pages 47 ms, 3000 pages 48 ms and rising with content
   — and those boxes carried the parser's tag lists and style runs, which the
   restack never reads.
2. **Nothing was written until everything was measured.** So the card showed a
   total that then sat still for as long as the layout took. On a five-year
   notebook that alone reads as a freeze, whether or not input is blocked.

Three changes, measured on a 2000-page synthetic import (5 boxes/page of wrapped
text), with the frame yield modelled realistically at 16 ms:

| | p99 interaction leg | worst | wall clock |
|---|---|---|---|
| one request, whole boxes | — | 48 ms *(layout phase alone)* | — |
| per batch, projected boxes | 12.2 ms | 21.8 ms | 13.4 s |
| …plus pipelining | **14.3 ms** | 27.6 ms | **11.0 s** |

- **Per batch.** Four pages ask for their own layout immediately before being
  written. Messages are kilobytes, and progress moves from the first batch.
- **Projected.** Only the nine fields `restackFlows` and `_measuredFlowHeight`
  actually read cross the boundary. `flow_projection_test.dart` fails if that
  list drifts — a projection missing a field would misplace imported content
  silently, which is the exact failure the restack exists to prevent.
- **Pipelined.** Batch *n+1* is laid out while batch *n* is written, so the
  measurement is off the writer's critical path.

**On the budget.** The layout pass gives a frame back when a chunk overruns
12 ms — just inside a frame. Tightening that to 8 ms took p99 from 14 ms to
4 ms, both far below anything a person can see, and made the import **60 %
slower**, because each extra yield waits a whole frame the writer is blocked on.
A chunk that fits inside a frame costs nothing visible; interrupting it costs
real time.

## 2.5 Round three — the freeze was never the import's

Report 4's launch clue cracked it: something froze the app that scales with what
an import *leaves behind*, not with importing. It was `SyncRecorder.open` —
which reads, JSON-decodes and replays **every op ever written** before
returning. Measured: **489 ms** for the 14 MB log a 2000-page import writes, on
a fast machine; a real notebook with multi-MB ink blocks, on Windows, plausibly
seconds. It ran synchronously on the UI thread from two innocent-looking places:

- **`_startWatching`, on the first frame after launch.** The whole lockup at
  startup, in one call.
- **`syncDeviceCount`, from every sync dot's first paint.** So the moment an
  import finished — guard lifted, UI refreshed, the new notebook's dot painted
  for the first time — the app replayed the giant log the import had just
  written. That is "locks up when it starts displaying all the pages in the
  popup", and it is why §2.4's fix (real, but tens of milliseconds) didn't make
  the report go away: the seconds were here.

Three changes:

1. **Status reads never open a recorder.** The device count is a directory
   listing (`OpLogStore.deviceIds`, 0.24 ms where the replay cost 489 ms) and
   the watcher takes paths plus the settings device id. A side effect died with
   it: painting a dot no longer *creates* `.onotebook/` directories for
   notebooks that never recorded anything.
2. **The replay runs in a background isolate** (`SyncRecorder.openAsync` →
   `AppState.warmRecorder`), started at launch, on notebook selection, and at
   import completion. `Isolate.run` hands the replayed state over via
   `Isolate.exit` — ownership transfer, not a copy — so receiving it costs O(1),
   not a repeat of §2.4's mistake. Measured at launch with the 2000-page log:
   dot paint 3.4 ms, warm lands in the background ~430 ms later, first edit
   2.6 ms.
3. **The synchronous open survives only as the mutation path's fallback**, for
   an edit that beats the warm. The race is settled by discard: if a recorder
   exists when the warm lands, the warm is thrown away, and `openAsync`
   guarantees a discarded recorder has written nothing (title seeding is
   deferred to the installer) — installing a stale replay would re-issue
   sequence numbers the log already contains, which is the one-writer invariant
   broken from the inside.

The restack also now paces **between boxes**, not just between pages
(`restackFlowsPaced`) — though §2.7 shows that was still not enough.

### 2.7 Round four — the atomic box

> *"I think the stall on startup is just a debug artifact, i built the exe and
> it had no stall at startup, it was super quick. The stall during import
> though was still very much there."*

A release build, so §2.5's debug-amplified replay was off the table for
startup — and the import stall survived even with everything above shipped.
Two theories measured, one confirmed:

- **GC bleed** — `Isolate.spawn` shares the spawner's isolate group, a group
  shares one heap, and old-space pauses are group-wide, so the parse's
  allocation storm could in principle stall the UI isolate with no code shared
  at all. Probed: p99 main-isolate leg was **0.9 ms** while a worker decoded
  50 MB of JSON in a loop. Real, and irrelevant. Killed.
- **The atomic box.** Every pacing layer so far — between pages, then between
  boxes — still measured one box in one `TextPainter.layout`. Probed with real
  sizes: a 50-line box is **18.5 ms** (already over a frame), 800 lines
  **96 ms**, 2000 lines **216 ms**, 5000 lines **613 ms**. Real lecture pages
  routinely carry one full-page text box; none of the synthetic probe pages
  did, which is why three rounds of fixes each measured clean and the user
  kept being right.

The fix is chunked measurement. With one uniform style per box and an explicit
`height` multiplier, every line box is exactly `fontSize × height` tall, so
hard-broken lines lay out independently and per-chunk sums equal the whole
**to the bit** — probed first across wrapping, interior empty lines, unicode
and unbreakable words. One exception, also probed: a chunk that is exactly one
empty line joins to `''`, which an empty `TextPainter` gives the font's
natural height instead of the line box — so the chunker never strands a lone
empty final line. 64 lines per chunk ≈ 8 ms.

| box size | atomic (before) | worst block (after) |
|---|---|---|
| 800 lines | 96–112 ms | **13.5 ms** |
| 2000 lines | 216–242 ms | **13.5 ms** |
| 5000 lines | 613–702 ms | **15.7 ms** |

A fuzz test pins sync-vs-paced equality over seeded random nasty content, and
the end-to-end responsiveness test now carries giant pages permanently — its
worst-leg assertion reads **326.7 ms against the atomic code** and ~14 ms
against the chunked one, verified in both directions.

### Two implementation notes, recorded so they aren't re-learned

- A closure handed to `Isolate.run` captures its enclosing **context**, not just
  the variables it names. Inlined in `openAsync`, it silently dragged
  `writeSetting` along — a tearoff of `Repository.setSetting`, which holds the
  workspace debounce `Timer`, which is unsendable. The replay lives in its own
  static function whose scope is two strings.
- The install originally hung — deterministically — when written as a
  `.then().catchError().whenComplete()` chain on the `Isolate.run` future, and
  worked when traced with `debugPrint` (whose throttle timers changed the
  scheduling). Rewritten as plain `async`/`await`: identical semantics, hangs
  gone, verified across eight suite runs. **The chain form is banned from this
  path.**

## 2.6 Three more defects, found reviewing the above

Not reported by anyone — found by reading the finished code, which is the point
of doing that.

- **A box the parser gave no position landed at `y = 0`.** The layout round trip
  reported a missing `y` as 0 rather than "missing", so `importOneParsedPage`'s
  `?? contentTop` default never applied and the box was written under the page's
  title band. The regression test reads 0.0 against the old code, 92.0 against
  the fix.
- **The device id would eventually have forked on every imported notebook.**
  `rememberImportedSeq` ran *after* the call that starts the replay whose
  identity check reads that very setting. It worked only because nothing awaited
  in between — an invisible dependency on synchronous continuation ordering,
  whose failure mode is silent.
- **A discarded import could leave an orphaned `.onotebook`.** The cancel path
  warmed the recorder for a notebook it was about to delete; the replay rewrites
  `manifest.json` on its way through, so one landing after the purge recreated
  the directory it had just removed — and an orphan is what the free-name search
  downstream trips over.

`AppState.settleBackgroundWork()` came out of the same pass: replays, backfills
and mirror runs are fire-and-forget by design, but *"nobody waits"* and
*"nobody can wait"* are different, and the second is how late file I/O lands
after its directory is gone.

## 3. How we know it worked

The old responsiveness test (a 1 ms timer must keep firing during a 40-page
import) was necessary and too weak — it passed the whole time the user's clicks
were starving, because firing is not the property that matters.

Replaced by the leg-latency measurement in §2.3, which asserts **p99 under one
frame across the entire import** and that at least a hundred legs completed
during it. Confirmed to bite: run the identical loop around the old in-process
writer and it fails on both counts (p99 19.3 ms, 50 legs). Alongside it:

- `import_writer_test.dart` — the isolate spawned for real against real files,
  including cancel, the seq handoff, wave 1a's hollow log, and "pages start
  landing straight away" (the §2.4 regression pin).
- `flow_projection_test.dart` — the projected box measures identically to the
  whole one, verified to fail when a single field is dropped.
- `recorder_warm_test.dart` — status reads touch no recorder and create no
  directories; a mutation that beats the warm wins without duplicate seqs.

The manual headline in TESTING.md stands, now with "and click into text boxes"
added — a test that measures scheduling latency cannot tell you the app *feels*
right.

## 4. What's left

1. **Storage 1c** (PDFs as PDFs) — the biggest absolute win for the notebooks

2. **Storage 1b** (blob GC) — designed in ADR-0007, unblocked, unbuilt.
