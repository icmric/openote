# Op-log compaction: designed twice, challenged, not built

**Status: rejected as designed — do not implement without answering every
kill-shot below.**

The op log is append-only and holds every pre-conversion giant ink op. On the
measured notebook that is 64.56 MB of `.oplog` (the user reported 112 MB on
another machine), and it is what a full replay reads and what actually syncs.
Nothing in the app can shrink it, and `Reclaim space` truthfully reporting
"nothing to reclaim" while the log sits at 112 MB is worse than either a lie or
a fix.

Two designs were produced independently and each was adversarially challenged
by an agent instructed to refute it against the real code and the real log.
**Both verdicts were "unreliable."** This file preserves what the round
established, because most of it was expensive to learn and all of it will be
true next time too.

## Settled facts (claimed by the designs, independently confirmed)

- **In-place rewrite of `<dev>.oplog` is disqualified, with numbers.**
  `readDeviceFrom` resumes AT a stored byte offset whenever `from <= len`
  (`op_log.dart:203` — only a file that *shrank below the offset* restarts at
  0), and `pendingForeignOps` filters on `op.seq > seen` with no gap check
  (`sync_recorder.dart:406-408`), so it cannot recover ops it never read.
  Simulated on the real 67,695,338-byte log: a returning device with a 1 MB
  watermark silently skips **1,994 ops it has never seen**. Silent, permanent,
  and only visible on the other machine.
- **Any rewrite must copy verbatim line bytes.** `Op.toJson` emits exactly
  `{v,dev,seq,lc,ts,enc,op,d}` and decode reads only those — a rewrite through
  `Op.encode` drops any envelope key a newer build wrote, and `d` is not even
  numerically byte-stable through jsonDecode/jsonEncode.
- **The supersession key for `block.set` is `(d.pageId, d.block.id)`** — there
  is no top-level `blockId` on that op, unlike `ink.strokes`/`block.remove`
  (`materializer.dart:105-117`). A compactor reading `d['blockId']` uniformly
  buckets every `block.set` wrong.
- **A soft `node.delete` keeps its page's blocks live.** Only `node.purge`
  erases page state. Dropping a deleted page's `block.set` ops would restore an
  empty page from the recycle bin — data loss disguised as a 30-day feature.
- **Ordering: compaction is worth ~nothing until the ink conversion records.**
  Measured: the own-anchor drop rule frees **0.10 MB of 64.56 MB** on a log
  whose 63.14 MB of inline ink is still LIVE state (nothing supersedes it).
  After `convertInkToBinary` records its superseding ops into the same log, the
  identical rule frees ~63 MB (projected ~1.4 MB kept, 46×). The automatic
  housekeeping shipped in v0.12 is therefore the *prerequisite*, and it makes
  the log slightly **larger** in the short term.
- **Nothing here shrinks a git remote.** `commitAll` is `git add -A`; retiring
  a log commits a deletion while the blob stays in history and every clone
  still downloads it. The only fix is an orphan branch / fresh repository — a
  user-visible, re-join-forcing action, never automatic.

## Kill-shot on the proposed fix (generational rotation)

The design proposed: freeze `<dev>.oplog` forever, copy surviving lines as
verbatim bytes to `ops/<dev>~g1.oplog`, append there from then on, retire gen0
after a 30-day acked grace period. Its load-bearing claim — "no other device's
watermark is touched, because both are keyed off the FILE NAME" — is **false on
the write side**:

- Watermarks are *read* per file (`deviceIds()` → settings key per name) but
  ***written* per the envelope's `dev` field**: `markForeignSeen`'s only caller
  keys on `op.device` (`app_state.dart:1500-1505`). Verbatim-copied lines still
  carry `"dev":"<dev>"`, so `syncSeen:<nb>:<dev>~g1` is **never written by any
  code path**. Every other device re-reads gen1 from byte 0 on every pull,
  forever; `foreignPending` is raised on every pull; and `page()` bails while
  it is true — the permanent version of the silent-non-recording failure that
  `c0a26d5` fixed a transient case of.
- Worse: that pull *advances gen0's seq watermark to gen1's maximum* while
  keeping gen0's byte offset, so any line that later reaches gen0 is skipped by
  the seq filter. Corruption of the *old* file's watermark by the *new* file's
  content.
- **The single-appender assumption at rotation time is false.** A synchronous
  `SyncRecorder.open` can win the race while the background replay runs
  (`sync_recorder.dart:150-154`, `app_state.dart:938-946` document exactly
  this), and the import-writer isolate is a second appender whose gate does not
  cancel in-flight warms. A line appended to gen0 after the copy pass exists
  only in gen0 — and Stage C then deletes gen0. No proposed retirement gate
  checked the one property that matters: *gen0 contains no line absent from
  gen1*.
- `File.rename` **replaces** an existing destination on Windows (the codebase's
  own temp+rename sites rely on it), so "create gen1 exclusively" via an
  exclusive *temp* file protects nothing: a second process's rotation silently
  clobbers a gen1 that already holds appended user ops.
- During the transition (≥30 days, indefinite if retirement is never safe)
  `readAll()` reads **both** generations, so open-time replay is *worse* than
  today. The headline speed win belonged entirely to the snapshot; the size win
  entirely to the retirement step the risks section itself said may never be
  safe.
- Backup mirrors (`keepVersions > 0`) copy every file unconditionally into
  fresh timestamped directories, multiplying the both-generations transition by
  `keepVersions`.

## Kill-shots on the snapshot-of-replayed-state idea

A local snapshot of `Materializer` state + per-file offsets, to kill the ~2 s
open replay:

- **A snapshot is a prefix of the TOTAL order, and foreign logs routinely
  arrive carrying lamports BELOW the local horizon** (written concurrently,
  delivered late by file copy). `Materializer.apply` is position-in-stream
  dependent (`block.set` last-in-stream-wins; `ink.strokes` *drops the op*
  when its block is absent), so applying late-arriving ops on top of a
  snapshot ≠ re-sorting and replaying. The replayed state is what
  `SyncRecorder.page` diffs against; diffing against wrong state emits stale
  `block.set` ops at a higher Lamport that **revert the other device's edits
  on every replica**. The "invalidate when a file shrank" test never fires for
  this — the log *grew*.
- Length-only invalidation also misses every event that changes bytes without
  shortening: cloud "restore previous version", conflict-copy swaps,
  `git checkout` to another history. A persisted replay cache needs a
  **checksum of the consumed prefix per file**, not a length.
- An own-device-only offset is wrong: `readAll()` spans every device's log, so
  resuming needs per-device offsets for all of them — and reusing the
  `syncSeenAt:` family collides with its pull semantics.
- ADR-0006 §3's reserved `snapshots/` directory is **inside the synced tree**
  and not gitignored, so a snapshot there is pushed, mirrored, and *adds*
  synced bytes; superseding one means deleting a synced file — the exact thing
  ADR-0006's safety argument ("deletes never happen") depends on never doing.
  Any snapshot must live outside the notebook (a deliberate, documented
  deviation), versioned, and be discarded-not-partially-trusted on any
  mismatch. Also priced honestly: until the ink conversion has recorded,
  the materialised state to serialise is ~64 MB, not ~1 MB.

## What must be true before anyone tries again

1. The ink migration has recorded on **every device** (housekeeping does this
   automatically now; it is the thing that creates the anchors).
2. Watermark keying is made file-based on **both** read and write sides
   (`pendingForeignOps` must report which *file* each op came from, and
   `markForeignSeen` must key on that), shipped and baked on all devices
   *before* any second file per device exists.
3. Rotation runs under a proven single-appender lock covering the synchronous
   open path and the import-writer isolate, claims `gN` with a genuinely
   exclusive create (not temp+rename), and retirement is gated on a mechanical
   `gen0 ⊆ gen1` byte check — not on time or acks alone.
4. The compactor copies verbatim bytes, aborts on anything it cannot fully
   interpret (unknown kind, `enc != 'none'`, `v >` known, envelope key outside
   the eight), and proves three-way `Materializer` equivalence (gen0-only /
   gen1-only / both) with `canonicalJson` **at runtime, before the rename**.
5. The never-drop list holds: `block.remove`, `node.delete`, `node.restore`,
   `node.purge`, `node.upsert` (it merges), `blob.put`, `notebook.meta`,
   unknown, undecodable.

Until then: the log stays append-only, exactly as ADR-0006 promises. After the
ink migration it grows by small reference-form ops only, so the 112 MB is a
one-time cost that stops compounding — real, bounded, and honest to say out
loud rather than half-fix.
