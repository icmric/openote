## The corrections

Two things this document asserted turned out to be wrong, found while building
Steps 1 and 2. They are corrected in place *and* recorded here, because both
were load-bearing for a proof.

**Correction 1 — `workspace.json` already had a `format` field.** This document
said it was *absent*. It never was. `_saveWorkspace` has always written
`{"major": 1, "minor": 0}` (`app/lib/store/repository.dart`, the `'format':
{'major': workspaceFormat, 'minor': 0}` line), and **spec §7 documents exactly
that shape** (`docs/specs/10-file-format-spec.md:192`). It was simply never
*read*. So Step 1 did not introduce a field; it introduced the **reader**, and
that changes what the guard has to tolerate:

- `Repository._formatOf` accepts the documented `{"major": n, …}` map **and** a
  bare integer, so a future build that flattens the field is still guarded by
  this one.
- **An unrecognised shape reads as COMPATIBLE, deliberately.** The code says
  why, and the reasoning is the whole design: a shape we do not recognise means
  "written by a build that predates the guard", which is by definition not
  newer than us. Guessing "newer" there would put every existing user's
  notebook list into read-only mode — the exact harm the guard exists to
  prevent.
- When the format *is* higher, the registry loads (those entries are real
  notebooks and the student should be able to open them) and is simply never
  written back, with a plain-words explanation and the technical line folded
  away.

**Correction 2 — Step 1's suggested proof stops working after Step 2, by
design.** This document proposed planting an undecodable `*.oplog`. Step 2's
whole business is making that decode tolerant, so after Step 2 the plant
succeeds silently and the test proves nothing. The shipped tests plant **a file
where the `.onotebook` directory belongs** instead
(`app/test/recorder_warm_test.dart:191`): it makes
`opsDir.createSync(recursive: true)` fail deterministically on every platform,
where "make the folder unwritable" is flaky on Windows. The truncation
behaviour Step 2 fixed is proved separately, table-driven, in matrix rows
F1–F3.

# Part 1 — What we are NOT doing

Cutting scope on evidence is the most valuable output of this investigation.
Five things in the cluster are cut. Each is recorded here so nobody
re-discovers them in six months.

## 1.1 #54 in its entirety — **close it**

The task is four mechanisms. All four were measured on the real logs, and one
of them was reproduced destroying real data.

| Mechanism | What it was for | Measured today | Verdict |
|---|---|---|---|
| **Log segments** (rotate at 8 MB) | GitHub's 100 MB single-file reject; whole-file re-reads | Live log is **1,523,044 B** — 1.5% of the limit. Rotation would never fire. Segmenting the current log to 256 KiB leaves CPU unchanged (33–37 ms vs 31 ms) and **triples wall time** (115 ms vs 53 ms), because the paced fold's wall clock is set by total bytes, not file count. For git it is *worse*: `.git` 344 KiB segmented vs 337 KiB monolithic after `gc`, because separate files defeat cross-segment delta. | **Cut** |
| **gzip closed segments** | Shrink the synced set | 5.52× on log text, but **1.00× on ink blobs** (already a zlib level-9 stream inside the OIS1 container — confirmed positively by inflating 20 blobs: 716,478 → 1,274,966 B) and **1.05× on PNG**. Gzipping everything gzip can help saves **1.98 MiB of a 34.95 MiB notebook (5.7%)**. It cannot touch the active tail: a compressed active segment turns a 522-byte append into a **212–322 KB rewrite every 700 ms autosave pause** (400–600× write amplification). And a truncated gzip member loses up to a whole member where a truncated line loses one op — trading away the exact property JSON Lines was chosen for. | **Cut** |
| **Snapshots** | Get open-replay under ~150 ms | Rebuilding the entire 329-page notebook from its log is **54 ms of CPU** (33 read+decode+sort, 2 materialize, 20 encode 329 mirrors); end-to-end 97–120 ms, in a background isolate. There is nothing to optimise. A snapshot would also *add* bytes inside the synced tree and, per ADR-0006 §3's `snapshots/`, superseding one means deleting a synced file. | **Cut** |
| **Own-history compaction** | Reclaim superseded bytes | Superseded bytes are **0.00% of Honours-4's log**, **0.16% (0.104 MB) of Honours-2's 64.56 MB log**, and **143 KB** of My Notebook's 268 KB. It reaches 93% only on edit-driven history, and the only edit-driven log in existence is 274.6 KiB total. | **Cut** |

Compaction is also the only one that can lose notes, and a spike reproduced
that **on the owner's real 1.5 MiB log**, not on a synthetic one:

- **Byte-offset corruption.** `readDeviceFrom`'s only guard is
  `from <= len` — a guard against a *shorter* file, not a *different* one.
  After device A compacts (1,585,183 → 1,567,083 B), a peer resuming at its
  stored offset silently lost **7 blocks at a 25% read point, 10 blocks + 3
  nodes + 2 blob refs at 50%, 24 blocks + 1 node + 1 blob ref at 75%**. No
  error anywhere. Invisible on the machine that compacted; total on the other.
- **The obvious implementation corrupts real data.** "Keep the last op per
  target key" on My Notebook's real log produced a state difference against a
  full replay: node `019fdff4-…` has `node.upsert@lc149`, `node.upsert@lc152`,
  `node.delete@lc184`; keeping only the delete makes `Materializer.nodeDelete`
  `putIfAbsent` a default node, and **the deleted page reappears in the recycle
  bin** with an empty title. Same rule drops the `block.set` an `ink.strokes`
  op depends on, and `Materializer.inkStrokes` then hits `if (block == null)
  return;` — the handwriting disappears and the log looks intact.
- **The rewrite loop loses roughly one op per window boundary** if the
  straddling-line carry is dropped — measured by deliberately removing it: 77
  ops lost on the 64.56 MB log, 3 on the 1.51 MB one. A spike author
  introduced this bug in his own first draft without noticing.

[v0.13](v0.13-op-log-compaction-review.md) rejected this design twice already,
from a different direction, and every one of its five kill-shots still stands.
Two of them were independently re-reproduced this round on the *post*-Phase-1
log shape. **#54 is closed. The log stays append-only, exactly as ADR-0006
promises.**

> **The one real instance of #54's problem, and its actual fix.** Honours-2's
> 64.56 MB log is genuinely large. Its cause is 113 ink `block.set` ops holding
> 64,616 strokes in 66,204,680 bytes — **97.8% of the file**. The fix is
> pressing the existing **Shrink handwriting** button (`convertInkToBinary`),
> not a format change. It has never run on that notebook because automatic
> housekeeping requires the notebook to be *open* and Honours-2 is not
> registered in `workspace.json` at all. A button press, offline, verified,
> opt-in — see §4.3.

**When to revisit:** when a real device's post-Phase-1 log passes ~8 MB. The
number to watch is not size but **write amplification**: measured 2.55× on the
one genuinely edit-driven log (237.6 KB written for 93.1 KB of final content;
worst single block 20.1×). If it is ever taken up, the shape to reach for is
**append-only multi-member gzip** (RFC 1952 concatenated members — measured
within 6.2% of ideal at 64 KiB members, never rewrites or deletes a byte, and
therefore sidesteps every kill-shot above), *not* rotation-plus-compaction.

## 1.2 ADR-0006 §3's literal layout — **amend the ADR, do not implement it**

§3 (2026-07-27) draws `cache.onote` **inside** `MyNotebook.onotebook/`. §8
(2026-08-03, six days later) made that same directory the git repo root and the
thing Drive/OneDrive/Dropbox/Syncthing replicate. Putting a live WAL SQLite
database inside the replicated tree re-creates precisely the torn-database
hazard §2 exists to prevent.

git tolerates it — `git check-ignore -v` reports
`.gitignore:8:*.onote  cache.onote`, and `git_sync.dart:203-213` writes that
ignore file. **The four consumer providers have no per-file ignore at all.**

The code already does the right thing (the container is a sibling, or lives in
the local workspace). **The ADR is what is wrong.** Leaving the diagram as
drawn invites a future implementer to "finish the job" by moving a WAL database
into a cloud folder. §3 and spec §11's identical diagram both need amending as
part of Step 4.

## 1.3 "Mirrors go incremental" (#55) — **already done**

`mirrors.dart:67` reads, in its own doc comment: *"Copies **newer-or-missing
files only**."* Nothing to do. Close that line of #55.

## 1.4 "Backups stop snapshotting the container" (#55) — **cut, deliberately**

`mirrors.dart` decided the opposite on purpose, and its reasoning is right: *a
snapshot you have to reconstruct before you can read it is not what anyone
wants in an emergency.* It uses SQLite's own `VACUUM INTO` (`mirrors.dart:75`),
never a plain file copy of an open database. After demotion that snapshot is
**1.34 MB** (measured `cache.onote` size), so it becomes cheap rather than
something to remove. Keep it.

## 1.5 Image re-encoding — **cut from this cluster, not from the roadmap**

Two passes measured it independently and it is the biggest remaining number:
PNG images are **26.33 MB, 72% of Honours-4's content**, and re-encode to
**15.50 MB lossless WebP** (58.9%, verified by decoding all 378 back and
comparing RGBA bytes: **0 pixel mismatches**) or ~9.76 MB lossy at q88. That is
8.7× the entire yield of #54.

It is cut from *this* cluster for a hard reason: **re-encoding changes every
content hash**, and hashes appear in `page_mirror.json`, `blob_refs`,
`page_versions.snapshot` (which holds *older* page JSON naming *older* hashes),
`refs`, and every device's unsynced logs. `page_versions` is exactly the
page-scoped table with no foreign key — commit `1be2d28` exists because of that
blind spot. And **blob GC does not exist** (ADR-0007, unbuilt), so the old
blobs would simply accumulate and then be collected wrong.

> **Decision 1 removes one of those five hash carriers.** Step 8a drops
> `page_versions`, so *"older page JSON naming older hashes"* stops existing.
> Four carriers remain — `page_mirror.json`, `blob_refs`, `refs` and every
> device's unsynced logs — and the logs are the hard one, because §4.1 forbids
> rewriting a log line, ever. So the ordering **demotion → blob GC → image
> re-encode** is unchanged; it is one degree less tangled, and the surviving
> objection is entirely about the log.
>
> Decision 3 shrinks the other half of the objection. §7.3 asked whether a
> minimal third-party reader must be able to decode WebP; with the container
> demoted to a cache, that question is now about the blob payloads named by an
> open log, not about the format of a file we hand people. Still a real
> question. A smaller one.

Correct order, which is also what v0.4 §2.4 argues on independent grounds:
**demotion → blob GC → image re-encode.** Open it as its own task after this
cluster, with the open-format question (§7.3) answered first.

## 1.6 What replaces #54 in the backlog

**ADR-0007's blob GC.** It now has a measured target and nothing in the
codebase can free a single byte: `grep` finds no code anywhere that deletes
from the `blobs` table or from `blobs/`. Orphan blobs (rows with no `blob_refs`
row) measured: **Honours-2 18 blobs / 1,691,344 B; Honours-4 3 / 250,178 B; My
Notebook 2 / 566,810 B — 20% of that notebook's blob bytes.** Phase 1 moved the
garbage out of the log and into `blobs/`, where nothing collects it. ADR-0007's
own "Revisit triggers" section names *"a user reports Openote filling a disk"*;
the duplicates finder shipping suggests that trigger has effectively fired.

# Part 2 — What we ARE doing, and why the case changed

## 2.1 The seam the tasks were bundled across

#39/#55 bundle **a size win Phase 1 already collected** with **a correctness
win they never mention**. Split on that seam.

**The size win shrank.** v0.11 §1.2 costed the demotion when the double-store
was 63 MB of ink JSON plus 26 MB of images, and quoted 2.23× → 1.05×. Measured
today, end to end, by a spike that actually performed the migration on copies of
the real notebooks:

| Notebook | Before | After | Saved |
|---|---:|---:|---:|
| **Drive notebook** (shared) | 63,193,548 B | 32,578,572 B | **30,614,976 B (48.4%)** |
| **Honours-4** (local-only) | 36,689,419 B | 32,630,831 B | **4,058,588 B (11.1%)** |

The local-only case is the *majority* case — that is why `materialiseBlobs`
defers image bytes at all. So the honest framing is: **an 11% win on most
notebooks, a 48% win on the ones that sync.** Not a 2.23× → 1.05× overhaul.

**The correctness win is live, on the owner's machine, right now.** Google
Drive is replicating a WAL SQLite database:

```
G:\My Drive\Openote\
  Eric - Computing Science Honours (2).onote        31,674,368 B   ← open in openote.exe
  Eric - Computing Science Honours (2).onote-wal       247,232 B   ← replicated independently
  Eric - Computing Science Honours (2).onote-shm        32,768 B
  Eric - Computing Science Honours (2).onotebook/    31.24 MB
  Eric - Computing Science Honours.onote            35,979,264 B   ← orphan, no .onotebook
  Eric - Computing Science Honours.onote-wal         4,152,992 B   ← 4 MB of uncheckpointed pages
```

That is ADR-0006 §2's *"WAL makes it worse … can produce a torn database. This
is a live risk today, not a future one"* — happening, in production. The cause
is `Repository.moveNotebookTo` (`repository.dart:455-519`), which moves the
container **and** the log dir into the sync folder for a notebook this device
created — while the joined-notebook branch **twelve lines above it**
(`repository.dart:437`) already refuses to do exactly that, with a comment
explaining why. *Half the fix is present and correct; the other half was never
wired up.*

**And the `-wal` is not a footnote.** Measured by reading each container with
and without replaying its WAL: My Notebook's 4,128,272-byte `-wal` holds **2
whole pages, newer revisions of 6 more, 1 of 5 blobs and 5 of 22
`page_versions`**. The Drive notebook's 247 KB `-wal` holds newer revisions of
4 pages. Any migration that moves a container without checkpointing it first
throws those away, and the result passes `PRAGMA integrity_check`.

## 2.2 The op log is now a proven rebuild authority

ADR-0007 recorded the blocker as *"rebuild-from-log … has never been the
user-facing join path"*. That is now half-false — `Repository.adoptLogDirectory`
+ `AppState.syncPull` ship as the git-join path — and the remaining half was
settled empirically rather than argued. Three independent passes replayed each
notebook's log with the app's own `Materializer` and compared canonical page
JSON against the container:

| Notebook | Pages identical | Blobs present | Skipped ops | Rebuild cost |
|---|---|---|---|---|
| Drive notebook | **329 / 329** | 491 / 491 | 0 | `readAll` 128 ms + replay 11 ms |
| Honours-2 (legacy 64.56 MB log) | **328 / 328** | 378 / 378 | 0 | `readAll` 1,638 ms + replay 14 ms |
| Honours-4 | **329 / 329** | see below | 0 | 102–120 ms |
| My Notebook | **14 / 14** | 5 / 5 | 0 | 72 ms |

Nodes: 360 in the container, 354 identical, **6 differing only in the spelling
of `kind`** (§3.3).

**But that verification is blind to the loss the migration can cause**, and
this is the single most important sentence in this document. `page_mirror` JSON
references an image only by hash, so a page whose blob *bytes* have been
destroyed is byte-identical to the same page with its bytes intact. A spike
stopped the blob backfill at 100 of 488 blobs, ran the migration to completion,
and it printed `MIGRATION COMPLETE`, left a `cache.onote` whose
`integrity_check` says `ok`, and the page-level check reported
**`same=329 differing=0`** — while **278 blob hashes had no bytes anywhere on
disk and 193 image blocks across 40 pages were permanently broken.**
`sync_shadow_test.dart` encodes exactly that page-level property and would have
gone green through it.

Every "rebuild == container" assertion in this plan therefore compares **blob
bytes**, not blob presence, and not just pages.

## 2.3 Where the log is *not* yet an authority

- **Blob coverage on local-only notebooks.** `SyncRecorder.blob`
  (`sync_recorder.dart:322`) gates bytes on
  `if (materialiseBlobs || mime == inkMimeType)`, and `materialiseBlobs` is
  `notebookIsShared(nb)` (`app_state.dart:1042`, `:1102`, `:1148`). Measured on
  Honours-4: **378 of the 488 blob hashes its log names have no bytes in
  `blobs/`** — 26.3 MB of images. A rebuild today produces a structurally
  perfect notebook (`same=329 differing=0`) in which **271 of 271 image blocks
  are broken across 44 pages**. This is Step 5.
- **This device's own log is never replayed.** `SyncRecorder.pendingForeignOps`
  opens with `if (dev == device.id) continue` (`sync_recorder.dart:412`). A
  fresh join works because a fresh device has no own log; a device that loses
  its cache and keeps its `deviceId` in `workspace.json` gets back **only what
  other devices wrote**. `rebuildContainerFromLog` still does not exist. This
  is Step 8.
- **`page_versions` has no op kind — and now never will.** `database.dart`
  states the position outright: *"Version history is container-local. There is
  no OpKind for it."* Measured rows: My Notebook 22, Honours-2 6, Drive 6, most
  notebooks 0 — 0.03–0.23 MB. This was posed as Step 8's product decision
  (§7.1) with two bad options — sync 30 full page snapshots per page into an
  append-only log, or promise the student that history never leaves this
  computer. **Decision 1 took neither.** The table is dropped and replaced by
  two things the log can already answer without a single new byte in it: who
  last changed each visible block, and the last ten notable deletions. That is
  **Step 8a**, and §7.1 records how the question was closed.

## 2.4 One number that is bigger than the whole cluster, and needs no format change

**324.4 MB of the owner's 409.45 MB workspace (79%) is containers whose
notebook id appears in neither `notebooks` nor `trashed` in `workspace.json`.**
Honours-2 (97.54 MB + 94.02 MB), `Honoursonepkg.onote` (92.63 MB, no
`.onotebook` at all), `Honours-3.onote` (31.67 MB), `test.onote`, and a stray
`-wal`/`-shm` pair whose `.onote` is gone.

**Correction to one investigation pass:** it reported these as invisible to the
app. They are not. `AppState.findOrphanFiles` (`app_state.dart:2626`) scans the
workspace root and every detected cloud folder, matches `.onote`, `.onotebook`
and stray `-wal`/`-shm`, and marks workspace-root ones `safeToDelete: true`
(`:2668`). `deleteOrphans` removes them. The gap is **discoverability**: it
lives behind a *"Find leftovers…"* button (`sync_dialog.dart:730`) inside the
**sync** dialog, under a section subtitled *"Sizes, paths and leftovers"*. A
student who has never set up sync will never look there.

So this is not a missing feature, it is a missing door — and it is worth more
disk than #39 and #54 combined. Open it as its own small task: surface the
existing leftovers scan from a plain **"Free up space"** entry point, in plain
words, with sizes. Do it *before* Step 7, because §3.7 has to teach the same
scan to stay silent while a migration is in progress.

# Part 3 — The work, in order

Eleven steps — nine as first written, plus the two the decisions of Part 0.5
added. Each is independently shippable and independently valuable. **No step
leaves the format in a state where an interrupted upgrade loses data**, and the
three that touch bytes (5, 7, 8) each ship with their inverse, tested in the
same PR.

Steps 1–4 change no file format at all and are worth shipping even if the rest
slips forever.

```
 1  Save failures become visible          ─┐   ✅ DONE 2026-08-15
 2  Log reader hardening                   │   ✅ DONE 2026-08-15
 3  Vocabulary + version gates             │  no format change · any order
 4  SQLite leaves the cloud folder        ─┘
 5  Blob bytes always materialised, and proved      ← +26 MB temporarily
 6  Container stops writing blobs; reads pass through
 7  Reclaim: empty the blobs table                   ← the 30.6 MB, first irreversible step
 8  Own-log rebuild, then the rename to cache.onote  ← format v2
 8a Simplified version history                       ← decision 1 · drops page_versions
 8b Register the notebook folder                     ← decision 2 · retires the .onote association
 ─────────────────────────────────────────────────────
 9  (split out entirely) Video engine on demand      ← 48.38 MB of install, touches no user file
```

8a and 8b are lettered rather than numbered because neither is a *format*
change and neither has to wait for the rename: 8a can ship the moment the
rebuild in Step 8 item 1 exists, and 8b only has to land in the **same
release** as the rename, so that the day `cache.onote` appears is the day
Explorer stops offering to open one.

## Step 1 — A save that could not be recorded says so ✅ DONE

**What changes.** `AppState._recorderFor` and `_warmAndInstall` catch every
exception, `debugPrint`, and return `null`. `_startBlobBackfill`
(`app_state.dart:1261`) attaches `.catchError` at `:1268` that prints and
returns 0. Those are *correct today* — the container is authoritative and
shadow mode must never break saving — and they become **silent permanent loss**
the moment the log is the format. Route both into the existing `saveError`
path, with a plain-words message and the technical detail behind Advanced.

Also in this step, because it must bake before anything needs it: **start
*reading* `workspace.json`'s `format` field**, and make a build that meets a
format higher than its own load the registry **read-only and refuse to rewrite
it**.

> **Corrected 2026-08-15 (correction 1).** This step originally said "give
> `workspace.json` a `format` integer", on the belief that the field was
> absent. It was not. `_saveWorkspace` has always written `{"major": 1,
> "minor": 0}`, and spec §7 documents that exact shape
> (`docs/specs/10-file-format-spec.md:192`). Nothing ever read it. So the
> shipped guard reads `format.major`, **also accepts a bare integer** so a
> future build that flattens the field is still guarded by this one, and
> treats **an unrecognised shape as compatible on purpose**: a shape we do not
> recognise was written by a build that predates the guard, which is by
> definition not newer than us, and guessing "newer" would lock every existing
> user out of their own notebook list — the exact harm the guard exists to
> prevent. When the format really is higher, the entries still load (they are
> real notebooks and the student should be able to open them) and the file is
> simply never written back.

**What it buys.** Converts three reachable silent failures into a message. All
three are reachable *today*: an `.oplog` truncated inside a multi-byte
character makes `readAll()` throw (Step 2 — 2 of 1,487 truncation points on the
real 1.5 MB log), a permission error, a full disk, or a cloud client holding
the file. Today the container catches the fall. After Step 7 it does not.

The workspace `format` field is the guard for a hazard nobody would otherwise
see coming: `Repository._loadWorkspace` skips any entry whose file does not
exist (`if (File(file).existsSync())`), and `_saveWorkspace` then rewrites
`workspace.json` from the in-memory list. **A student who upgrades the laptop
in October and the desktop at Christmas opens the old build on a migrated
workspace, sees an empty sidebar, creates one notebook — and permanently
prunes all the others.** The guard has to be in the field *before* Step 8
moves any container, which is why it ships first.

**Migration.** None. An older build ignores an unknown JSON key.

**Proof — as shipped, and corrected from what this step first proposed.** The
original suggestion was "make the ops directory unwritable, and separately
plant an undecodable `*.oplog`". **Both halves were wrong**, and correction 2
records why: making a folder unwritable is flaky on Windows, and an undecodable
`.oplog` stops throwing the moment Step 2 lands — by design, since tolerating
exactly that is Step 2's whole business. A proof that Step 2 turns green is not
a proof.

What shipped instead plants **a file where the `.onotebook` directory belongs**
(`app/test/recorder_warm_test.dart:191`), which makes
`opsDir.createSync(recursive: true)` fail deterministically on every platform
and stays failing forever. Three tests: the background warm reports it; the
**synchronous** fallback open reports it too (a separate `catch`, and the path
every mutation falls back to when no warm has landed); and the sentence that
reaches the user contains no exception class, no `errno`, no path and no file
extension, while still saying what happened and what to do. The page itself
still saves — the container is still authoritative, and a log that will not
open must never fail a student's save. Truncation behaviour is proved
separately in F1–F3. Second test, unchanged: a `workspace.json` with a higher
`format` loads read-only and a subsequent notebook creation does **not**
rewrite the file.

**Data safety.** Crash: nothing on disk changes. Disk full: this is the step
that makes disk-full *visible*. Old build meets new file: ignores the key.
Shared-folder skew: none.

**Rollback.** Revert the commit. The `format` key is inert to older builds.

## Step 2 — Two pre-existing log-reader bugs ✅ DONE

**What changes.** Two one-line-class fixes in `op_log.dart`:

1. `readDevice` uses `File.readAsStringSync` (`op_log.dart:181`), which decodes
   UTF-8 **strictly** and throws `FileSystemException` on a partial sequence.
   The paced `readDeviceFrom` on the identical bytes uses
   `utf8.decode(…, allowMalformed: true)` (`:269`) and is fine. `readAll`,
   `highestLamport` and `lastSeq` all route through the strict one. Make it
   match.
2. `append` writes `ops.join('\n') + '\n'` in one `writeStringSync`
   (`op_log.dart:344`). A tear one byte from the end leaves a complete JSON
   line with no terminator, and the *next* append concatenates onto it, gluing
   two records into one unparseable line. Measured: append 3 ops, drop one
   byte, append 2 more → `readDevice` returns seqs **[1, 2, 5]**. Two ops lost
   for one lost byte, where the format's own doc comment promises one. Fix:
   check the last byte before appending and prepend a newline if it is missing.

**What it buys.** Measured on the real 1,523,044-byte log: of 1,487 truncation
points at every 1 KiB boundary, **2 made `readAll()` throw**. In a minimal
317-byte reproduction using the maths symbols the owner's notes are full of
(ℝ, ∃, ∈), **6 of 316 truncation points threw**. Today that stops sync
silently. After Step 7 it is the notebook refusing to open.

**Migration.** None. **Proof.** Table-driven: truncate a generated log at every
1 KiB boundary and at every byte of a small multi-byte-dense log; assert
`readAll` never throws and returns every complete op before the cut. Separately:
append, truncate one byte, append, assert no op is lost.

**Data safety.** All four cases unchanged — this step only makes an existing
reader more tolerant. **Rollback.** Revert.

## Step 3 — Say `section_group`, and gate the envelope

**What changes.** Two vocabulary/compatibility holes, both cosmetic today and
both data-losing after Step 8.

1. **Node kind.** `SyncRecorder.node` writes `n.kind.name`, producing
   `sectionGroup`; `database.dart`'s DDL is
   `CHECK (kind IN ('section_group','section','page'))` and the published CC0
   spec §3 documents only the snake_case set. The fold maps back with
   `NodeKind.values.firstWhere((k) => k.name == n.kind, orElse: () =>
   NodeKind.page)`. Measured on **all four notebooks: 6 nodes each**, and every
   rebuild a spike ran needed exactly 6 fixups or the `INSERT` failed outright.
   Fix: write the **spec** spelling; accept both on read, forever; and make an
   *unrecognised* kind land in `Materializer.skipped` and be preserved verbatim
   rather than being coerced to `page` — a page has a `page_mirror` foreign
   key, a `level`, and completely different semantics from a section group.
2. **Envelope version and encryption.** `Op.decode` reads `j['v']` into
   `Op.version` and **never compares it to `opFormatVersion`**;
   `Materializer.apply` switches on kind alone. Measured: a hand-written
   `{"v":2,…,"op":"block.set"}` carrying the structured `{nodes:[…]}` model
   ADR-0006 §4 plans **was applied with `skipped=0`**; an `{"enc":"aes-gcm"}`
   op decoded, yielded `map={}`, and was **silently dropped with `skipped=0`**.
   `SyncRecorder.verifyPage`'s only escape hatch ("inconclusive rather than
   incomplete") keys off `skipped.isNotEmpty`, so a real divergence today is
   reported as *data loss*. Fix: `v > opFormatVersion` or `enc != 'none'` →
   `skipped`, and the notebook opens **read-only** with a plain message. The
   container already has this gate (`database.dart:130` throws on
   `user_version > 1`); the log has none.

**What it buys.** Removes the one place where Openote's open artifact uses a
vocabulary that appears nowhere in Openote's published spec — while it is still
cosmetic. It also makes Step 8's forward compatibility mechanical rather than
hopeful.

**Migration.** Logs will contain both spellings forever; the reader accepts
both forever. No rewrite of any existing log — **this plan never rewrites a
log line, anywhere.**

**Proof.** Feed a `node.upsert` with `kind: 'section_group'` and assert it
materialises as a section group; feed `kind: 'wormhole'` and assert it lands in
`skipped` and is *not* a page. Assert an op with `v: 2` and one with
`enc: 'aes-gcm'` both land in `skipped` and put the notebook read-only.

**Data safety.** Old build meets new file: an old build reading a
`section_group` kind hits `orElse → page` — which is why the reader fix must
ship at least one release before the writer flips. **Ship read-accepts-both in
release *n*, write-spec-spelling in release *n+1*.** That is the one ordering
constraint inside this step.

**Rollback.** Revert the writer half; the reader half stays forever.

## Step 4 — Get SQLite out of the cloud folder

**What changes.** `Repository.moveNotebookTo`'s created-notebook branch
(`repository.dart:455-519`) stops moving the container into the target folder.
It moves the `.onotebook` — exactly what the joined branch at `:437` already
does — and leaves the container in the local workspace. Plus:

- A one-click **"Move the notes file out of Drive"** action in the sync dialog
  for notebooks already in this state, in those words, with no mention of WAL,
  SQLite or tearing. Technical detail behind Advanced.
- Replace `moveNotebookTo`'s `File(destFile).lengthSync() != src.lengthSync()`
  check with a **SHA-256 comparison of both files**. The primitive already
  exists (blob hashing). A copy torn in the middle by a crash or a cloud client
  has the same length and passes today — and that function's own comment
  records a previous version of this check passing *while destroying the
  notebook*.
- Amend **ADR-0006 §3** and **spec §11**'s identical diagram to put
  `cache.onote` outside the synced directory (§1.2).

**What it buys.** Removes SQLite from the replicated set. Measured on the live
Drive folder: **31,954,368 B of container + `-wal` + `-shm` stops being
replicated** (63.19 MB → 31.24 MB in Drive for that notebook, −50.5%), and
ADR-0006 §2's "live risk today" goes to zero. No format change, no byte of
anyone's notes touched. **This is the step that justifies the cluster.**

**Migration.** For each notebook whose container sits in a detected cloud
folder, offer the move. Checkpoint first (`checkpointAndClose`), copy, verify
by hash, then delete the original and its sidecars. Never delete before the
hash matches.

**Proof.** A test that performs every notebook operation — create, save,
import, join, move-to-folder, mirror, git sync — and then asserts **no path
matching `*.onote*` exists anywhere under `NotebookRef.logDirPath` or under any
configured sync location**. It must fail today for the move-to-folder case;
that is the point. Second: pre-create a `-wal` with uncommitted pages, move,
assert the destination opens with identical page count *and identical page
content*.

**Data safety.** Crash mid-move: the original is deleted only after a hash
match, so a crash leaves either the original or both. Disk full: the copy
fails, the original is untouched. Old build meets new file: the container is
still a normal `.onote` at a normal path — an old build reads it fine, and the
`format` field from Step 1 covers the registry. Shared-folder skew: this step
*removes* skew; the folder now contains only append-only files.

**Rollback.** The same mover, in reverse. Nothing is deleted that cannot be
put back.

## Step 5 — Blob bytes are always materialised, and coverage is proved

**What changes.** `materialiseBlobs` becomes unconditionally true
(`sync_recorder.dart:322`; the `notebookIsShared` gate at `app_state.dart:1042`
and `:1102` goes away), and `backfillBlobs` runs on every existing notebook.
Note the trap: `backfillBlobs` **returns 0 without reading anything** when the
flag is false (`sync_recorder.dart:354`), which reads exactly like "nothing to
do" rather than "I was not allowed to look" — so **the flag must flip before
the backfill runs**, and the backfill's completion must be *asserted*, not
inferred.

Add the invariant that every later step is gated on:

```
for every hash in blob_refs:
    a file blobs/<hash> exists
    AND its bytes re-hash to <hash>
    AND SyncRecorder.missingBlobs() is empty
```

**What it buys.** Closes the 378-of-488 hole on Honours-4. Only after this is
"the log is the notebook" true for local-only notebooks as well as shared ones.
It **costs** disk in the short term: Honours-4 goes 36.69 MB → ~63 MB until
Step 7 removes the container copy.

**Migration.** Backfill runs in the background, resumable, idempotent
(`writeBlob` is temp+rename and survived every hard kill a spike threw at it,
with no `.tmp` litter). Its failures are visible from Step 1.

**Proof.** Local-only fixture with images: run the backfill with `blobs/` made
read-only, assert it reports failure (not 0) and that the container is
untouched. Then run it normally and assert the invariant above holds byte for
byte.

**Data safety.** Crash: partial `blobs/` is always a strict subset of the
container, which is still authoritative. Disk full: the invariant fails, and
nothing downstream proceeds. Old build meets new file: extra files in `blobs/`
are exactly what a shared notebook already looks like. Shared-folder skew: a
content-addressed file written twice is the same file.

**Rollback.** Delete the added files, or leave them — they are never wrong,
only redundant.

## Step 6 — The container stops writing blobs; reads pass through

**What changes.** New blob bytes go to `blobs/` only. `AppState.blob(hash)`
(`app_state.dart:206`, 16 call sites, synchronous) becomes **file-first, then
the table** as a fallback. The `blobs` table stops being written but is not
touched. The SQL surface is small and contained: 14 call sites across 5 files
(`notebook_writer` 13, `app_state` 3, `repository` 4, `database` 2,
`ink_storage` 1).

**What it buys.** Nothing on disk yet — deliberately. It puts the read path
that Step 7 depends on into the field for a full release, on real notebooks,
while the old bytes are still sitting there as a safety net. **Renaming and
de-duplicating in one release is two irreversible changes sharing one crash
window;** this step is the split.

**Migration.** None — existing rows stay.

**Proof.** Assert a brand-new notebook has **zero** `blobs` rows and that every
`blob_refs` hash resolves to a file whose SHA-256 equals its name. Assert every
image and ink block still renders on a fixture that has bytes only in the
table, only in `blobs/`, and in both.

**Data safety.** Every case is a no-op: the bytes exist in two places
throughout. **Rollback.** Revert; new blobs written during the bake are in
`blobs/`, which the fallback read path and Step 5's backfill both already
handle.

## Step 7 — Reclaim: empty the `blobs` table

**The first irreversible step.** Everything above can be reverted by reverting a
commit. This one deletes bytes.

**What changes.** `DELETE FROM blobs` + `VACUUM`, gated, crash-idempotent, with
its inverse shipped alongside.

Five things must be true, and the migration must **refuse** rather than
proceed when any is false:

1. **Step 5's invariant holds for this notebook**, byte for byte. A spike
   destroyed 193 image blocks across 40 pages by skipping this, and the
   migration printed `MIGRATION COMPLETE`.
2. **The container has been opened and checkpointed** — never renamed or
   emptied while a `-wal` holds pages. On My Notebook that `-wal` is 2 whole
   pages and newer revisions of 6 more, and the damaged result passes
   `integrity_check`.
3. **Free space ≥ 2.0× the container.** Measured: `VACUUM` on the 97,542,144 B
   container peaked at **192,787,184 B** across the `.onote` + a 95,048,432 B
   `-wal` + `-shm` (1.98×), took 1.33 s, and recovered 3 MB. A rebuild peaked at
   a 14.86 MB `-wal` for a 31 MB container. And local-only notebooks need the
   Step 5 double-store first: Honours-4's transient peak is ~63 MB from 36.69 MB
   (**1.72×**). Refuse *before* touching anything, with a plain message.
4. **`PRAGMA foreign_keys` is handled explicitly.** `database.dart:272`
   declares `hash TEXT NOT NULL REFERENCES blobs(hash)` and spec §2 requires
   foreign keys ON, so `DELETE FROM blobs` errors. **The obvious repair — add
   `ON DELETE CASCADE` — silently empties `blob_refs`, which is ADR-0007's GC
   root set, and the next housekeeping run then classifies every blob file as
   unreferenced and deletes it.** A spike had to pass
   `PRAGMA foreign_keys=OFF` to take its own measurement, which is how easy
   this is to walk into. The correct fix is to drop the constraint in the v2
   schema, deliberately, and to assert `blob_refs`' row count is **byte-
   identical** before and after.
5. **`reclaimFreeSpace` stops reporting failure as success.** Its bare `catch`
   returns 0, so an out-of-disk `VACUUM` is indistinguishable from "nothing to
   reclaim".

**What it buys.** Drive notebook 63,193,548 → 32,578,572 B (**48.4%**);
Honours-4 36,689,419 → 32,630,831 B (**11.1%**). Container 31,707,136 →
1,470,464 B by direct measurement of `DELETE FROM blobs; VACUUM`.

**Its inverse, shipped in the same PR.** `refillContainerBlobs()` — re-ingest
every hash in `blob_refs` from `blobs/` back into the table. It is only
*possible* because Step 5 proved coverage; it must be **written and tested
before Step 7 is allowed to ship**, and it is the rollback story for anyone
who hits a problem in the field.

**Data safety.** Crash: the delete is one transaction and rolls back; the
`VACUUM` either completes or leaves the original. A real `SQLITE_FULL` (code
13) was injected during a rebuild and the `BEGIN`/`COMMIT` held — **but it left
a 4,096-byte container beside a 14,864,992-byte `-wal`, and that pair passes
`notebookFileProblem` via the `appId==0`-plus-`-wal` concession**, after which a
normal open settles it into a valid, empty 73,728-byte notebook. So the
migration must write a marker file naming the step *before* it starts, and
refuse to treat a container as fresh while that marker exists. Disk full: the
§3 precheck. Old build meets new file: an emptied `blobs` table with a populated
`blobs/` is exactly what an old build sees on a joined notebook today — it
reads through `blob_refs` and finds bytes; the read-through path from Step 6 is
what makes this safe, which is why Step 6 must bake first. Shared-folder skew:
`blobs/` is content-addressed and append-only; nothing here writes to it.

**Interaction with the leftovers scan (§2.4).** `findOrphanFiles` marks any
unclaimed workspace `.onote` `safeToDelete: true`, and classes a `-wal`/`-shm`
as an orphan precisely when its `.onote` is absent — **which is the state a
migration creates for its duration**. Take a lock file, and make the scan
return nothing at all while it is held. Test that at every migration step.

**Rollback.** `refillContainerBlobs()`, plus revert.

## Step 8 — Own-log rebuild, then the rename

**What changes.** Five things, in this order, in one release:

1. **`rebuildContainerFromLog(notebookId)` for real.** `pendingForeignOps`
   structurally cannot provide it — `sync_recorder.dart:412` is
   `if (dev == device.id) continue`, and a single-device notebook's entire
   history lives in exactly the file that skips. Measured cost: 102–120 ms for
   329 pages / 2,780 ops.
2. **`openOnote` must refuse to fabricate.** On a path that does not exist it
   returns a valid `Database` with 0 nodes and 0 pages, leaves a 73,728-byte
   file, and `notebookFileProblem` then reports *"looks like a notebook"*.
   `Repository._db` calls `openOnote(nb.file, …)` with **no existence check**
   (`repository.dart:366-369`), so this is reachable today whenever a
   registered container's path goes missing — an unmounted drive, a cloud
   client that evicted the file. Add `openExistingOnote`, and use it
   everywhere a notebook is *expected* to exist.
3. **`page_versions` does not survive the rebuild — it is dropped.**
   *Superseded 2026-08-15 by decision 1.* This step used to recommend
   preserving the table across the rebuild by copying it out and back, on the
   grounds that syncing 30 full page snapshots per page is the one thing that
   would genuinely make an append-only log grow without bound. That reasoning
   still stands and is **why no `page.version` op kind is added**. What changed
   is the other end: the owner asked for a *smaller and different* feature, so
   the table is not preserved either. The v2 schema has no `page_versions`, the
   rows are deleted with the migration, and what replaces them is **Step 8a**,
   which stores no history at all because the log already is the history.
4. **The rename must refuse a `cache.onote` handed to it as a notebook.** After
   this step there is a file on disk that looks exactly like a notebook to
   every sniff test the app has — `notebookFileProblem` checks the SQLite magic
   and `application_id`, both of which a cache satisfies. `user_version = 2`
   makes an *old* build refuse it; a **new** build must refuse it too, on the
   double-click path and on argv, because adopting a cache clones a copy that
   is no longer authoritative and whose `blobs` table Step 7 has already
   emptied. See Step 8b, which owns the sentence the student reads.
5. **Only then, the rename**, with the version gate below.

**The migration is a named step sequence with a marker file**, because the
scariest failure a spike found is not a crash — it is the **recovery**:

> A hard `TerminateProcess` immediately after the rename, followed by the
> obvious *"just run the migration again"*, **destroyed a 329-page notebook**.
> Step 1 of the re-run called `openOnote` on the now-missing old path, which
> fabricated an empty database; step 5 renamed it over the real `cache.onote`
> — which `File.renameSync` on Windows does **silently, with no exception**
> (verified directly: destination content `REAL NOTEBOOK CONTENT` became `new`,
> no error, source gone). Result: 73,728 bytes, 0 pages, 0 blobs,
> `integrity_check` `ok`. The same disaster reproduced from a kill one step
> later, where the crashed state was itself perfectly fine.

So: write `migrate.json` into the log directory before touching anything,
naming the step and both paths; **never rename onto an existing destination**;
and make every step resumable from the marker.

**What it buys.** The container becomes what ADR-0006 §3 always said it was —
a local, rebuildable cache — and the app can finally offer *"rebuild this
notebook from its history"* as a real repair rather than a hope.

### The version gate, stated

| Surface | Value now | After Step 8 | Why |
|---|---|---|---|
| Op envelope `v` | 1 | **1, unchanged** | No new op kind is added anywhere in this cluster. Spec §12: new kinds are additive and do not bump `v`. |
| Op `enc` | `none` | `none` | Gated in Step 3 so a future value stops an old build instead of being silently dropped. |
| Container `user_version` | 1 | **2** | The file's name and role change. An old build meeting a `cache.onote` must refuse, and `database.dart:130` already throws on `user_version > 1`. |
| `manifest.json` `format` | 1 | **2** | So a joining device knows which layout it is looking at. |
| `workspace.json` `format` | **1** — written since the file existed as `{"major":1,"minor":0}`, documented in spec §7, and never read until Step 1 | **2** | The only mechanical guard against the old build silently pruning the registry. *Corrected: this row used to say "absent". See correction 1.* |
| Container `page_versions` table | present, up to 30 snapshots per page | **gone** | Decision 1. Dropped in the v2 schema, replaced by Step 8a's derived attribution index and ten-deep deletion list. |

**On the format freeze.** Spec §12 promises *"From v0.2.0 onward, format v1 is
frozen."* v0.11 Part 0 lifted that on the owner's words *"No real users yet"*.
That was worth checking rather than assuming, so it was measured: the GitHub
API reports **10 release objects, 7 with published assets, and no single asset
with more than 2 downloads** (two summarisation passes over the same response
totalled 14 and 22, so treat the exact sum as low tens; the per-asset ceiling of
2 is the number that matters). Some of those are certainly the owner's own.

**Conclusion: the exposed population is at most a couple of dozen downloads,
none of whom can be contacted — so do the documented one-way v1 → v2 migration
properly (spec §12's own mechanism), and do *not* build a downgrade path.** The
in-app updater means a stranger's app will offer the newer build; the
`workspace.json` guard from Step 1 means the older build fails *safe* rather
than failing *permanent* in the meantime.

**Also required in this step, and easy to miss:** `MediaGc`'s safety argument
is written in prose that stops being true. `media_gc.dart:310-317` skips this
device's own `.oplog` and justifies it: *"The container is authoritative and the
log is written alongside it … our own log can lag our container but never lead
it."* Demotion deletes both halves of that premise. The conclusion probably
survives — a replay-to-final-state rebuild does not resurrect a removed block —
but it survives for a *different reason*, and a wrong delete here costs somebody's
lecture recording. Rewrite the comment and add the test in row C7 of the matrix.

**And `MediaGc`'s list of sources loses an entry and gains a smaller one.**
`media_gc.dart:94-116` enumerates, as prose, *"every place a stored media name
can survive"*, and says outright that the scan's correctness is entirely a
question of whether that list is complete. Source 3 is *"`page_versions.snapshot`
— up to thirty autosaves per page"*. Decision 1 deletes it and puts Step 8a's
**ten-deep** deletion list in its place. That is strictly less pinning, and
§ Step 8a quantifies what it frees. The list is normative prose that a reader is
told to trust, so it must be edited in the same commit that drops the table —
not left describing a table that no longer exists.

**Data safety.** Crash: the marker file plus refuse-to-fabricate plus
never-rename-onto-a-destination. Disk full: the §3 precheck, run before the
marker is written. Old build meets new file: `user_version = 2` → refuses;
`workspace.json format = 2` → read-only registry. Shared-folder skew: the
rename happens entirely outside the synced directory (Step 4 put the container
there), so no synced file changes.

**Rollback.** A scripted, tested **`undemote`**: rename back, `user_version`
back to 1, `refillContainerBlobs()`, `workspace.json format` back to 1. Written
and tested in the same PR as the rename.

### What decision 4 adds to this step

Step 8 is **no longer gated on a human macOS pass** (§7.4). The rationale is
sound: commit `3230264` records that the macOS Xcode project never built the
Rust core and the loader fell back in silence, so macOS has *already* been
shipping unverified, and this migration does not make it meaningfully riskier
than the release before it.

But the consequence has to be written down rather than filed under "accepted
risk", because it is specific: **a one-way v1 → v2 migration will run, for the
first time, on a platform no human has ever driven.** Three things therefore
move from "nice" to "required", and all three are cheap:

1. **The migration is opt-in, on every platform.** Not automatic on open. A
   one-click *"Update how this notebook is stored"* with a plain sentence, and
   an app that runs indefinitely without it. This is what converts "an unproven
   one-way migration ran on your notebook" into "you chose the moment, and if
   we hear of a problem we can tell you to wait." It costs one dialog and it is
   the single largest risk reduction available.
2. **`undemote` must run green on macOS in CI**, not only on Windows, and it is
   a **release blocker** for the release that ships this step. Part 6's rule
   already says an irreversible step does not ship until its inverse is
   written, tested, and reachable without a terminal. Decision 4 is what makes
   the macOS half of "tested" load-bearing rather than decorative.
3. **The macOS rows of the matrix must actually run on a macOS runner** — see
   §5.5. Today a great many rows read `W/L/M` on the strength of being
   platform-independent Dart. Marking a row `M` and never running it there is
   exactly the kind of inference this project has been punished for.

## Step 8a — Who changed this, and what was deleted (decision 1)

**Replaces `page_versions`.** The owner asked for something smaller and
different from what the table does: *"keeping track of who made what edits
(that are currently visible and maybe recent deletions, like the last 10
noteable deletions)"*. Two features, and neither of them is a history store.

### Why this is nearly free: the log already carries it

`Op` (`app/lib/sync/op.dart`) already stamps every record with `dev` — *"the
device that wrote it. Exactly one device ever appends to a given log"* — and
`ts`, the wall clock, whose own doc comment says it is *"**Informative only** —
shown to users"*. `Op.compare` gives a deterministic total order across every
device: Lamport, then device id, then seq. And the ops name their targets:
`block.set` carries `{pageId, block}` with the block's own id inside,
`ink.strokes` carries `{pageId, blockId, …}`, `block.remove` carries
`{pageId, blockId}`, `node.delete`/`node.purge` carry the node id.

So **"who last changed this block, and when" is the last op in total order that
names that block** — a byproduct of a fold the app already performs, not a
thing to store. Concretely:

- **No new op kind.** The version gate's *"Op envelope `v`: 1, unchanged"* row
  is unaffected, and spec §12's promise that new kinds are additive is not
  called on.
- **No new bytes in any log.** Not one. This matters more than it sounds:
  every alternative version-history design in this document failed on log
  growth, and this one cannot, because it writes nothing.
- **Nothing new syncs.** A device that has never heard of this feature produces
  logs that answer its questions perfectly.

### The one thing that is genuinely new: turning a device id into a name

Attribution is worthless if it says *"last changed by
`019fdff4-8c31-7a2e-…`"*. The machinery is half-built already:
`OpLogStore.announceDevice(device, {String? label})` writes into
`manifest.json`'s `devices` map, whose own comment says it exists *"for showing
the user which devices touched a notebook"* — and both call sites
(`sync_recorder.dart:111`, `:184`) pass **no label**. So the map exists and is
empty of names.

- Pass a label. Default it to something a student recognises without being
  asked a question at first run, and let them change it in **one field** in the
  sync dialog: *"What should other people call this computer?"*
- Never show a raw device id in the interface. When the manifest has no label
  for a device, the line reads *"changed by another computer"*, which is true
  and is not jargon.
- **Say plainly that the name is shared.** In a group notebook `manifest.json`
  is a synced file, so the label is visible to everyone in the notebook. One
  sentence under the field, and a sensible default that is not the Windows
  hostname — `DESKTOP-4G7H2K` is jargon by any reasonable reading of the bar.

### Where it is kept: a derived index, never a source of truth

```sql
CREATE TABLE IF NOT EXISTS block_authors (
  page_id  TEXT NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  block_id TEXT NOT NULL,
  device   TEXT NOT NULL,
  lamport  INTEGER NOT NULL,
  changed_at INTEGER NOT NULL,
  PRIMARY KEY (page_id, block_id));
```

**One row per block that currently exists** — bounded by how big the notebook
is, not by how long it has been edited. That is the whole difference from
`page_versions`, which is bounded by editing history and therefore by nothing.

- **Maintained on write, for free.** The save already knows which blocks
  changed; it is what `SyncRecorder.page` diffs to decide which `block.set` ops
  to emit (`sync_recorder.dart:564-635`). One upsert per op it was already
  writing.
- **Rebuilt from the log, for free.** Step 8's `rebuildContainerFromLog`
  already visits every op in total order. Populating this table is an
  assignment inside that loop.
- **Safe to be empty and safe to be wrong-by-omission.** A missing row renders
  as *"not recorded"*, never as a wrong name. It carries the `ON DELETE
  CASCADE` that `page_versions` never declared, so the entire class of bug
  commit `1be2d28` fixed cannot recur here — the fix stays in history and the
  *need* for it is designed out.
- **Never synced, never authoritative.** It lives in the cache, which decision
  3 says no third party should read. Deleting it costs a rebuild, nothing more.

### "Notable", defined concretely — and why

A deletion goes in the list when it is one of these. Everything else is an
edit, and an edit's remedy is undo.

| Notable | Rule | Why this and not everything |
|---|---|---|
| A **page** deleted or purged | `node.delete` / `node.purge` on a page node | This is the thing students actually lose. |
| A **section or section group** deleted or purged | `node.delete` / `node.purge` on a non-page node — **one entry for the whole subtree**, not one per child page | Otherwise deleting one section fills all ten slots and pushes out everything else. |
| A block that **holds or names a blob** | image, file, video, PDF, embed, ink, or code-cell block, removed by `block.remove` — regardless of size | It is the thing that cannot be retyped. A paragraph can be rewritten from memory; a lecture recording cannot. |
| A **large text-shaped block** | `block.remove` where the block's last known content is **≥ 280 characters** of text | A paragraph-sized bar. Below it, deletion is editing. |
| **Not notable:** an eraser gesture | `ink.strokes` with a large `del` list | It is an edit, and one cleanup session would fill the list of ten by itself — the exact "every keystroke" failure the owner ruled out. Undo is its remedy, and undo already holds 100 page snapshots. |

**The 280 is a knob, and it must be set from measurement before it is fixed.**
The honest position: no `block.remove` count has ever been taken on the real
logs. The one genuinely edit-driven log is My Notebook's 268 KB, and what *is*
measured about it — 2.55× write amplification, 237.6 KB written for 93.1 KB of
final content — says ordinary editing produces many `block.set`s per block and
says nothing at all about removals. Matrix row **H3** adds `block.remove` counts
and a blocks-per-page distribution to the existing shape tool, **counts only,
never content**, and the number is chosen from that. Anything else is a guess
wearing a decimal point.

### How a deletion is undone: a query, not a stored copy

Nothing needs to be copied anywhere, because **§4.1 guarantees no log line is
ever rewritten**. That promise, made for a completely different reason, is what
makes this feature possible:

- A removed block's last content is the last `block.set` naming that block id
  **before** the `block.remove`. Still in the log. Always.
- A purged page's content is every `block.set` for its pages, plus its
  `node.upsert`. Still in the log. Always — `node.purge` removes the row from
  the container, not the history from the log.
- **Restoring is an ordinary edit.** Re-apply the recovered content through the
  normal save funnel, exactly as `AppState.restoreVersion` already does
  (`app_state.dart` — `pushUndo()`, set blocks, `markDirty()`). So a restore
  syncs to other devices and is itself undoable, and the existing dialog shape
  is reusable.

The list itself is a small capped table (`recent_deletions`, ten rows, derived,
rebuildable, never synced) so it opens instantly, with a background refresh
that scans the log tail. `MediaGc.chunkBytes` — a megabyte at a time, ~30 ms of
work between yields — is the model for that scan and the reason it is a hitch
rather than a freeze. **The list is deliberately not keyed on `nodes`:** a
purged page has no `nodes` row, and that is precisely the entry a student most
needs. Its cap of ten *is* its prune; ten rows cannot leak.

### The one real hole: bytes are not in the log

A restored image needs its **bytes**, and bytes live in `blobs/` (and the
container's `blobs` table until Step 7), never in the log. ADR-0007's collector,
once built, frees a blob when no `blob_refs` row names it — and `blob_refs` is
rebuilt from **current** page content on every single save
(`notebook_writer.dart:226`, `DELETE FROM blob_refs WHERE page_id=?` then
re-insert). So a deleted image's bytes become collectable the moment the page
saves.

**Therefore the ten notable deletions are a GC root.** Blob GC declines to free
a hash named by an entry in the list. That is a bounded, explicit, ten-deep
rule — and it is a straight improvement on today, where `page_versions` pins
blobs *by accident and for ever*.

Worth stating in the same breath, because it means the reduction is smaller
than it looks: **today's 30-deep restore is already partly broken and nobody
has noticed.** `page_versions` is not a GC root and its snapshots name hashes
that have no `blob_refs` row — which is exactly the orphan class §1.6 measured
(Honours-2 18 blobs / 1,691,344 B; Honours-4 3 / 250,178 B; My Notebook 2 /
566,810 B, **20% of that notebook's blob bytes**). Restoring such a snapshot
returns a page with a broken picture. It has not bitten only because blob GC
does not exist yet; it would have bitten on the day ADR-0007 shipped.

### What this frees

**Container bytes, today: 0.03–0.23 MB.** Small, and it would be dishonest to
sell it as the reason.

**Container bytes, at the ceiling: about 225 MB on the one shape that has been
measured.** `database.dart`'s `_sweepOrphanedVersions` records its measurement
on *"a 322 MB container holding 9,840 snapshots, the worst shape the owner's
328-page imported notebook could reach"* — against that notebook's actual
97,542,144 B container. 9,840 is 328 pages × the 30-per-page retention rule.
Dropping the table does not free 225 MB from anyone's disk today; it removes
the ceiling, permanently, and with it the 19.6 ms first-open sweep and the
364 ms pass that clears it.

**Video reclamation, which is where the real bytes are.** `MediaGc` consults
every stored source, and skips **this device's own** `.oplog` (`media_gc.dart:
310-317`) on the argument that it is history rather than a reference. On a
**single-device, never-synced notebook — the majority case, which is why
`materialiseBlobs` defers image bytes at all (§2.1)** — that leaves
`page_versions` as the *only* permanent pin on a deleted video. And it never
releases: a snapshot is evicted only when 30 newer snapshots of the **same
page** exist, so a video deleted from a page the student then stops editing is
pinned **for ever**. Dropping the table makes `kVideoReclaimMinimumAge` — 30
days, chosen to match the promise already made about the recycle bin — the
actual bound, which is what it was written to be. Concretely: **on a
single-device notebook, a video deleted from a page that is not edited 30 more
times becomes reclaimable after 30 days instead of never.** Video files are the
largest single things Openote stores.

**Ink blobs.** Commit `78886cf` established what a changed ink hash costs: 82
blobs / 2,933,421 B, a whole second copy of the handwriting, for a payload
whose decoded strokes are byte-identical. Every "Shrink handwriting" conversion
(§4.3) and every erase that rewrites a stroke list mints a new hash, and today
the snapshots hold the old hashes alive as references while carrying no
`blob_refs` row — the orphan class above. Dropping snapshots does not delete
those by itself (blob GC is unbuilt), but it stops the mechanism that mints
them, so ADR-0007's collector can free them instead of finding a snapshot
naming each one.

### What a student loses. Stated plainly, because it is a real reduction

**Today:** up to **30 restorable snapshots per page**, taken automatically
about every ten minutes of editing, each a complete copy of the page. A student
can step back through a morning's work in ten-minute increments and restore any
of them — including a change they made, saved, and only regretted hours later.

**After Step 8a:** they can see **who last changed each block and when**, and
they can get back **the last ten notable deletions**. They **cannot** wind a
page back to how it looked at 09:40 this morning. If they rewrote a paragraph
badly, saved, and closed the app, there is no earlier copy of that paragraph to
return to.

That is the loss. Three things soften it and none of them is a rewrite of the
sentence above:

- **Undo and redo are untouched** — a hundred page snapshots per page, in
  memory (`media_gc.dart`'s source 6), which is how "I deleted it by accident"
  is actually undone in practice.
- **The recycle bin is untouched** — thirty days, whole pages and sections.
- **Mirror backups are untouched**, and are the real *"get me last Tuesday"*
  answer: `mirrors.dart` takes a `VACUUM INTO` snapshot on purpose, and §1.4
  measured it at **1.34 MB** after demotion. If anything, the honest response to
  this reduction is to make that door easier to find, in the same way §2.4 says
  the leftovers scan needs a door.
- And, as above, **part of what is being removed does not work**: a restore
  that names a collected blob returns a broken picture.

### Migration, proof, data safety, rollback

**Migration.** The v2 schema has no `page_versions`; the rows go with it. Five
prune sites collapse to zero, and each must actually be deleted rather than
left pointing at a table that is gone: `maybeSnapshotVersion`'s 30-deep
retention `DELETE` and its ten-minute `minGap` snapshot-on-save
(`repository.dart:1284-1308`), `NotebookWriter.purgeNode`'s delete
(`notebook_writer.dart:136`), `Repository.purgeExpiredNodes`'
(`repository.dart:1149`), the delete-notebook clear (`repository.dart:1253`),
`_sweepOrphanedVersions` (`database.dart:147-208`, the whole of commit
`1be2d28`'s repair), and the `page_versions` half of `everyStoredPageText`
(`repository.dart:1499`). Losing the snapshot-on-save is also the removal of a
write: a full page-JSON `INSERT` every ten minutes of editing, in the save path.

**Proof.** Matrix rows **B7, B8, C8, C9, H3**. The load-bearing ones: an
attribution index rebuilt from the log alone equals the one maintained
incrementally on save (this is the "it is free" claim, asserted rather than
argued); and a notable deletion restores **with blob bytes** after a rebuild,
with blob GC run in between.

**Data safety.** Crash: both tables are derived, so a torn one is a rebuild,
not a loss. Disk full: they are the smallest things written. Old build meets
new file: an old build opening a v2 container is refused by `user_version`
anyway; an old build never sees these tables. Shared-folder skew: nothing here
is synced except the device *label* in `manifest.json`, which is
last-writer-wins on a display string.

**Rollback.** Revert. The tables are derived and droppable. The **one
irreversible part** is deleting the `page_versions` rows, and it happens inside
Step 8's migration — so it is covered by the same marker file, the same
refusal-to-proceed prechecks, and `undemote`. If that is judged too tight a
coupling, the safe split is: ship 8a's two tables and the UI first, leave
`page_versions` in place and unread for one release, and drop the rows in the
release after. That costs one release of dead table and buys a clean revert.

## Step 8b — Register the notebook folder, and retire the `.onote` association (decision 2)

**Ships in the same release as Step 8's rename.** The day `cache.onote` appears
is the day Explorer must stop offering to open one.

### The decision, and the part of it that may not be implementable

The decision is *"register the folder instead"*: associate the `.onotebook`
directory, stop associating `.onote`. §4.2 and commit `39e5d33` both flagged
that folder associations are weaker on Windows and **unverified**, and that
flag has not been cleared. So, plainly:

> **On Windows, this decision may not be implementable as stated, and nobody
> has yet proven otherwise.** Windows associates *extensions*, and an extension
> on a directory name is not one. The mechanisms that exist are a
> `Directory\shell\<verb>` entry — which would put "Open with Openote" on the
> context menu of **every folder on the machine** and still not change what a
> double-click does — or a registered shell namespace extension, which is a COM
> DLL and far outside what a per-user Inno install can or should do. The
> realistic outcome is that double-clicking `MyNotebook.onotebook` opens it in
> Explorer, as any folder does.

This is recorded as a decision **taken**, with the Windows implementation
**unproven**, rather than quietly reinterpreted. What must be proven, and the
fallback if it fails, are both below.

### What must be proven, per platform

| Platform | The claim to test | How | If it fails |
|---|---|---|---|
| **Windows** | A per-user (HKCU) registration can make double-clicking a `*.onotebook` **directory** open Openote, with no COM namespace extension | Register the candidate keys on a clean Windows 11 VM, create `Foo.onotebook`, double-click, record what happens | The pointer-file fallback below. Expected to be needed. |
| **Linux** | freedesktop MIME can subclass `inode/directory` with `<glob pattern="*.onotebook"/>`, and **GNOME Files and Dolphin honour it on a double-click** rather than always opening the folder | New `openote.xml` type, `update-mime-database`, test in both file managers | Pointer file, same as Windows |
| **macOS** | `.onotebook` as a document **bundle** (`CFBundleDocumentTypes` + `LSTypeIsPackage`) — the one platform where this is native and clean | ADR-0006 §6 already anticipates it, and says presentation MUST NOT change the layout | — |
| **All** | The layout is **unchanged** by any of it: `manifest.json`, `ops/`, `blobs/` are plainly there and `Directory.listSync` sees them | Automatable, and now a matrix row rather than a human pass (decision 4) | Stop — this one is not negotiable |

**The fallback, designed now rather than later.** A small pointer file inside
the directory — `MyNotebook.onotebook/Open this notebook.onotelink` —
associated by extension the ordinary way, described in Explorer as *"Openote
notebook shortcut"*, whose contents name the notebook. A student sees a file
with the Openote icon inside the folder they just opened and double-clicks it.
It costs one small file in the synced tree, it is not a database, and it cannot
be mistaken for a notebook. It deliberately does **not** reuse the `.onote`
extension, which is being retired.

### Retiring `.onote` is an uninstall/upgrade problem, not a deletion

This is the half that is easy to get wrong, because deleting lines from the
installer script does nothing to machines that already ran the old one.

**Windows.** `packaging/windows/openote.iss` registers, under
`HKCU\Software\Classes`: `.onote`'s default value and `Content Type`, the
ProgID key with `DefaultIcon` and `shell\open\command`, `.onote\OpenWithProgids`,
and `Applications\openote.exe` with `SupportedTypes = .onote`. Every one
carries `uninsdeletevalue` or `uninsdeletekey`, so an **uninstall** is clean.
An **upgrade** is not: Inno applies the new `[Registry]` section and **deletes
nothing that is merely absent from it**. Removing the lines therefore leaves
`.onote` pointing at Openote on every existing install, for ever — and the
in-app updater (`/SILENT`, same `AppId`) is exactly that path. So the upgrade
must ship **explicit deletions**, keeping the same asymmetry the existing
comments already explain: delete the *value* on `.onote` and on
`OpenWithProgids` (other programs may have entries under those keys), delete
the *key* for our own ProgID and for `Applications\openote.exe`.

**Linux.** `packaging/linux/openote.xml` declares `application/x-onote` with
both a `*.onote` glob and a magic match on `SQLite format 3` at offset 0 plus
`ONOT` at offset 68 — **the magic match is the sharper problem**, because it
identifies a `cache.onote` just as well as a notebook. The new file declares a
directory type on `*.onotebook` and the old type is removed; `MimeType=` in
`org.openote.openote.desktop` changes with it. The postinst already runs
`update-mime-database` and `update-desktop-database`, so both take effect
without a logout — that is stated in the desktop file's own comments and is why
this is a packaging change rather than a support burden.

**The app side.** `startup_args.dart` needs no change *in kind* — a directory
arrives on argv as an ordinary path, and its rules about switches, `--`,
`file://` URLs and relative paths all still apply. What changes is downstream:
`main()` must notice that the path is a **directory** and route it to the
adopt/join path (`Repository.adoptLogDirectory`) rather than to `openOnote`.
The single-instance handoff through `.open-request` (spec §7) carries a path
already and needs no new shape.

### The `cache.onote` hazard

The investigation raised it and it is the sharpest thing in this step: **a
`cache.onote` still matched by the old association lets someone clone a dead
copy.** After Step 7 that cache has an **empty `blobs` table**, so the clone is
a notebook whose every image is missing — and it will pass `integrity_check`,
and `notebookFileProblem` will call it *"looks like a notebook"*, because it
sniffs the SQLite magic and `application_id` and a cache satisfies both.

Three mitigations, and all three are wanted:

1. **The stale association is actually removed** (above), so Explorer stops
   offering Openote for a `.onote` at all. This is the one that matters, and it
   is the one that only works if the *upgrade* deletions ship.
2. **Both builds refuse it.** `user_version = 2` makes an old build refuse
   (Step 8's version gate). A **new** build must refuse too — Step 8 item 4 —
   on the double-click path and on argv, by name (`cache.onote`) and by
   `user_version`. The sentence a student reads: *"This is Openote's working
   copy, not your notebook. Open the notebook folder instead."* No "container",
   no "cache", no "format v2".
3. **Considered and rejected:** renaming the file so nothing can match it —
   `cache.db`, say. It would work, and it contradicts ADR-0006 §3 and spec §11's
   diagram for a benefit that mitigation 2 already delivers. Recorded so nobody
   re-proposes it as new.

Note what is **not** a hazard: `.gitignore:8:*.onote` already covers
`cache.onote` for git (§1.2), and Step 4 has already moved the container out of
the synced folder, so no cloud client is replicating one either.

**Proof.** Matrix rows **G6, G7, G8**, plus the per-platform table above.
**Rollback.** Revert the packaging change; a re-registered `.onote` association
is one upgrade away in either direction. Nothing on disk changes.

## Step 9 — Video engine on demand (split out entirely)

**Not part of this cluster.** It shares nothing with the format work but a task
number, and bundling it behind a format migration is why it has not shipped.

Measured: the video stack is **48,377,078 B of a 97,831,741 B Windows Release
bundle (49.4%)** — `libmpv-2` 29,764,622 + `libGLESv2` 7,414,088 +
`d3dcompiler_47` 4,891,080 + `vk_swiftshader` 4,808,008 + `vulkan-1` 872,776 +
`libEGL` 472,904 + the two plugin DLLs. The ANGLE half is **media_kit's, not
Flutter's**: `media_kit_libs_windows_video-1.0.11/windows/CMakeLists.txt`
downloads *both* `mpv-dev-…7z` and `ANGLE.7z` at build time into
`build/windows/x64/{libmpv,ANGLE}`. It touches **zero bytes of notebook data** —
no `media/` directory exists anywhere in the workspace or the Drive folder.

One open verification (§7.4) and one product constraint: the first-video
download must be **one click**, and must say something like *"Openote needs to
fetch a video player (about 30 MB). Get it"* — no mention of mpv, ANGLE or
codecs.

**Open it as its own task and ship it whenever.** It cannot lose anyone's notes.

# Part 4 — Things this plan deliberately leaves alone

## 4.1 Nothing rewrites a log line, ever

Not compaction, not segmentation, not a spelling fix. `Op.toJson` emits exactly
`{v,dev,seq,lc,ts,enc,op,d}`, so a rewrite through `Op.encode` drops any
envelope key a newer build wrote, and `d` is not numerically byte-stable through
`jsonDecode`/`jsonEncode` — table cells, board card geometry, code-cell output
and block transforms all still carry doubles there.

## 4.2 The `.onote` file association — ⚠ NO LONGER LEFT ALONE

> **Superseded 2026-08-15 by decision 2.** This section used to say the
> question of what a student double-clicks was open (§7.2) and that the plan
> was leaving the association alone. The owner answered it: *"Register the
> folder instead."* The work moved into **Step 8b**, and the original reasoning
> is kept below because it is still the accurate statement of the hazard.

`packaging/windows/*.iss` registers `Software\Classes\.onote` and
`packaging/linux/openote.xml` globs `*.onote`; `notebookFileProblem` sniffs the
SQLite magic and `application_id`, both of which a cache satisfies. Task #43
shipped the double-click-a-notebook flow. After Step 8 the container is a
local-only cache in the workspace — so what does a student double-click? Step
8's `user_version = 2` at least makes a double-clicked cache **refuse** rather
than silently clone itself into a second notebook.

Two things Step 8b adds that were not visible from here. First, refusing is
only half of it: the association must be **removed on upgrade**, explicitly,
because Inno deletes registry entries at uninstall and never merely because
they have vanished from the script — so deleting the lines would leave `.onote`
pointing at Openote on every machine that already has it. Second, after Step 7
the cache a student might clone has an **empty `blobs` table**, so the clone is
a notebook with every image missing that nevertheless passes
`integrity_check`.

## 4.3 The legacy notebooks on this disk

Honours-2 still holds 113 inline-ink pages, 67.05 MB of `page_mirror` and a
64.56 MB log. The ink conversion never ran on it because `_runHousekeeping`
requires the notebook to be **open**, and Honours-2 is not registered in
`workspace.json` at all. That is settled, not mysterious — but it means the
pre-Phase-1 shape can still walk into the migration if a user ever re-registers
one, which is why matrix row B3 exists and why the two migrations must compose
in either order.

The honest offer for such a notebook is a one-off, opt-in, offline, verified
**"this notebook still uses the old handwriting format — shrink it"** action.
Not a format change.

# Part 5 — The CI testing matrix

## 5.1 Four rules that make it trustworthy rather than merely long

1. **Every fixture is generated, never committed.** Model: commit `2a0a300`,
   whose Rust `onenote.rs` test module synthesises real MS-ONESTORE bytes at
   runtime. One new `app/test/support/notebook_fixture.dart` emits a real
   `.onote` + `.onotebook` pair to a requested shape — pages, ink blocks,
   images, videos, `page_versions`, op count, device count, `user_version`,
   `materialiseBlobs`, pre- or post-Phase-1 ink — seeded and deterministic,
   **each parameter named after the trap it reproduces**. Images are generated
   4×4 PNGs. **The owner's notes never enter the repo.**

   *Added by decisions 1 and 2:* `deletions:` (a scripted sequence of page,
   section, blob-bearing and large-text removals, so the "notable" rule is
   exercised against things that must and must not qualify), `deviceLabels:`
   (so attribution is asserted against a *name*, not a uuid, and against a
   device with **no** label), and `folderOnly:` (a `.onotebook` with no
   container beside it, which is what Step 8b's double-click path receives).
   `page_versions:` stays — the migration has to be tested against notebooks
   that have snapshots to drop. All still synthetic; the rule does not bend for
   the new cells.
2. **Every destructive cell asserts on CONTENT, not on the absence of an
   exception.** All six bugs found on 2026-08-15 passed their exception checks.
   The assertion of record is `Materializer(readAll())` == container,
   page-for-page and block-for-block, **plus blob-set equality with bytes
   compared** — because §2.2 showed the page-level property going green through
   two runs that destroyed 193 and 271 image blocks respectively.
3. **A cell that cannot fail is not a cell.** Each row ships with a recorded
   revert-check: name a mutation, record how many assertions it turns red.
4. **A skip is a failure in CI.** `initSqliteForTests` already throws under CI.
   A meta-test reads the JSON reporter and fails if the skipped count exceeds a
   number committed to the repo.

   **Decision 4 makes that number per-platform.** One shared budget is exactly
   the shape that hides a regression: macOS already skips more than Windows
   (the sample-gated files below), so a migration test that starts skipping on
   macOS alone disappears under a budget sized for macOS. Commit **one number
   per platform**, and let the macOS one be the tightest thing in the file,
   because macOS is now the platform carrying a one-way migration with no human
   behind it.

**Baseline, measured at `bb35fad`:** Dart 1,388 passed / 16 skipped / 0 failed
locally; Rust 74 passed / 0 failed. In CI it is really **~1,384 passed / 20
skipped** — five sample-gated files (45 `expect()` calls) skip because
`USERPROFILE` is unset on Linux/macOS runners, verified empirically by
re-running them with `USERPROFILE` pointed at an empty directory.

## 5.4 Which three rows to build first

If only three cells are ever built, build these — they are the ones that would
have caught the six bugs found on 2026-08-15:

1. **E7 + C1's orphan-scan assertion** — the cleanup surface must not offer the

2. **B1/C4's blob-completeness invariant** — every `blob_refs` hash resolves to

3. **E3** — Windows rename under a lock.

4. **A5 — `undemote` green on macOS.** If the inverse of an irreversible step

## 5.5 Before any `M` in this matrix means anything

Decision 4 rests entirely on the macOS column being real. It is worth checking
that it is, because **`W/L/M` in a plan is a claim about a workflow file, not
about a test**, and this project has been punished before for exactly that
grade of inference (§5.2: `release.yml` runs no tests at all, and its own
comment says CI gates every push).

Three things to verify in `.github/workflows/ci.yml` **before** Step 8 is
written, not after:

1. A macOS runner is in the job matrix at all, and the Dart and Rust suites
   both run on it.
2. The migration tests are not skipping there. `initSqliteForTests` throws
   under CI, so a missing SQLite would fail loudly — but the five sample-gated
   files skip on macOS because `USERPROFILE` is unset, and a per-platform skip
   budget (rule 4) is what keeps a *new* skip from hiding behind those.
3. Group M's cells run on **every** push, not only on tags. A cell gated to
   `release/**` finds the bug after the release branch exists, which for a
   one-way migration is the wrong side of the decision.

If any of the three is false, decision 4 is not "ship it, macOS is untested
anyway" — it is "ship an unproven one-way migration to a platform with no
coverage at all", which is a different sentence and not the one that was
agreed.

# Part 6 — Rollback, per step

| Step | Reversible? | How |
|---|---|---|
| 1 Save failures visible | yes | revert; `workspace.json`'s `format` key is inert to older builds |
| 2 Log reader hardening | yes | revert; no on-disk change |
| 3 Vocabulary + gates | yes (writer half) | revert the writer; **the reader accepts both spellings forever**, so a rolled-back build still reads new logs |
| 4 SQLite leaves the cloud | yes | the same mover, in reverse; nothing is deleted before a hash match |
| 5 Blobs always materialised | yes | delete the added files, or leave them — content-addressed files are never wrong, only redundant |
| 6 Read-through | yes | revert; blobs written during the bake are in `blobs/`, which the fallback path and the backfill both handle |
| 7 **Reclaim** | **only via its inverse** | `refillContainerBlobs()` — written and tested in the same PR, possible only because Step 5 proved coverage |
| 8 **Rename to v2** | **only via its inverse** | scripted `undemote`: rename back, `user_version` → 1, `refillContainerBlobs()`, `workspace.json format` → 1. Tested in the same PR |
| 8a **Simplified version history** | **mostly** | the two new tables are derived — drop and rebuild. The **irreversible** part is deleting the `page_versions` rows, which rides inside Step 8's migration and therefore inside `undemote`. The clean split, if that coupling is judged too tight: ship 8a's tables and UI first, leave `page_versions` in place and unread for one release, drop the rows the release after |
| 8b **Folder association** | yes | revert the packaging change; a re-registered association is one upgrade away in either direction, and nothing on disk changes. **But the retirement half only reverts if it was written as explicit registry deletions in the first place** — see G7 |
| 9 Video on demand | yes | re-bundle the DLLs |

**The rule:** an irreversible step does not ship until its inverse is written,
tested, and reachable by a user without a terminal.

**Decision 4 adds one word to that rule: *everywhere*.** "Tested" now has to
include the platform nobody has driven by hand, or the rule protects two
platforms out of three. Row A5 is that word made mechanical, and it is a
release blocker for the release that ships Step 8.

## 7.1 Is *"Earlier versions of a page are kept on this computer only"* acceptable? — ✅ ANSWERED

and preserving it across a rebuild by copying the table out and back** —
measured at 6–22 rows and 0.03–0.23 MB, so the mechanism is nearly free. What
needed a call was the *promise*: is it acceptable that page history does not
follow a notebook to a second machine and does not survive a full disk loss?
The alternative — a `page.version` op kind — puts 30 full page snapshots per
page into an append-only log, which is the one thing that would make it grow
without bound.

**Answered — with neither option.** *"Could we do a simplified version history?
Dont need full complete edit history, but keeping track of who made what edits
(that are currently visible and maybe recent deletions, like the last 10
noteable deletions)"*.

That is a smaller and different feature, and the design is **Step 8a**. In one
paragraph: attribution comes out of the op log for free, because every op
already carries `dev` and `ts` and names the block it changed, so "who last
changed this" is the last op in total order naming that block — no new op kind,
**not one new byte in any log**, nothing new synced. The last ten notable
deletions are likewise a *query* over the log rather than stored copies,
because §4.1's promise that no log line is ever rewritten means a removed
block's last content is still there. `page_versions` is dropped, six prune
sites collapse to zero, the 30-per-page ceiling goes (measured at 322 MB and
9,840 snapshots on the one shape that has been measured, against a 97.5 MB
container), and on a single-device notebook a deleted video becomes reclaimable
after 30 days instead of never.

**What it costs the student is written out in full in Step 8a and is not soft:**
they lose the ability to wind a page back to how it looked at 09:40 this
morning. Undo, the recycle bin and mirror backups are untouched, and part of
what is being removed does not currently work anyway — but the reduction is
real and is stated where it will be read.

## 7.2 What does a student double-click after the demotion? — ✅ ANSWERED

**As asked.** Task #43 shipped the double-click flow and the installers
register `.onote`. After Step 8 the thing that syncs is a **directory**, and
Windows has no equivalent association. Options: register a directory verb; ship
a small pointer file; or drop double-click for shared notebooks and lean on the
join flow. Step 8's `user_version = 2` makes a double-clicked cache *refuse* —
which is safe but is not an answer.

**Answered: *"Register the folder instead."*** The work is **Step 8b**, and it
is bigger than a registration because the `.onote` association already shipped:
retiring it is an **upgrade** path (Inno deletes registry entries at uninstall,
never merely because a line disappeared from the script), and the `cache.onote`
that Step 8 leaves behind is a file that satisfies every sniff test the app has
while having an empty `blobs` table after Step 7.

**One thing must be said back rather than quietly worked around.** The plan and
commit `39e5d33` both flagged that folder associations are weaker on Windows
and unverified, and that flag is not cleared: Windows associates *extensions*,
and there is no per-user way to claim a directory's double-click without a COM
shell namespace extension. **The decision is recorded as taken; the Windows
implementation is recorded as unproven and probably not possible as literally
stated**, with the proof named in Step 8b's per-platform table and the
pointer-file fallback designed now rather than after the discovery. macOS is
the one platform where it is native and clean — which collides with decision 4
in an interesting way, since nobody has ever run macOS.

## 7.3 Does the demotion keep a third-party-openable single file at all? — ✅ ANSWERED

**As asked.** Spec §10 sells the `.onote` container as the open format. Spec
§11 already says the openness guarantee **moves to the log** — but §10 has not
been rewritten to match, and "anyone can read and write `.onote` files" is the
licensing invariant CI enforces via `cargo deny`. Is the ordered union of
`ops/*.oplog` + `blobs/<sha256>` the artifact we tell third parties to read,
and do we owe them a one-file export instead?

**Answered: *"The log is the open format."*** The container is purely a cache,
and **no third party should read it**. The consequence, stated so it cannot be
missed: **there is no longer any obligation to maintain a self-contained
single-file `.onote` that a third party can open with plain SQLite.**

The two sections that disagreed are resolved in §11's favour, and the edit is
larger than §10 — because the *promise* is actually made in §4, which neither
side of the disagreement mentioned.

| Spec section | Says today | Must become |
|---|---|---|
| **§1** goal 1 | *"Every byte is either a well-known open format … A competent developer MUST be able to write a read-only implementation from this spec alone"* | Unchanged in force, **re-pointed at the `.onotebook` tree**. It gets easier to meet, not harder: JSON Lines plus SHA-256-named files is a lower bar than SQLite plus a JSON schema. |
| **§2** Container overview | *"An Openote notebook is a single file with the `.onote` extension"*, and *"Notebooks are self-contained: moving/copying a `.onote` file moves the whole notebook, attachments included"* | **Both false after the demotion, and both are exactly what a third party would build on.** The notebook is the `.onotebook` directory; the container is a local cache with no compatibility standing. Highest-priority rewrite in the list. |
| **§4** "Page content and the openness guarantee" | Bullet 3: *"Third-party writers need nothing but SQLite and JSON"* | The heading names a guarantee that has moved. Rewrite §4 as the *cache's* internal layout, informative only, and move the guarantee into a new normative section about the log. **This is the one the §10-vs-§11 framing missed.** |
| **§7** The workspace | *"Notebooks are discoverable without the registry (directory scan)"*; and the single-instance rationale, *"Associating `.onote` with the app made a second process one double-click away"* | The scan looks for `*.onotebook` directories; the single-instance reasoning re-points at the folder association (Step 8b). The `format` field itself is **correct as documented** and is what correction 1 confirmed. |
| **§8** Open-folder export | A lossless export to a plain folder | Unchanged, but it now needs one sentence distinguishing it from the `.onotebook` tree, which is also a folder full of open files. **A genuinely new confusion this decision creates.** |
| **§10** Conformance checklist | Minimal reader: open SQLite → check `application_id` → read `nodes` → read `page_mirror.json` → resolve `blobs`. Minimal writer: write `page_mirror.json` + the `nodes` row in one transaction | Minimal reader: read `manifest.json`; read every `ops/*.oplog` as JSON Lines; order by (`lc`, `dev`, `seq`); apply the documented op kinds; resolve hashes to `blobs/<sha256>`. Minimal **writer**: append JSON Lines to your own `ops/<device>.oplog`, never touch anyone else's, write bytes to `blobs/<sha256>`. **That is a simpler writer than today's** — one append, no transaction, no projections to keep in step. |
| **§11** Where this format is going | Already correct in substance | Promoted from *(informative)* to normative. Its diagram still draws `cache.onote` **inside** the synced directory — §1.2's amendment, still required and now doubly so. Its "one caveat" paragraph about sparse `blobs/` on local-only notebooks is **fixed by Step 5** and should go to past tense there, not at Step 8. |
| **§12** Compatibility promise | ✅ on the container's tables | Move the ✅ onto the **log envelope, the total order, and the `.onotebook` layout**; mark the container schema **not a compatibility surface** — it is a cache, it may change whenever, and it does, at v2. Add the v2 changelog entry. |

**What does not change:** the `cargo deny` licensing invariant (ADR-0005,
matrix row A3) is about dependency licences, not about the container, so it
survives verbatim — only the sentence describing what it protects is
re-pointed.

**And the one-file export question is answered too:** §8's open-folder export
is the thing we already promise, and it is a *better* answer than a SQLite file
because it needs no library at all to read. **No new export is owed.**

## 7.4 Two things that gated work rather than shaping it — one now answered

- **Is one human macOS pass available before Step 8 ships? — ✅ ANSWERED: no,
  and it does not have to be.** *"ship it, macOS is untested anyway."* The
  rationale holds: commit `3230264` records that the macOS Xcode project never
  built the Rust core and the loader fell back in silence, so macOS has already
  been shipping unverified and this migration does not make it meaningfully
  riskier than the release before it. **I4 stops being a gate.**

  What that costs is not filed under "accepted risk", because it is specific:
  **a one-way v1 → v2 migration will run, for the first time, on a platform no
  human has ever driven.** So the compensations are strengthened rather than
  the risk softened, and all three are cheap:

  1. **The migration is opt-in** on every platform — one click, plain words, an
     app that runs indefinitely without it. This converts "an unproven one-way
     migration ran on your notebook" into "you chose the moment". It is the
     single largest risk reduction available and it costs one dialog.
  2. **`undemote` must run green on macOS in CI** (row A5), and it is a
     **release blocker** for the release that ships Step 8. Part 6's rule
     already required an inverse; decision 4 is what makes its macOS half
     load-bearing.
  3. **Group M** replaces the human pass with four automated cells — including
     M4, which tests commit `3230264`'s own bug and is the reason this
     decision's rationale holds at all. And **§5.5** says to check that the
     macOS column in `ci.yml` is real *before* Step 8 is written, because
     `W/L/M` in a plan is a claim about a workflow file, not about a test.
- **Does removing media_kit actually reclaim all 48.38 MB, or does Flutter's
  Windows embedder need `libEGL`/`libGLESv2` independently?** The five ANGLE
  DLLs are all dated 2022 and sit under a directory media_kit created, which is
  strong evidence — but that is inference. The only honest answer is a release
  build with the dependency removed and the app launched. One afternoon, and it
  is Step 9's whole business case.

## 7.5 Can Windows associate a folder at all? — NEW, created by decision 2

Not a product question; a factual one nobody has answered. Step 8b's
per-platform table is the test plan, and the expected answer on Windows is
**no** — an extension on a directory name is not an extension, and the
mechanisms that exist are a context-menu verb on every folder on the machine or
a COM shell namespace extension. **The fallback is designed** (a small pointer
file inside the directory, associated the ordinary way), so this question gates
which of two designs ships, not whether the step can ship. It needs one clean
Windows 11 VM and an afternoon, and it should be answered before Step 8b is
written rather than during it.

## 7.6 What is "notable"? The rule is decided; one number in it is not — NEW, created by decision 1

Step 8a's rule is defensible on its face: whole pages, whole sections, anything
holding or naming a blob, and text blocks over a size bar; explicitly not
eraser gestures. The size bar is currently **280 characters**, and that number
is a guess with a decimal point on it. **No `block.remove` count has ever been
taken on the real logs** — the one edit-driven log's measured properties (2.55×
write amplification, 237.6 KB written for 93.1 KB of content) say a great deal
about `block.set` and nothing about removals.

Matrix row **H3** adds removal counts and a removed-content size distribution
to the shape tool the owner already runs, **counts only, never content**. The
number comes from that. Until it does, 280 is written down as a placeholder
rather than as a decision, which is the honest way round.
