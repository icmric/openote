## 0. The report, verbatim

> *"Ive just done some further testing with the folder sync and its not live
> updating. If i make an edit on one machine it seems like that change doesnt
> really ever get reflected on the other machine (bar maybe closing and
> reopening the app potentially, but i havent tested that). For a change to be
> reflected i have to press the little sync button in the bottom which does
> sync the changes, however is also causing the app to fully lock up for 10-20s
> as it works. I dont need to do any of that for the device that writes the
> changes though … I also noticed there were a bunch of files left over in the
> folder from deleted notebooks … which meant that when i was running through
> the setup process it thought there were several notebooks which didnt
> actually exist."*

**This supersedes [v0.12 sync latency](v0.12-sync-latency.md) §2**, which
asserted from code reading that folder sync was already the 2–6 s path. The
watcher exists and the debounce is 900 ms, but *it is not firing in practice* —
so that section's conclusion was wrong and its recommendation ("reposition
folder sync as the default fast path") must not be acted on until this is
fixed.

## 1. Three distinct faults

### 1a. The receiving device never notices — THE headline

**DID NOT REPRODUCE — fixed by d51c89a before this was investigated.** Two app
states pointed at one shared folder now see each other's edits with no button
pressed, in both directions. Everything below is the plan as written on
2026-08-09 and was not carried out; it is kept because the reasoning about
cloud clients renaming files is still the thing to check first if this ever
comes back.

Writing is fine; receiving is broken. The manual chip works, so `syncPull` and
everything under it is correct — **only the notification is missing.**

Where to look, in order:

1. **Is `_startWatching` ever armed?** It returns early on `!autoSync`,
   `notebookId == null`, `!syncLogEnabled`, or `!store.opsDir.existsSync()`.
   Instrument all four. Note `_startWatching` is called from `init()` (a
   post-frame callback), `setAutoSync`, `moveNotebookToFolder`, and — as of
   0.5.0 — `_loadNotebook`. Before that last fix it never re-pointed when you
   switched notebooks, so **test whether this reproduces on the notebook open
   at launch versus one switched to.**
2. **Does `Directory.watch` see a cloud client's writes at all?** This is the
   prime suspect. OneDrive and Drive do not write a file in place: they write a
   temp name and rename, or replace via a placeholder/reparse point, and on
   Windows some of those produce no `FileSystemModifyEvent` for the final path.
   `OpFolderWatcher._onEvent` filters on `path.endsWith('.oplog')` and
   `!contains(ownDevice)` — a temp name like `foo.oplog~RF1234.TMP` fails the
   first test, and the subsequent rename may arrive as a `FileSystemMoveEvent`
   whose `path` is the *source*. **Write a standalone probe that watches a real
   OneDrive folder and prints every event verbatim**, then edit on the other
   machine. Do not reason about this — measure it.
3. **Is the watcher alive but the pull silently failing?** `onForeignChange`
   fires `syncPull(...).catchError(debugPrint)`. Check whether it logs.

**Likely fix regardless of cause: do not rely on the watcher alone.** A
low-frequency poll (stat the ops directory's entries' mtimes every ~5 s; it is
a handful of files) is cheap, cannot be defeated by a filesystem-notification
quirk, and turns this from "works on some setups" into "works". Keep the
watcher as the fast path and the poll as the floor.

### 1b. The manual sync locks the app for 10–20 s

`syncPull` → `warmRecorder` (background isolate, fine) → `_syncPullLocked`,
which runs `applyForeign`, `_ingestForeignBlobs` and a whole
`runInTransaction` writing every changed page **on the UI thread**.

This is the same shape as the import freeze that v0.10 fixed: work that belongs
on another thread, and it will get worse as a notebook grows. The import's
answer — a writer isolate that owns its own SQLite connection, with the main
isolate doing only what genuinely cannot leave it — is the model. Note the pull
cannot simply reuse `IsolateImportSink`: the import targets a brand-new
notebook nothing else holds, whereas a pull writes a container the app has
open, so the handle has to be handed over or the work batched and paced.

Cheapest useful first step: pace it. `_syncPullLocked` already loops per page;
yielding between pages the way `restackFlowsPaced` does would turn one 20 s
block into interactive frames, without the isolate work.

### 1c. Deleted notebooks leave files behind, and setup offers phantoms

Two bugs, probably:

* **Deletion leaks.** Task #35 fixed `purgeNotebook` leaking the log directory,
  so some leftovers predate it — but the user says *several* notebooks, not
  all, which suggests a second path still leaks. Audit every route that removes
  a notebook: `trashNotebook`, `purgeNotebook`, `purgeExpiredTrash`, and the
  duplicates finder added in 0.5.0. Each must remove the container, the
  `-wal`/`-shm`, the `.onotebook` directory, and — for a notebook in a shared
  folder — must decide deliberately whether it may delete files another device
  still owns. **It probably may not**, which is the real subtlety: deleting a
  shared log directory removes another machine's ops. A tombstone, or refusing
  and telling the user, is likely correct.
* **Setup trusts the folder.** `findExistingNotebooks` lists `.onote` files in
  cloud folders. It should validate each candidate — open it, check it has
  nodes — and either hide or clearly mark ones that are empty or unreadable,
  with an offer to clean them up. The leftovers scan already exists
  (`findOrphanFiles`); onboarding should use the same judgement.

## 2. Order of work

1. **1a**, with a real probe against a real cloud folder, and the poll as a
   floor whatever the cause turns out to be.
2. **1b**, pacing first, isolate second.
3. **1c**, with the shared-folder deletion question answered explicitly rather
   than by accident.
4. Only then revisit git latency.

## 3. Tests this needs

There are none for the watcher today, which is why this shipped. At minimum:
a test that writes a foreign `.oplog` into a watched directory by a path that
mimics a cloud client (temp name then rename) and asserts a pull happens; and
one that deletes a notebook and asserts nothing of it remains on disk.
