# v1.0.2 — the right-click menu that flashes

> Reported during the v1.0.1 pass: *"If i right click and move my mouse over
> the right click menu it will flash … the bigger issue seems to come when
> there is an image inlined with the text. If i rightclick anywhere inside
> there while editing, whether on text or on the image, it will flash rapidly
> while my mouse is on it, never ceasing, making it basically unuseable."*
>
> **Root cause found, fix found, fix NOT shipped** — it breaks undo, and why is
> not yet understood. Everything below is so that the next attempt starts from
> the measurements rather than from scratch.
>
> Not a v1.0.1 regression: the inline closure responsible has been there since
> `3315cba` (2026-08-03), well before v1.0.0.

## The cause, confirmed in the framework source

`EditableTextState.didUpdateWidget` (`widgets/editable_text.dart`):

```dart
if (_selectionOverlay != null &&
    (widget.contextMenuBuilder != oldWidget.contextMenuBuilder || …)) {
  final bool shouldShowToolbar = _selectionOverlay!.toolbarIsVisible;
  _selectionOverlay!.dispose();
  _selectionOverlay = _createSelectionOverlay();
  if (shouldShowToolbar || shouldShowHandles) {
    SchedulerBinding.instance.addPostFrameCallback((_) {
      if (shouldShowToolbar) { _selectionOverlay!.showToolbar(); }
    });
  }
}
```

A `contextMenuBuilder` that is not **the same object** as last build disposes
the entire selection overlay and re-shows the toolbar a frame later. Both of
Openote's are inline closures, so they are a new object on every build:

- `live_markdown_engine.dart` — `contextMenuBuilder: (context, editable) { … }`
- `inline_table.dart` — `contextMenuBuilder: (context, field) => _cellMenu(context, field, r, c)`

So every rebuild of the block remounts an open menu. `BlockView` calls
`setState` on hover enter and exit, and the menu is drawn in the `Overlay` —
outside the block — so moving the pointer onto it *leaves* the block and
rebuilds it. A picture in the sentence adds rebuilds of its own, which is the
difference between "annoying" and "unuseable".

## The measurements

`app/test/context_menu_hover_test.dart`, over an eight-step pointer move onto
the menu. The two element-stability tests are **skipped**, because they fail:
they are the reproduction, kept so nobody has to rediscover it.

| | distinct menu elements during one hover |
|---|---|
| plain sentence | 3 |
| sentence with an inline picture | 5 |
| either, with the fix below | 1 |

Two things that rule out the obvious wrong turns:

- **`TextBlockView`'s element and the paragraph's `EditableText` element are
  stable throughout.** The editor is never replaced; only the overlay entry is.
  Do not go looking for a widget-tree reparent in `BlockView`.
- **`pumpAndSettle` always settles.** Nothing loops. "Never ceasing" is one
  flash per pointer event, which is why it stops when the hand stops.

Also ruled out: the `if (inlineChildFocused) return const SizedBox.shrink();`
early return in the paragraph's builder — stubbing it out leaves the churn
identical. And the menu's *contents* are stable, so it is not the
"Save image as…" row appearing and disappearing.

## The fix, and why it is not in

Hoist both builders so their identity is stable: a method tear-off for the
paragraph (equal to itself across builds), and one closure per cell built with
the grid for the table, since each is bound to its own `(r, c)`. Measured: the
churn goes to 1 and 1, and the whole table suite stays green.

**But `marker_chord_test.dart` → "a letter chord is never mistaken for a
marker" then fails.** Select a word, Ctrl+B from the toolbar chord, Ctrl+Z:

- With the inline closure: the text goes back to `hello world`.
- With the stable one: it stays `**hello** world`.

Probed: the controller is the **same object** before and after (`same=true`),
so the app's own undo never ran — `app.undo()` would have replaced the block
and with it the controller. It is the field's own `UndoHistory` that used to
have the pre-bold value and now does not. So **undo after a toolbar format
currently depends on that overlay churn happening**, which means the churn is
load-bearing by accident and the fix exposes a second, hidden bug.

Checked and not the explanation:
- Not a throttle: adding a 900 ms flush between Ctrl+B and Ctrl+Z does not
  help.
- Not `shouldChangeUndoStack`: `EditableText`'s predicate looks only at the
  selection's validity and the composing region, never at focus or the
  overlay.
- Not a stray edit: the diff is exactly two hunks, the call site and the
  moved method.

## Where to start next time

1. Find out what the overlay dispose/recreate does that puts a value on
   `UndoHistory`'s stack. `_createSelectionOverlay` and
   `TextSelectionOverlay.dispose` are the two places to read, and
   `undo_history.dart`'s `_push` / `initState` / `didUpdateWidget` are where it
   would land.
2. Fix that, then land the identity fix. In that order — the identity fix is
   right and small, and shipping it over a hidden undo dependency would trade
   a visible annoyance for a silent data-shaped one.
3. The alternative fix, if the above turns out to be framework-side: stop
   `BlockView`'s hover state from rebuilding the editor at all. Hovering
   changes chrome, so only chrome needs to rebuild — which removes the trigger
   rather than the sensitivity. Bigger, and it leaves the sensitivity in place
   for any other rebuild.
