### A.2 The shared widget

**New file: `lib/math/equation_editor.dart`.**


### A.4 The card dies — say so plainly

**Delete `InlineMathPopover` and `_InlineMathCard` from `lib/editor/inline_math_editor.dart`.** They are ~200 of that file's 270 lines. What replaces them: the `EquationEditor` mounted **inside the `_SourceSpan`** that `live_markdown_controller.buildTextSpan` already emits at line 1193 (§B). `InlineMathAtom` (lines 232–270) stays — it is the not-being-edited drawing — and gains nothing but a `selected` outline.

The file's own doc comment (lines 9–18) says the card was chosen because pixel-matching a WidgetSpan's baseline was fragile measurement bought for a transition effect. That reasoning is now obsolete for a different reason than it anticipated: we are not *matching* the span's rect, we are *becoming* the span. There is no baseline to match.

### A.5 The one thing that keeps a floating panel

The LaTeX escape hatch needs platform text input (a real `TextField` with IME, selection handles and a system caret). A `MathField` deliberately needs none of that — it is a bare `Focus` on raw `KeyEvent`s (`math_field.dart:1–12`) — which is exactly why it can live in a span. A `TextField` in a span opens a *second* `TextInputConnection` inside the host's.

Measured: a real nested `TextField` inside a `WidgetSpan` of a live `TextField` **does** take focus and accept text in the widget-test harness (`inner.hasFocus=true`, `host.hasFocus=true`, `inner.text="xyz"`, host buffer untouched). I do not trust that across three desktop embedders, and it buys nothing: the LaTeX view is an escape hatch behind the toolbar's ellipsis, used rarely and deliberately.

**Decision:** `EquationSourcePanel` — a small anchored panel, in `lib/editor/inline_math_editor.dart` where the card used to be — is the *only* surviving overlay, opened only when `placement == inline` and only from the Maths tab's LaTeX item. The block keeps its in-place source field (`math_block_view._latexEditor`), unchanged.

## B. In-place editing — option (i)

**The `MathField` lives in the `WidgetSpan` and takes focus.** The plan's §7 table calls this "Option A: dead end — receive keystrokes at all". That row is wrong and should be struck.

### B.1 The measurement it rests on

Re-run this session against the current tree (`scratchpad/probe5_real_mathfield_inline_test.dart` — a real `MathField` + `MathEditor` emitted from a controller's `buildTextSpan` into a live `TextField`):

```
after click-in: primary=math host.hasFocus=true math.hasFocus=true
  onChanged tex="x^{}"    text=area is $x^{}$ ok
  onChanged tex="x^{2}"   text=area is $x^{2}$ ok
  onChanged tex="x^{2+}"  text=area is $x^{2+}$ ok
  onChanged tex="x^{2+1}" text=area is $x^{2+1}$ ok
wrapper (session Focus) saw: []
editable renderEditable.selection=TextSelection.collapsed(offset: 17)
  EXIT MathExit.done
```

Every keystroke reached the inner `onKeyEvent` and nowhere else; the host inserted no characters (the embedder composes text only for a key the framework reports *unhandled*, the same mechanism `live_markdown_engine._onKey` already relies on); the host kept `hasFocus`, so its `TextInputConnection` and selection survived; Escape reached `onExit(MathExit.done)`.

### B.2 Mechanics

1. **State lives in the session, never in the placeholder's `State`.** `_LiveMarkdownSession` gains `int? _mathStart`, `MathEditor? _mathEditor`, `FocusNode _mathFocus`, `GlobalKey<EquationEditorState> _mathKey`. The span is rebuilt on every keystroke; a `State` there would be recreated and the caret lost.

2. **The controller learns one flag and one builder.** `LiveMarkdownController` gains `int? editingMathAt` and `Widget Function(String latex, TextStyle style)? mathEditorBuilder`. In the math branch of `buildTextSpan` (line 1189), when `from == editingMathAt`, emit `mathEditorBuilder!(c.inner, cBase)` as the `_SourceSpan`'s child instead of `InlineMathAtom`. **`source` stays `'$'` and the trailing hidden `TextSpan` stays** — the coverage check at line 489 counts only `_SourceSpan.source`, and a bare `WidgetSpan` would drop the paragraph to unstyled source. This is the invariant the whole live editor rests on and it is not touched.

3. **Entry points**, all landing on `session.enterInlineMath(int start, int end, String latex, MathCaret where)`:
   - click on `InlineMathAtom` — the existing `onMathTap` (`live_markdown_controller.dart:76`), minus the `Rect` argument, which nothing needs any more;
   - Left arrow crossing in from the right → `where: MathCaret.end`;
   - Right arrow crossing in from the left → `where: MathCaret.start`;
   - Backspace at the run's `end`, Delete at its `start` (§B.5);
   - Alt+= (§C).

4. **Focus in.** `enterInlineMath` sets `_mathStart`, builds `_mathEditor = MathEditor.open(latex)`, places the caret, and calls `notify` → the placeholder mounts → `EquationEditor(autofocus: true)` claims focus post-frame, exactly as `MathFieldState.build` (lines 301–305) already does and for the recorded reason ("i cant actually type anything right off the bat").

5. **Focus out, and where the caret lands.** `session.closeInlineMath(MathExit how)`:
   - `MathExit.right`, Enter, Escape, Done → `controller.selection = TextSelection.collapsed(offset: start + '\$$latex\$'.length)`;
   - `MathExit.left`, or Backspace out of an empty equation → `offset: start`;
   - a click elsewhere in the paragraph → the host's own tap moves the caret; the controller's `value` setter clears `editingMathAt` when the new selection falls outside `[start, end]`;
   - leaving the block → `OnoteEditSession.dispose`.

   All four run through `closeInlineMath`, which is also the single place the empty sweep (§C) and `app.clearActiveMath(_mathKey.currentState)` fire. One exit path, not five.

6. **The keys that still escape.** A key `MathField` returns `ignored` for bubbles to the ancestor `Focus` and is treated as a keystroke aimed at the paragraph. Three gates, all keyed off one flag `session.inlineMathFocused`:
   - `_LiveMarkdownSession._onKey` (line 224): `if (inlineMathFocused) return KeyEventResult.ignored;` as the very first line, *above* the `isAltXChord` check — otherwise Alt+X rewrites the code point at the host caret while you are inside an equation;
   - `app_shell._onKey`'s `if (editable)` block (~line 385): it fires Ctrl+B/I/U, Ctrl+1..5 and the marker ladder whenever `app.activeEditor != null`, which it is while a paragraph is open — so **Ctrl+B while typing an inline equation bolds the paragraph** today. Gate it on `_editableFocused()` resolving to a `MathField` (the function at line 145 already recognises one; it needs to *report which*, not just yes/no);
   - the Escape ladder in the same handler reaches `app.editingBlockId != null` and calls `select(null)`, deselecting the paragraph, *and then* `MathField`'s Escape also runs `onExit`. Same gate: while an equation holds focus, Escape means "leave the equation" and nothing else.

7. **Tab.** `MathField` returns `ignored` when every box is full (`math_field.dart:198`), and Flutter's traversal then moves focus out of the equation *and* out of the paragraph. `EquationEditor` converts an ignored Tab into `onExit(MathExit.right)`. Tab out of a full equation means "leave to the right" — which is what it already means in the block.

### B.3 Overflow — already broken today, and fixed here

Measured in the same probe run: at 40 extra characters the atom clamps to the field width and `A RenderLine overflowed by 112 pixels on the right`. The read-only `InlineMathAtom` overflows identically today (the earlier probe measured 96 px at a 150 px box), so this is not introduced by in-place editing — it is v0.18 §14.6's first open item, made reachable by typing.

Four levers, all of which the block editor already has:

- `_SourceSpan` gets a real `width:` for maths, so `_dimOf` (line 779) stops reporting `Size(0, fs)` and the wrap predictor puts the break in the right place;
- `EquationEditor` wraps its `OnoteMath` in `SingleChildScrollView(scrollDirection: Axis.horizontal)` inside a `ConstrainedBox(maxWidth: constraints.maxWidth)` — the exact shape of `math_block_view.dart:239`, now written once. Overflow becomes structurally impossible at both sites;
- `onWidthWanted` → block: `_growToFit` up to `_kMaxMathWidth = 900`; inline: `controller.requestExtraWidth` → `text_block_view` widens `block.w` (clamped 80..4000, `autoWidth = false`), the seam in-flow images already use;
- read mode: `FittedBox(fit: BoxFit.scaleDown)` around `InlineMathAtom`'s `OnoteMath`, which also closes "`FittedBox(scaleDown)` in read mode is dead code" from §14.6.

### B.4 Caret crossing

Today the caret crosses `$x^2$` in **two** steps (9→5 by `_snapOutOfHiddenMarkers`, then 5→4), and offset 5 sits between the `$` and the `x` — visually on the equation's left edge. With in-place editing that intermediate offset acquires a meaning: **offset `start + 1` *is* "inside this equation"**. Arrow-Left from `end` therefore calls `enterInlineMath(…, MathCaret.end)` and returns handled; the `MathField` owns Left from then on; a further Left at the equation's own start returns `MathExit.left` and the caret lands at `start`. Symmetric for Right. `_snapOutOfHiddenMarkers` keeps its job for `**bold**` and stops special-casing maths.

### B.5 Backspace

`_lineRuns` records a math run as `(start: m.start+1, end: m.end, openLen: m.end-m.start-1, closeLen: 0)` — so `innerStart == innerEnd` and `markerAwareDelete` `continue`s past it (line 397). Measured consequence: one Backspace deletes the closing `$` and the paragraph reverts to `aaa $x^2 bbb` — the exact defect class `markerAwareDelete` exists to prevent for `**bold**`.

Fix: `_MdRun` gains a `kind`, and `markerAwareDelete` gets an explicit maths rule ahead of the marker rules — **Backspace at `end` opens the equation with the caret at its end; Delete at `start` opens it with the caret at its start**, returning `null` (no text edit) and calling `enterInlineMath` instead. That is §7's "Backspace from the right steps *into* it (Q3)", now buildable because there is somewhere to step into.

## C. The empty state — no `$$` on screen, ever

### C.1 What the student sees

Alt+= in a paragraph puts, **at the caret, on the sentence's own baseline**, the same empty-slot chip they already see inside a half-filled fraction: `MathTexCtx.activeSlotTex` (`math_tree.dart:497`) — a `\square` in the accent colour on the accent tint — with the caret rule in front of it. Nothing else appears: no card, no 420 px panel under the paragraph, no dollars.

It is deliberately *not* a wide grey "Type equation here": OneNote can afford that because its equation is on its own line, and mid-sentence a four-word chip would shove the paragraph apart. The tint box is the affordance the editor already teaches, in the only place a student has already seen it, and the Maths tab is open at that moment saying what the buttons do.

The **block** empty state is unchanged: `math_block_view.dart:258–271` already draws "Empty equation — click to edit" with the ∑ icon, and a block has room for it.

### C.2 How it is stored while empty

**Two code units, `$$`, at the caret — but never drawn as source.**

Not because that is nice: because caret arithmetic requires it. Every `_SourceSpan` the controller emits stands for at least one buffer character; a zero-source placeholder would still insert Flutter's own U+FFFC into the laid-out paragraph and shift every offset after it by one, breaking the invariant the entire live editor rests on ("visible and source offsets have never diverged and still do not", `live_markdown_controller.dart:50–55`).

### C.3 How the live editor knows to draw it

`lib/markdown/md_syntax.dart`, two alternatives ahead of `_math` (line 117), both classified `MdInline.math`:

```dart
const String _mathDisplay = r'(\$\$([^$\n]*?)\$\$)';  // both pairs consumed
const String _mathEmpty   = r'(\$\$)';                // inner = ''
```

registered in `_order` before `MapEntry(MdInline.math, 2)`. Then:

- `live_markdown_controller` math branch: `c.inner.isEmpty` → the chip; otherwise the atom or the editor. `_lineRuns` records it identically (`openLen: len - 1, closeLen: 0`), so the caret crosses it in one step and Backspace at its edge deletes it whole;
- `md_render.dart:676` (read mode): `c.inner.isEmpty` → emit nothing. An empty equation that somehow survives to a saved note is invisible, not two dollar signs;
- `_mathDisplay` also closes the "stray dollar on each side of a pasted `$$E = mc^2$$`" finding, because both pairs are now inside the match instead of only the inner one.

### C.4 Clicking away

`session.closeInlineMath()` — the one exit path from §B.5 — ends with:

```dart
if (_mathEditor?.isEmpty ?? true) controller.replaceMathAt(start, end, '');
```

`replaceMathAt` already writes `''` for empty LaTeX (line ~302) and already accepts `start == end`, so both dollars come out and the caret lands at `start`. This is the inline twin of `math_block_view._handleExitTransition`'s post-frame `removeBlock`, and it is the leak the investigation found: today Alt+= then Escape leaves `$$` in the note **permanently**, because `_editInlineMath.onDone` (line 164) is just `_focus.requestFocus()`.

`startInlineMath` (`live_markdown_engine.dart:121`) loses its `_focus.context.findRenderObject()` anchor entirely — there is no card to anchor. It writes `$$`, sets `_mathStart = start`, and returns; the placeholder mounts the editor at exactly the right place because it *is* the span. That also kills "Alt+= drops a 420 px card under the entire paragraph, nowhere near where you were typing".

## D. Paste that never shows source

Four holes remain, and one of them is new.

### D.1 The double paste — new, and in the working tree now

`app_shell._onKey` (line ~454) calls `_pasteMathsIntoEditor()` and then `return false; // never swallow the keystroke`. So the field's own paste inserts the raw clipboard text **and** the async `_pasteMathsIntoEditor` inserts the wrapped form. Pasting `$\frac{1}{2}$` into a paragraph inserts it twice.

The decision cannot be made synchronously in the key handler, because reading the clipboard is a `Future`. **Fix: intercept where the text actually arrives.** New `lib/editor/math_paste_formatter.dart`:

```dart
class MathPasteFormatter extends TextInputFormatter { … }
```

It diffs `oldValue`/`newValue`; when the inserted run is longer than one character and `MathClipboard.looksLikeMaths(run)`, it substitutes `MathClipboard.wrapInline(MathClipboard.unwrap(run))`. Added to the live field's `inputFormatters` beside `WrapSelectionFormatter` — the seam this codebase already uses (`math_block_view.dart:307`). Synchronous, no clipboard read, and it covers drag-and-drop and middle-click paste too. **Delete `_pasteMathsIntoEditor` and its call.**

### D.2 `insertSource`'s character fallback still escapes backslashes

`math_editor.dart` ~447 still ends with `for (final ch in source.split('')) insertChar(ch)`, and `math_tree.dart:561` maps `\` → `\backslash ` and `{` → `\{`. So an unparseable paste becomes *typeset* backslashes which then re-parse cleanly — there is no way back. 22 of 79 realistic constructs landed here.

Fix: `insertSource` returns an outcome instead of `void`.

```dart
enum InsertOutcome { placed, notMaths }
```

When neither the linear nor the LaTeX reading parses, insert **nothing** and return `notMaths`. `EquationEditorState._paste` then:
- equation empty → switch to the LaTeX view with the source intact (the same honesty rule `MathEditor.open` already follows, lines 42–47);
- equation not empty → leave it untouched and say so in the status bar: *"That doesn't look like maths this editor can hold — it's still on your clipboard."*

Never escape a backslash-bearing paste into the tree. Also: `insertSource` should call `deleteSelection()` first, so pasting over a highlight replaces it the way typing already does.

### D.3 Canvas paste

`lib/canvas/media_drop.dart`, the `Formats.plainText` branch (~line 306), before building the text block:

```dart
if (MathClipboard.looksLikeMaths(text)) {
  final b = app.addBlock(Block(type: BlockType.math, x: at.dx, y: at.dy,
      content: {'latex': MathClipboard.unwrap(text), 'display': true}));
  app.select(b.id, edit: true);
  return PasteResult.text;
}
```

One branch, one call.

### D.4 Cut a math block, paste it back

`app_shell._pasteFromSystemOrBlocks` (line ~1035) awaits `pasteOntoCanvas` first and reaches `app.pasteBlocks()` only on `PasteResult.nothing`. The equation's own Ctrl+C has just put `$\frac{1}{2}$` on the system clipboard, so the cut block never returns — a text block full of LaTeX does. (`cutSelectedBlocks`, `app_state.dart:5283`, only fills `_blockClipboard` and never touches the system clipboard, and nothing clears it.)

Fix: `AppState` stamps `int _blockClipboardAt = nowMs()` in `copySelectedBlocks` (line 5274). Split the read: `pasteOntoCanvas` gains a `probeClipboard()` that reports the kind without acting. Images and files keep priority — that ordering was chosen for screenshots and stays. When the only thing the system offers is **plain text**, the block clipboard wins if it is the more recent of the two.

### D.5 The grammar's two remaining refusals

- `$$…$$` in a sentence leaves a stray dollar each side — closed by `_mathDisplay` in §C.3.
- `$ x $` with padding spaces is refused outright, because `[^\s$\n]` guards both ends. Those guards are load-bearing: they are what stops *"coffee is $5 and lunch is $10 today"* becoming an equation (measured, and recorded in the comment at `md_syntax.dart:110–116`).

  **Decision: allow one space of padding on each side, but only when the inner run contains a backslash command.**
  ```dart
  const String _mathPadded = r'(\$ ([^$\n]*\\[a-zA-Z]+[^$\n]*) \$)';
  ```
  Money never contains a backslash. This is the same narrowness rule `MathClipboard.looksLikeMaths` already applies, and it is applied for the same reason: a false positive turns someone's prose into an equation, which is worse than a false negative.

## E. Selection inside an equation

> *"I also still cant highlight text, and when i cut it cuts all the content, id love to be able to highlight and cut only part of the equation."*

### E.1 The model — already right, keep it

A selection is **a contiguous run of siblings in ONE row** (`math_editor.dart:98–176`). Not a range over the tree: a run that started in a numerator and ended outside the fraction has no meaning to copy, cut or replace, and every operation on it would need a special case. Shift+arrow therefore steps *over* a structure rather than into it, so a fraction is taken whole — pinned: `typed('1/2')` + `extendBy(-1)` gives `selectionLatex == r'\frac{1}{2}'`.

Keyboard is done: Shift+←/→ (`extendBy`), Shift+Home/End (`while (extendBy(±1)) {}`), Ctrl+A (`selectAll`). Copy/cut/delete/overtype are done: `_copy` uses `selectionLatex`, Ctrl+X does `deleteSelection() ?? clear()`, and `backspace()`, `delete()`, `insertChar()`, `insertItem()` all call `deleteSelection()` first.

| Candidate | Result |
|---|---|
| `\fcolorbox{c}{c}{$run$}` | paints; costs **exactly 0.680 × fontSize in both width and height**, at 12/14/16/22/30 px, in text style and display style alike (= `2 × (\fboxsep 3pt + \fboxrule 0.4pt)` = 0.68 em) |
| `\colorbox{c}{$run$}` | lays out (142.8 × 30.3) and paints **nothing** — re-confirmed |
| `\fboxsep=0pt`, `\fboxrule=0pt`, `\bbox[c]{…}` | renderer **refuses** → `MathSourceFallback`. The padding cannot be removed |
| `\!`, `\kern-0.34em`, `\hspace{-0.34em}`, `\mkern-6mu` around the box | **silently ignored** — all four lay out at exactly 144.5 × 32.1, identical to no cancellation |
| `\smash{X}` | rewritten to `{X}` by `renderableLatex` — not a lever |
| `\textcolor{c}{run}` | costs **exactly nothing** (129.6 × 17.1 = baseline; a fraction 81.1 × 44.2 = baseline) |
| a fraction inside the box | **shrinks**: `a+\frac{1}{2}` is 81.1 × 44.2 plain, 89.4 × 41.1 boxed (text style inside the box), 96.0 × 59.1 boxed with `\displaystyle` inside |

Three consequences, and they are the whole design:

1. **Keep `\fcolorbox`** — it is the only fill that paints, and a colour change alone does not read as "selected".
2. **`MathTexCtx.selectionOpen` carries the style**: `\fcolorbox{tint}{tint}{$\displaystyle ` for `EquationPlacement.block`, `…{$\textstyle ` for inline. Without it a highlighted fraction physically shrinks the moment you select it (44.2 → 41.1 measured). `MathTexCtx` gains one field, set by `EquationEditor` from `placement`.
3. **Reserve the 0.68 em permanently.** `EquationEditor` wraps its `OnoteMath` in `Padding(EdgeInsets.all(0.34 * fontSize))` at all times, selection or not. Then the equation's outer box is the same size either way, and nothing outside it moves when a highlight appears — not the paragraph's line height, not the block's width, not the wrap prediction. Pin the constant as `kSelectionBoxEm = 0.68` in a test so a renderer upgrade that changes it fails loudly instead of silently reintroducing a jump.

   **What still moves, stated:** glyphs *after* the highlight shift right by 0.68 em inside the equation, because the padding is interior to the row and negative space is ignored. That is the single visible artefact and it is accepted.
4. **Suppress the caret rule while `hasSelection`.** `rowToTex` currently computes `caretHere` and `selHere` independently and can emit both; a text editor draws one or the other.

### E.3 How the pointer sets it

`MathField`'s gesture layer is one `onTap` that places the caret at the end (`math_field.dart:337`), with a comment saying true hit-testing needs geometry `flutter_math_fork` does not expose. That is true per-node. It is **not** true per-prefix.

**New file `lib/math/math_hit.dart`: `MathHitTable`.** For a row of `n` children it holds the laid-out width of each prefix `rowToTex(children[0..i])`, `i = 0..n`. `indexAt(double dx)` binary-searches it and returns the nearest child boundary.

**The table is built on pointer-DOWN, never per keystroke.** The equation cannot change while the button is held, so `n + 1` layouts happen once per gesture — a click is not a 60 fps budget — and the v0.19 rule ("an atom widget is built once per id, never per keystroke") is not touched. It is discarded on pointer-up.

That one table gives all four gestures:
- **click** → place the caret at the nearest boundary (today it jumps to the end);
- **drag** → `onPanStart` sets the anchor, `onPanUpdate` sets `caretIndex`; the run is contiguous by construction because both ends are indices into the same row;
- **Shift+click** → extend from the existing anchor;
- **double-click** → the child under the pointer, whole, which for a fraction selects the fraction.

Accuracy limit, stated: TeX spaces a trailing binary `+` differently from the same `+` between two operands, so a prefix width can be a few px off. It does not matter — the result snaps to a child boundary, and a few px only ever picks the neighbouring boundary.

### E.4 Selection that spans the equation from outside

Dragging in the paragraph across an inline equation selects the raw `$x^2$` and Ctrl+C puts `$x^2$` on the clipboard. With `MathClipboard.wrapInline` on the copy side and `MathPasteFormatter` on the paste side, **that is now correct by construction** — it round-trips back into an equation. Pin it rather than change it.

## F. The order of work

Each step ships on its own.

**1 — Extract `EquationEditor`; both hosts use it. No user-visible change.**
`lib/math/equation_editor.dart` new; `math_block_view.dart` shrinks to read mode, the empty husk, undo coalescing and the model commit; `_InlineMathCard` keeps working, now as a thin holder.
*Risk: low.* The one real hazard is `ActiveMathEditor.owner` identity — `clearActiveMath` guards against a late teardown unregistering its successor, so `owner` must become the `EquationEditorState` and both hosts must stop passing `this`. The inline site gains the calculator here, which is the first visible proof the sharing works.

**2 — Paste: D.1–D.5.** Independent of everything else.
*Risk: medium.* D.5 touches `mdInlineRe`, which every rendered character goes through; guarded by `live_hidden_markers_test` and by the controller's coverage fallback. D.1 moves the interception point; the hazard is a formatter firing on ordinary typing, removed by the "inserted run longer than one character" guard. D.1 also fixes a double paste that exists in the tree *today*, so it is the most urgent item in this plan.

**3 — In-place editing (B) and the empty state (C), together.** They are one change: C's chip is the same placeholder B mounts. The card dies here.
*Risk: highest in the plan.* The mechanism is measured; what is not is the interaction with the shell's chords. Mitigation is that all three gates read one flag, `session.inlineMathFocused` — `_LiveMarkdownSession._onKey`, `app_shell`'s `if (editable)` block, and `app_shell`'s Escape ladder. Test first, in `test/inline_math_inplace_test.dart`: Ctrl+B inside an equation must not bold the paragraph; Escape must not deselect the block; Tab out of a full equation must land the caret after it, not in another widget.

**4 — Overflow and growth (B.3).** `_SourceSpan.width` for maths, the shared scroll view, `onWidthWanted` in both hosts, `FittedBox` on the read atom.
*Risk: medium.* `_dimOf` feeds the wrap predictor; a wrong width moves line breaks in paragraphs that contain no maths at all. Guarded by the existing wrap tests, and by the fact that a width is only supplied where it was previously `0`.

**5 — Selection drawing (E.2).** Reserve 0.68 em, style token inside the box, caret suppressed while highlighted.
*Risk: low.* Every number is already measured; the step is three small edits plus a constant to pin.

**6 — Pointer selection (E.3).** `MathHitTable`, click-to-place, drag, Shift+click, double-click.
*Risk: medium.* The prefix table's boundary accuracy, bounded as in E.3. Ship the click-to-place half first — it fixes "clicking an equation puts the caret at the end no matter where you clicked", which is its own reported annoyance — then the drag.

**7 — `EquationSourcePanel`** for the inline LaTeX escape hatch.
*Risk: low.* It is the card's corpse, reduced to the one job that genuinely needs platform text input.
