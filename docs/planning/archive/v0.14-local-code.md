# v0.14 — Local code: write and execute JS, SQL, like a Jupyter notebook

> PLANNING.md: "Write and execute code like JS, SQL, etc — Similar to
> juniper notebook." The order of sections is the order of decisions: the
> sandbox rule first, because it is the one that cannot be retrofitted.
>
> **Status: Phases 1 and 2 shipped 2026-08-10** (`code/code_runner.dart`,
> Run button + Ctrl+Enter on `sql`/`js` cells, output persisted in the
> block). Two deviations from the plan as written, both recorded in the
> runner's library comment: flutter_js's `getJavascriptRuntime()` enables a
> fetch bridge BY DEFAULT, so the engine is constructed directly without
> it; and the five-second bound is enforced by killing the run's isolate,
> which a stuck NATIVE call (one pathological sqlite step, one infinite JS
> eval) survives as a burning thread until it completes — closing that
> needs the engines' interrupt hooks, which the current bindings do not
> expose. "A stranger's cell can waste CPU and nothing else" holds; the
> hard five-second bound on the waste does not yet.

## 0. What "good" looks like

A code block with a **Run** button. Output appears under the source —
text, an error, or rows rendered as a table — and stays there, so the page
reads like a finished notebook without re-running anything. Re-run
replaces the output. `Ctrl+Enter` runs the block you are editing, exactly
as Jupyter's muscle memory expects. A student uses it for: crunching a CSV
they just dropped in, checking an algorithms answer, keeping a worked
example next to the lecture slides it belongs to.

## 1. The rule that everything hangs on

**Note content is untrusted.** A shared notebook, a git-joined notebook, an
imported file — "can contain anything a stranger wrote" is already this
project's threat model, and executable cells are where that stops being
hypothetical. So the sandbox is not a feature of the runner; it is the
selection criterion FOR the runner:

1. **Nothing ever runs without a click.** Not on page open, not on sync,
   not on import, not "Run All" as a page-load behaviour. A pulled change
   to a code cell arrives as text.
2. **Engines with no ambient authority.** The runtime must have no file,
   network, process or environment access UNLESS we hand it a bridge — and
   v1 hands it nothing but data that is already on the page. This is why
   "just shell out to node/python" is rejected outright: a system
   interpreter's default authority is the whole machine.
3. **Bounded by construction**: wall-clock limit (~5 s, engine interrupt),
   memory cap, and an **output cap** (~64 KB, truncated with a notice) —
   the last one because a print loop must not manufacture a 100 MB block
   that then syncs to every device.
4. The invariant, stated for the release notes: *running a stranger's cell
   can waste five seconds of CPU, and nothing else.*

Run happens on an **isolate**, so Stop genuinely kills a runaway loop
instead of freezing the window with it.

## 2. Phase 1 — SQL, because the engine already ships

SQLite is in the app today. Zero new dependencies, and it lands the other
half of a separate ask ("Excel like spreadsheet or **SQL like table**"):

- A `sql` code block runs against a **fresh in-memory database** per run.
- **Every table block on the page is mounted as a real SQL table** before
  the run — named from its header row's first cell (sanitised), `t1…tn`
  as fallback. The CSV/xlsx you dropped this morning is instantly
  queryable: `SELECT unit, AVG(mark) FROM marks GROUP BY unit`.
- `SELECT` results render as an output table, with an **"insert as table
  block"** action — the loop back onto the page (and later, the feed for
  charts).
- Sandbox: in-memory DB, nothing attached, `PRAGMA` surface restricted,
  progress-handler timeout. SQLite alone cannot reach the disk we don't
  give it.

## 3. Phase 2 — JavaScript, via an embedded engine

- **QuickJS embedded** (the `flutter_js` package, or its underlying
  bindings — evaluate at build time; adds a small native lib per
  platform). QuickJS has no DOM, no `fetch`, no `require` — its world is
  exactly the globals we install:
  - `tables` — read-only copies of the page's table blocks as arrays of
    objects keyed by header;
  - `print(...)` / `console.log` — captured to the output pane;
  - the completion value renders like Jupyter's `Out[n]`.
- Interrupt-handler timeout, engine memory cap, same output cap.
- **No network, no filesystem, no timers** in v1. Every later bridge is a
  security decision made one bridge at a time, never a capability the
  engine came with.

## 4. Data model — additive on the existing code block

`BlockType.code` already stores `{language, source}`. Add, additively:

```jsonc
{ "language": "sql",
  "source": "SELECT …",
  "output": { "kind": "text" | "table" | "error",
              "text": "…",            // text/error
              "cells": [[…], …] },     // table rows, header first
  "ranAt": 1786300000000 }
```

- **Outputs persist and sync** — the page reads like a notebook without
  re-running, which is half the point. The output cap is what makes this
  safe for the op log.
- Old builds: unknown content keys round-trip untouched (the same contract
  every recent block change has leaned on); they render the source as
  today and simply don't show output.

## 5. Phase 3 — the extensions, in the order they earn themselves

1. **Page session**: variables shared across a page's cells, `Run all`,
   a reset button — Jupyter's actual model. Needs a visible "session
   state" indicator; deferred because standalone cells are reproducible
   by construction and sessions reintroduce "works after I ran that other
   cell first".
2. **Write-back**: `writeTable(name, rows)` mutating a page table —
   behind a per-run confirmation, because it crosses the compute/mutate
   line that keeps v1's story clean.
3. **Chart output** — shared design with the Tables item's graphing ask:
   one chart-rendering component fed by either a table block or a cell's
   output.
4. **Other languages** (Python…) — now explicitly asked for: "it could
   even just be ones that the user already has installed on their system
   if we can access that in a sandboxed way." The honest shape: detect
   installed interpreters, and run them under REAL OS sandboxing — a
   restricted-token/AppContainer child on Windows, bubblewrap/landlock on
   Linux, sandbox-exec on macOS — because a system interpreter's default
   authority is the whole machine and a prompt saying "trust this?" is not
   a sandbox. Per-notebook trust grant ON TOP of the OS sandbox, not
   instead of it. This is a real project per platform; design it when the
   SQL/JS cells have earned the appetite.

## 6. Sandbox invariants, as tests

- A cell that calls any file/network/process API fails to resolve the
  symbol (probe each bridge surface explicitly).
- `while(true){}` and a recursive CTE both come back as a timeout error in
  ~5 s, and Stop returns the UI instantly.
- A print loop's output arrives truncated at the cap with a notice.
- Opening / syncing / importing a page containing a code cell executes
  nothing (assert by counter).
- The output of a run on device A renders on device B without running.
