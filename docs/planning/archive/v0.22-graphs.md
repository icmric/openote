# v0.22 — Graphs

> The owner's brief: *"Graphs would be great too, put some time into planning
> this, i dont know how complex we could go with this, but if we can graph
> realy complex stuff (like at minimum 2d equations, but being able to graph
> more complex 3d functions would be increidble), which also means we need to
> think about what it looks like, how people will insert them and deal with
> them, all that sort of stuff."*

Every number below was **measured** by a probe against this codebase during
the 2026-08-20 research pass, not estimated. Where a claim is an opinion it
says so.

---

## 0. The answer to "how complex can we go"

**More than OneNote, and 3D is real** — but not in that order, and the reason
is not difficulty.

A rotatable 3D surface costs **0.60 ms of Dart per frame at 60×60**, and
5.2 ms at 150×150 — 3.6% of a 60 fps budget, in pure Dart, with no new
dependency and no SDK upgrade. It is roughly 400–600 lines. So "3D is too
hard" is simply false, and this plan says so plainly.

3D is nonetheless **second**, for three reasons: 2D is what beats OneNote and
2D is not shipped; the parts of 3D that make it *useful* (contours,
cross-sections, labelled axes) are a second feature riding on the first; and
z=f(x,y) is first-year university, while y=f(x) is Year 10 and up. §6 lists
the six things the 2D work must get right so 3D lands as an added file rather
than a rewrite.

## 1. What is actually in the way (all measured)

The input side is **already done** and nobody expected that: `y = x^{2} - 4x
+ 3` typed in the visual editor parses into the tree and projects cleanly to
`y=(x)^(2)-4x+3`. The equation editor can already *type* almost everything a
2D grapher needs. The feature is ~90% evaluator and renderer.

What blocks it today, in the order a student would hit it:

| # | Measured behaviour | Where |
|---|---|---|
| 1 | **0 of 9** realistic `y = …` equations reach the evaluator at all — every one dies on `if (src.contains('=')) return err('not an expression')` *before* the variable question is asked | `evaluate.dart:66` |
| 2 | `x` is unknown: there is no variable environment | `evaluate.dart:249` |
| 3 | `2πx` → `unknown "pix"`, `xy` → `unknown "xy"` — the maximal-name rule eats implicit products between named things. The **first** thing a student graphs fails, naming a symbol they never wrote | `_parseNameOrCall` |
| 4 | **`sin(x)^2` evaluates as `sin(x^2)`** — measured `sin(2)^2 = −0.7568`, i.e. sin 4. A calculator shows one wrong number; a graph shows the wrong *shape*, which is far more damaging | `evaluate.dart:251` |
| 5 | `(-8)^(1/3)` → `undefined`, so `y = x^(1/3)` plots nothing left of the origin and reads as "the graph is broken" (`cbrt` already has the correct odd-root branch; `^` never got it) | `evaluate.dart:171` |
| 6 | `θ`, `≤`, `≥`, piecewise and subscripts are vetoed one stage **earlier**, in the projection — so an evaluator-only fix silently keeps failing on them | `math_linear_projection.dart` |
| 7 | No comma in the grammar at all: no points, no `max(a,b)`, no data | `evaluate.dart` |

Items 3, 4 and 5 are bugs **today**, in the calculator, independent of graphs.

## 2. The one decision everything rests on: compile once

`_Parser.parseExpression()` returns a `double`. To get f(x) at 900 x-values
the only available move is to rebuild the source string and re-parse, 900
times. Measured, for 3200 samples of one curve:

| | textual re-parse | compiled closures | speedup |
|---|---|---|---|
| `x^2` | 2.898 µs/sample | 0.108 µs/sample | 26.8× |
| `sin(x)` | 2.008 | 0.042 | 48.4× |
| `sin(x)exp(-x/4)+sqrt(abs(x))` | 5.492 | 0.158 | 34.9× |
| 3200 points, heavy | **14.50 ms** | **0.438 ms** | 33× |

14.5 ms is **87% of a 60 fps frame for one curve**. Textual substitution is
not a slow fallback, it is a non-starter — and 3D (which re-samples a whole
grid) cannot work at all without this.

**So: `_parse*` returns a closure tree instead of a value.**
`typedef Fx = double Function(List<double> env)`, with names resolved to
positional slot indices at compile time — a `List<double>`, not a `Map`.
`evaluateLinear(src)` becomes a one-line wrapper (`compile(src, const [])
.call(const [])`), so the calculator's 40+ existing expectations stay green
and there is **one grammar and one bug surface**. Going from `['x']` to
`['x','y']` for 3D is then a length change, not a redesign.

New file: `lib/math/compile.dart`.

## 3. What a student does — the whole feature, keystroke by keystroke

A student is writing a sentence and presses **Alt+=**. The equation opens
where the caret is; the Maths tab appears, already selected.

* **y** → an italic y. Nothing offered — no relation yet.
* **=** → `y=`. Nothing offered — the right-hand side is empty.
* **x** → `y=x`. **First graphable moment**: one relation, `y` on the left,
  one free letter on the right. A small live preview lights up in the Maths
  row showing a straight line.
* **^** → an empty superscript box opens. This is *unfinished*, not
  *ungraphable*: the preview keeps its last picture but goes **dim and
  inert**, so nothing blinks and nothing lies.
* **2** → `y=(x)^(2)`. The preview goes live with a parabola.
* **− 3** → `y=(x)^(2)-3`. The preview follows.
* **Click the preview** → a graph block appears flush under the paragraph,
  selected. The equation edit ends and the Maths tab retires. **One Ctrl+Z**
  takes the graph back and leaves the equation exactly as written.

### Where the preview lives — and why this is not the mistake we just undid

The research proposed reusing the calculator's answer slot, and measured that
the Maths row has **5.25 px of headroom** (1144.75 px against a 1150 px
guard) — no new button fits. That slot has since been **removed**, because
the owner found an answer at the top of the window unintuitive and it now
lands at the caret instead. That frees its 84 px, which is exactly what the
graph preview wants.

The distinction is worth stating so it is not "re-fixed" later: an **answer is
a value**, and a value belongs in the equation the student is writing. A
**graph is an object**, and it cannot go inside a line of maths — it has to
be somewhere, and beside the equation that produced it is the least
surprising place. A live miniature is a *preview of the thing you are about
to make*, not a readout of a result.

### Every other route in

2. **Right-click an equation → "Graph this."** Two clicks, discoverable, and
   the only route that can **explain a refusal** — a menu item can be shown
   disabled with a reason where a chip can only be absent.
3. **Insert ▸ Graph.** Inserts an *empty* graph: faint axes and a focused
   `y = ▢`. The Desmos entry, for a student who hasn't written anything yet.
4. **Canvas right-click → "New graph here."** Every other block type is
   reachable this way; a gap here reads as a missing feature.
5. **Alt+G.** With an equation focused it graphs it, otherwise it drops an
   empty graph at the viewport centre — the two-branch shape Alt+= already
   has. Documented in the keyboard map, or it isn't done.
6. **Paste.** Nothing new: pasting `y=x^2-3` already lands a maths block,
   which then offers its own preview.

### The block on screen

**Not selected — a figure, not an app widget.** A faint square grid; axes with
the origin marked and "nice" 1/2/5×10ᵏ tick numbers; x and y at the axis
ends; the curve; and **the equation drawn top-left in real notation**
(`OnoteMath`, ~13 px). No buttons at all. That caption is what makes the
block readable in print, in a shared portal, and by the student six weeks
later.

**Hover / selected** — the usual block chrome, plus a quiet row bottom-left
*inside* the plot: `⊕ ⊖ Fit`. Three icon controls with plain tooltips —
**"Show more of it", "Show less of it", "Fit the curve in"**. No student is
ever shown the words "x-range" or "domain".

**Being edited** — the equation line becomes an `EquationEditor` docked under
the plot, so editing a graph's equation is bit-for-bit the same experience as
editing any equation, with the Maths tab, the palette and the `=` calculator.
The owner's rule, verbatim: *"the exact same experience … all using the same
code."*

**Size:** `w: 360` (matching every other maths insertion), `h: 264`. Both are
exact multiples of the 24 px page grid, so a snapped block sits flush. **No
auto-size** — a graph is a picture with an aspect ratio. Storing a real `h`
also buys the height handle for free. Resizing changes the *paper*, not the
window: the x-range is held and y follows the new aspect, so a stretched
graph never distorts the curve.

A graph must **not** be an `_editableType`, or one click on the curve opens
an editor instead of selecting the block.

### Interaction: v1 and after

**v1** — pan (drag), zoom (wheel / ⊕ ⊖), **Fit**, and that is deliberately
all. **v1.1** — *trace*: drag along the curve and a dot with its coordinates
follows. This is Desmos's single most-loved feature for students and the
cheapest big win once sampling exists. **Later** — marked intercepts and
turning points, a second curve, hide/show.

The gesture conflict with the canvas's own pan/zoom is real and has a named
mechanism already in the codebase (`claimedPointers` / the `_bodyDragMoves`
opt-out); the graph claims the pointer only when the block is selected, so a
drag on an unselected graph still pans the page.

### When it can't be graphed

The pipeline already refuses cleanly; the rule is that **the app never
guesses and never shows a broken graph**. No relation (`2+3`) → no offer, the
`=` calculator answers instead. Two free letters (`y = mx + c`) → the message
names them: *"m and c need values before this can be drawn"* (and that
message is the seam sliders arrive through later). A matrix, a words box, a
subscripted name → no offer at all.

### Storage — three keys, all readable

```json
{ "type": "graph", "w": 360, "h": 264,
  "content": {
    "latex": "y=x^{2}-3",
    "from": "blk_7f3",
    "view": {"x0": -10, "x1": 10, "y0": -8, "y1": 8}
  } }
```

* **`latex` is the truth**, canonical, the same key and rule maths blocks
  use. The linear form is derived, never stored — two copies of one fact is
  drift.
* **`from` is a hint that may dangle.** A pointer-only design is broken by
  two shipped paths: `duplicateBlock` deep-copies content under a new id
  without rewriting references, and `pasteBlocks` re-mints ids. So the graph
  **owns** its equation. Consequences, all good: self-contained for export
  and portals, can never render broken, copy/paste/duplicate/move-page all
  just work, and undo is atomic because undo is a whole-page snapshot — the
  equation and its graph revert together in one step.
* **`view` absent means auto-fit**, which is self-healing: change the
  equation and the window follows. It appears only once the student pans or
  zooms — they chose it, so it is kept even if the curve later leaves the
  window, and the plot then says *"the curve isn't in this window"* beside
  the Fit button that fixes it.
* **Nothing computed is stored** — no samples, no PNG, no colours. Everything
  redraws from `latex` + `view`, which is what keeps it right in dark mode,
  in print, and at any zoom.

`BlockType.graph` is additive and safe: the `rawType` contract means an older
build shows "Unsupported block: graph" and round-trips the content verbatim,
the same guarantee that made `flashcard` and `board` safe to add. **One**
`graph` type, never `graph2d` + `graph3d` — the enum is a wire format, and
the dimensionality is content.

## 4. Drawing it correctly

The parts that separate a real grapher from a toy, each with the technique
named:

* **Sampling** — uniform seed at one sample per *device* column, then
  recursive bisection where the curve bends more than half a pixel. Note the
  canvas transform: block painters draw in page units, so the sample count
  must include `controller.scale` or a zoomed-in graph is visibly polygonal.
* **Asymptotes** — the break test must be **geometric**, not `isInfinite`:
  `tan(pi/2)` measures 1.63e16, a finite double, so nothing ever fires. Break
  the path when a step's slope explodes relative to its neighbours; otherwise
  `y = 1/x` draws a vertical line through the discontinuity that a student
  will read as part of the curve.
* **Domain gaps** — a NaN run collapses to **one** break, and refinement
  stops inside it (measured: 8417 wasted probes without that rule).
* **Clamping** — huge values are clamped before they reach `ui.Path`, and the
  window itself is sanitised: no NaN, no zero-width, no inverted ranges.
* **Auto-range** — seed on [-10, 10], find features, then choose y by
  **percentiles**, not min/max: one asymptote otherwise flattens the whole
  curve to a horizontal line.
* **Repainting** — one `Path` with breaks, inside a `RepaintBoundary`, with a
  real `shouldRepaint`.

## 5. Ranked by who actually needs it

| Kind | Who | v1? |
|---|---|---|
| `y=f(x)`, one curve | everyone | **v1** |
| Several curves on one axes | Year 10 transformations, simultaneous equations | **v1.1** — a list in `content`, no new maths |
| Scatter / data + line of best fit | Year 10 stats, uni labs, **industry's #1** | later — needs the comma and a data source; Openote already has tables and CSV import, so "graph this table" is one hop and nobody in the category offers it |
| Implicit (`x²+y²=25`) | Year 10 in AU — circles are named in the curriculum | later — marching squares |
| Inequalities / shading | Year 10–11 | later — needs relational operators |
| Piecewise, domain restriction | Year 11–12 | later — falls out of inequalities free |
| Parametric | Year 12, physics | later |
| Polar | Year 12 specialist | later — `θ` is vetoed two stages up |
| **3D surface `z=f(x,y)`** | first-year university, industry | **§6** |
| Slope fields | uni ODEs | later — the *cheapest* exotic kind: a short segment per grid point, no root finding at all |
| Complex plane | Year 12 specialist, EE | **skip** — the only kind needing a type change through every node of the evaluator |

## 6. 3D, honestly

**Verdict: later, not skip.** Measured, pure Dart, no dependency:

* a rotatable 60×60 surface: **0.60 ms/frame**; 150×150: **5.2 ms**;
* flat `Float32List` arrays, a 0.03 ms bucket sort for depth order, and
  **one `ui.Vertices` draw call**;
* the single decision that makes or breaks it: one `ui.Vertices`, **never**
  one `Path` per quad — measured **14× slower**, and it blows the frame at
  100×100;
* painter's algorithm is not a compromise for a height field, it is exact; a
  Dart z-buffer is the trap.

Every dependency option was checked and rejected: everything predating 2026
is unmaintained, and the one live option fails the ADR-0004 rule (own a few
hundred lines rather than take a dev-channel dependency). The WebGL-in-a-
webview escape hatch fails on the block model, not on the graphics.

An opinion worth recording: **a rotatable surface on its own is a toy.** What
makes 3D useful to a student is contours and cross-sections — the level
curves are how you actually read a surface. Budget for those or don't start.

**The six things 2D must do now** so 3D is an added file: the compiled
expression layer with a variable *list*; one `BlockType.graph`; an
arity-carrying function table; the window/camera state kept in `view`; the
sampler separated from the painter; and the gesture claim written so a
rotate-drag can reuse it.

## 7. Order of work

1. **The four measured bugs** (§1 items 3, 4, 5 and the projection vetoes).
   They are calculator bugs today and they would each become a *visibly wrong
   curve* tomorrow. Ship them first, independently.
2. **`compile.dart`** — the closure layer, with `evaluateLinear` reduced to a
   wrapper. No user-visible change; every existing test must stay green.
3. **The `=` split and the graphable test** — what makes an equation offer a
   graph, and what makes it refuse with a reason.
4. **`BlockType.graph`**, storage, and every export/read-only path that
   enumerates block types (a graph missed in one of them silently vanishes
   from a PDF).
5. **The painter**: sampling, breaks, auto-range, axes, ticks.
6. **The routes in**, preview chip first.
7. **Pan/zoom/Fit**, then **trace** (v1.1).
8. **3D**, per §6.

## 8. The vision amendment this needs

`docs/specs/12-math-input-spec.md §1` and `evaluate.dart` both record
graphing as a **Vision §9 non-goal**. That has to change explicitly before
step 4, not quietly during it.

The honest framing: the same document already made this call once. The
calculator was built precisely because OneNote paywalls its Math Assistant
behind M365 Education, and the cost was a few hundred owned lines. Graphing
is the same move with the same justification — and the measured openings are
wide: OneNote's graph is **a dead screenshot, not a live object**; it takes
**six steps and a side pane** to produce one; and no note-taking app in the
category has a native live grapher at all.

**This is the owner's call to make, and it is the only thing in this plan
that is not a straightforward build.**
