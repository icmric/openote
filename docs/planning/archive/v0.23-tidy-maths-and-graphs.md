## What still constrains the next round

### The object row, and the bar a face has to clear

> Bands A and B belong to the student. Band C belongs to the page — and the
> page lends it to an equation while the student is writing one.

Chrome is **32 + 44 + 36 = 112 px in every state of the app**. Nothing grows,
nothing shrinks, nothing re-points, and the canvas box never moves. That is
what makes "don't move the user" a property of the layout rather than a
promise someone has to keep.

- **Band A** — three permanent tabs: Home, Insert, Draw. Plus a *badge* while
  an equation is open — a pill that says `ƒ Equation`, never underlined, and
  **not clickable**, so it cannot be misread as a fourth tab.
- **Band B** — the command row. If you were on Home when you started an
  equation, Home is what you are still looking at.
- **Band C** — the object row. At rest it carries the page's own controls
  (background, canvas/paper, snap, zoom); while an equation is being written
  it carries `MathBar` **verbatim**. Only its contents cross-fade, 90 ms,
  opacity only.
- **Parity, mechanically** — `EquationFace`'s constructor takes an
  `ActiveMathEditor` and primitives only: no `AppState`, no `Block`, no
  `BlockType`, no placement. A block equation and one in a sentence cannot be
  told apart, because nothing downstream is given anything to tell them apart
  with. **Any new face must keep this shape**, or principle 4 goes back to
  being a promise.
- **Insert** — one catalog (`insert_catalog.dart`) rendered twice: as the
  ribbon and as the right-click menu. The ribbon is one row of thirteen, each
  with its word, in `kRibbonOrder`; the menu shows the ten of them whose
  `onMenu` is true, as three short columns. Three are ribbon-only and each
  says why beside itself.

  This went the other way for one release — ten items, three groups, four
  wordless icons — and came back: *"i dont love the new menu stuff though, i
  think we go back to what we had before."* The cost of the row as it stands
  is real and measured: thirteen labelled buttons is **1704 px** against the
  ~965 px a 1280 window leaves with the navigator open, so about five of them
  are a horizontal scroll away. Pinned by a test so nobody discovers it by
  accident.

### What of the build order is left

1. **`Ctrl+Space`** — focus into and out of the symbol panels. `Shift+F10`
   and the object row's F6 region shipped; this did not.
2. **A graph face on the object row.** `ObjectFace` has two arms, `page` and
   `equation`; `object_face.dart`'s own doc still says "A graph will qualify."
   Graphs shipped without one, so a graph is currently the only first-class
   object on the canvas with no row of its own — which is the exact rule the
   row was built to hold. Its controls already exist (pan, zoom, fit, and the
   window it is looking through); they just have nowhere to live.

### Known-live defects this release did not fix

- ~~Two source files contain literal NUL bytes~~ — **fixed in v0.24**, and
  the guard that found the second one is `test/source_hygiene_test.dart`.
  A literal NUL makes ripgrep call the whole file binary and skip it, so
  nine hundred lines of `text_block_view.dart` were invisible to every
  code search in the repo — including the audits looking for defects in
  it. The \u0000 escape reads identically to Dart. Left here because the
  RULE is live and the same trap is one keystroke away in any new file.
- **A large file DROP still reads the whole thing into memory** —
  `media_drop.dart:293` and `:432` — rather than streaming it the way
  Insert ▸ Video already does. The half that LIED (a drop that landed nothing
  and said nothing) is fixed; the progress half is not.

### What the test suite structurally cannot see

Two classes of defect, and both have now bitten:

1. **A debug-only API used in shipped code.** `KeepBaseline` read
   `RenderObject.debugNeedsLayout`, whose result is assigned inside an
   `assert` — so it throws with asserts stripped, in release and profile only.
   Every open inline equation broke its paragraph's layout in the build a
   student downloads, and every test in the suite passed. The fix was to stop
   using it; the rule is that `lib/` may not touch a `debug*` member outside
   an assert, and a sweep is the only way to check.
2. **Whether the app runs at all.** This session cannot build it: a Windows
   build rebuilds `rust/onote_core/target/release/onote_core.dll`, which is
   out of bounds. `flutter analyze` and the suite are the ceiling; a smoke
   test on a real machine is the rest.

### Not built, and why

- **3D.** The owner: *"if its going to require its own seperate system
  compared to 2d stuff and will add a lot of complexity, lets not bother for
  now."* It does: a surface needs a second grammar (two variables), a second
  painter and a projection. The 2D work is shaped so it lands as an added file
  rather than a rewrite.
- **A blank graph on the Insert menu.** A graph is a graph OF something, and a
  graph has no editor of its own — a blank one would be a box with nothing to
  change. The route is the `Graph` button on the equation's own row.
- **Number bases** (binary, hex, octal). Explicitly *"not a priority"* and
  *"must be integrated thoughtfully, cleanly, and without making everything
  feel cluttered"*. Nothing about the current design earns it a place yet.
- **Worked solutions with steps**, in the manner of Wolfram Alpha. Far future,
  noted so the idea is not lost.
- **The Bench's best idea.** The rejected "permanent 320 px dock" design had
  one thing worth stealing: *press a symbol with a text caret in a paragraph
  and an inline equation starts, seeded with that symbol.* Still worth
  building; still unbuilt.

## What was asked

Kept because the words are the requirement, and because the standing style
rules live here.

### The interface principles (B10, B11)

1. As simple and easy for the user as possible.
2. As fast and responsive as possible — assume success and show a failure if
   it comes, or show progress where that is better.
3. Never move the user or change things without their command.
4. Consistent behaviour — *"A regular user is not going to think a standalone
   maths box is any different to one in a text box, so they must have exact
   feature and behaviour parrody."*
5. Instructions carry as little text as they can: icons and mapping over
   sentences, and where words are needed, the fewest that work — the model
   being `symbol (\symbol)` rather than `symbol — type \symbol`.

### The maths conventions

Where a convention is unclear, follow a **Casio fx-82AU PLUS II**. That is the
calculator on the desk beside the app, and disagreeing with it is a bug
whatever the textbook says.

### The graph brief

- **B16** Write `y = 3x+10` as maths, press Graph — a *new* graph element
  appears on the page. It moves independently, and stays tied to that
  equation: change it to `y = 2x+6` and the graph follows.
- **B17** The link is shown by selection and only by selection: click the
  graph and it takes a subtle themed border while its equation takes a
  background tint of the same colour; click the equation and both light up the
  same way. *"i dont want the highlighting to be always there."*
- Benchmarks: **Desmos and Wolfram Alpha**, being where a student would
  otherwise go. Neither is matched yet; both are the bar.
