# Four asks that are features, not fixes

> Written 2026-08-08, after fixing the image-offset and new-page bugs from the
> same message. Nothing here is built. This exists so the four can be sized
> honestly and picked between, rather than started in the order they were said.

## 1. Everything in one box — flashcards (and the rest) in flow

> "would be nice if i could have them in the same box with text and other
> stuff. Ideally id like to be able to have everything in a single box at once."

**The shape already exists.** In-flow images are a Markdown line
(`![alt](sha256:… =WxH)`) that both renderers turn into a widget: read mode in
`md_render._renderLine`, edit mode as a placeholder in
`live_markdown_controller._buildLine`. The hard part — a widget inside a live
`TextField` without desyncing a single caret offset — is solved and tested
(`inline_image_edit_test.dart`).

So a flashcard in flow is that pattern again:

- **Syntax.** Needs to be a whole line, line-anchored, and survive a round trip
  through a build that does not know it (it will, since unknown Markdown is
  just text). Something like `?[front](back)`. It must not collide with
  `![...](...)`; the leading character is the discriminator.
- **Both renderers**, or the box visibly changes on entering edit mode. The
  parity test in `edit_view_metrics_test.dart` is the guard.
- **Card extraction** moves from "a `flashcard` block" to "a line in a text
  block", which `cardsFromBlock` already does for tags — so the study panel,
  the scheduler and the exam plan need nothing.
- **The block type stays.** A standalone card is still the discoverable thing
  in the Insert menu; the in-flow form is for when you are mid-sentence.

**Cost:** medium. Two renderers, a syntax decision, extraction, tests. The
riskiest part is already done and proven.

**Note the general version of the ask.** "Everything in a single box" is really
about which block types can be in-flow. Today: text, images, tables, maths,
code. Not in flow: ink, PDFs, video, attachments, flashcards. Each is its own
piece of work and they are not equally sensible — ink is page-absolute by
design (Ink Spec §3) and probably never belongs inside a paragraph.

## 2. Templates need to be templates

> "They dont respect the current layout of the page (with the title and stuff),
> they just go over it all and also arent all that helpful as is."

They now apply without throwing (fixed), which revealed that applying them is
the smaller problem. Two real defects:

- **They overwrite rather than compose.** `applyTemplate` replaces `pageProps`
  outright and appends blocks at their stored coordinates, which land on top of
  whatever is already there. It should place relative to the page's existing
  content — `smartPlacement` and `contentBounds()` already know how — and leave
  the title and page settings alone unless the template deliberately sets them.
- **The content is thin.** Six hand-written templates of a few blocks each,
  authored as literal JSON, never seen rendered because they never worked.

**Recommendation:** treat the built-ins as new work, not as data to repair.
Design two or three that a student would actually use (Cornell notes is the
only current one that earns its place), author them by building the page and
using "save as template", and check the result in the app. Also decide what a
template MEANS when the page is not empty — most likely "insert below what is
there", with "replace the page" as an explicit second action.

**Cost:** small-medium for the placement fix, then design time for content.

## 3. Pages as well as canvas

> "id like the option to switch between pages and and this pageless/canvas
> mode. By default it should be canvas, but id like the option to be able to
> work in set page sizes (which should be alterable too)."

Also PLANNING.md's "Page Format" entry, which adds: "default is A4, but also
setting other metric and american sizes".

**What exists.** `PageProps` already carries `pageWidth` and a `gridSize`, and
`AppState.pageSize()` / `pageGrowMargin` already compute an unbounded canvas
that grows with content. Blocks are page-absolute already. So the model is not
the obstacle.

**What does not exist:** a page BOUNDARY — the thing that makes content
overflow onto a second page, which is the whole point. That means:

- a paginated layout mode that flows blocks across fixed-height pages,
- what happens to a block that straddles a break (push whole? split? forbid?),
- page-break-aware scrolling, printing and PDF export (the vector exporter
  currently emits one long page),
- and a per-page or per-notebook setting for the size, with the standard
  metric/US list.

**Cost: large, and the biggest open question is the straddle rule.** Worth
noting that PDF export already produces real paginated output, so some of the
geometry exists to borrow.

## 4. .docx in, .docx out

> "id like to import files like .docx and alike into this, work on them in the
> page format, then export them again (or have it just edit that file in
> place)"

**This depends on #3.** Editing a Word document in a canvas with no page
boundaries and exporting it back is not a round trip anyone would recognise.

**Feasibility.** `.docx` is a zip of XML — readable without a heavy dependency,
and the Rust core is the right home for it (it already does the far nastier
`.one` format, and `onote_core` is the permissive tier, so a docx reader there
stays reusable). Import is tractable: paragraphs, runs, styles, lists, tables,
images.

**Export is where the honesty is needed.** A faithful round trip that preserves
everything Word put in a file — styles, numbering, section properties,
revision marks — is not achievable, and "edit that file in place" would silently
destroy the parts we did not model. What IS achievable is a clean `.docx`
generated from Openote's own content. The two should not be confused, and
in-place editing of a file we cannot fully represent should probably not be
offered at all.

**Cost: large.** Import alone is a reasonable standalone piece; the round trip
is not.

## Suggested order

1. **Templates placement** — smallest, and they are currently misleading.
2. **Flashcards in flow** — the machinery is proven, the ask is specific.
3. **Pages** — large, and blocks #4.
4. **.docx** — after pages, and scoped to import + clean export, not in-place
   editing.
