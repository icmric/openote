## 1. The consistency rule

**The keyboard map lives in code as a single table** (`ui/keyboard_map.dart`,
to be created): every binding as data — key, context, action, description.
Two consumers keep it honest:

1. The app registers its `Shortcuts`/`Actions` FROM the table — a binding
   that isn't in the table doesn't exist.
2. A **shortcut reference overlay** (`Ctrl+/`) renders the table, so the
   documentation is the implementation and cannot drift.

The rule for future features, mirroring spec 14 §7: a PR that adds an
interactive surface adds its rows to the table, or it isn't done. A test
asserts every registered shortcut has a description.

## 2. Inventory (done — what exists and where it lives)

Every binding found by the grep is now a row in `ui/keyboard_map.dart`.
The implementation sites, for the phase that moves registration into the
table: the global chords live in `app_shell.dart`'s HardwareKeyboard
handler (deliberately NOT widget-tree `Shortcuts` — see the comment there:
bare-letter activators shadow text fields on desktop); per-surface
bindings live in `table_block_view.dart` (cell movement `Shortcuts`),
`code_block_view.dart` (Ctrl+Enter run, Tab-as-spaces via focus onKey),
`study_panel.dart` (Space/1–4 via focus onKey), `unicode_input.dart`
(Alt+X chord test), `sidebar.dart` (rename Escape). Editor-internal and
staying that way: the markdown engine's list/fence continuation and
`wrap_selection.dart`'s wrap-on-pair-char (documented in the map as a
behaviour, not a chord).

## 3. The map to build toward (proposed)

| Context | Key | Action |
|---|---|---|
| Everywhere | `Ctrl+/` | Shortcut reference overlay |
| Everywhere | `F6` / `Shift+F6` | Cycle focus: sidebar → page → open panel |
| Canvas | `Tab` / `Shift+Tab` | Select next / previous block (reading order) |
| Canvas | `Enter` | Edit the selected block (its natural editor) |
| Canvas | `Escape` | Exit edit → deselect → close panel, in that order |
| Canvas | Arrows | Move selection spatially between blocks |
| Canvas | `Ctrl+Arrows` | Nudge the selected block |
| Sidebar | Arrows / `Enter` | Move through pages / open |
| Board block | Arrows / `Enter` / `Ctrl+Arrows` | Move between cards / edit / move card between columns |
| Dialogs | `Enter` / `Escape` | Confirm / dismiss (audit: every dialog) |

Screen-reader semantics ride along: the same traversal order feeds
`FocusTraversalGroup`s, so fixing Tab fixes assistive tech ordering too.

## 4. Phases

1. **Inventory + table + Ctrl+/ overlay** — no behaviour change, ends the
   era of undiscoverable bindings.
2. **Block traversal core** (Tab/Enter/Escape/arrows on the canvas) — the
   single highest-value stretch; a canvas you can work one-handed.
3. **Region cycling + dialog audit** (F6, Enter/Escape everywhere).
4. **Board & panel internals**, then the every-new-surface rule enforces
   itself via §1.

## 5. After this: i18n (the third of the trio, in order)

Wiring `flutter_localizations` + ARB extraction is mechanical but touches
every string in the app — it gets its own pass after keyboard, with one
decision from Eric first: which languages have an actual audience, because
the infrastructure is cheap once and translations are a commitment forever.
