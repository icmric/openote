# Openote v0.7 — installers, and the signing problem

> **Document status:** v1.1 · Windows installer built; site on Cloudflare Workers · 2026-08-06
> **Owner:** Eric · **Related:** [ROADMAP](../../ROADMAP.md) · [release workflow](../../.github/workflows/release.yml)

## 0. The ask

> *"I want them to be able to install a single exe or equivalent file which has
> a setup wizard to do everything and make it nice."*

## 1. Where we already were

The release workflow produces, on tag:

| Platform | Artifact | Is that "a single file with a wizard"? |
|---|---|---|
| Linux | **AppImage** (+ `.tar.gz` fallback) | **Yes, effectively.** Download, `chmod +x`, run. That is the Linux idiom; a wizard would be *less* native, not more. |
| macOS | **`.dmg`** | **Yes.** Open, drag to Applications. Also the idiom — mac users do not expect a wizard. |
| Windows | **portable `.zip`** | **No.** Unzip-and-find-the-exe is the one that reads as unfinished. |

So the gap was Windows only, which is also where most of the users are.

## 2. The options for Windows

| Option | Wizard | Single file | Admin needed | Cost | Verdict |
|---|---|---|---|---|---|
| **Inno Setup** | ✅ classic | ✅ one `.exe` | ❌ (per-user install) | free | **Chosen** |
| MSIX | ⚠️ store-style | ✅ `.msix` | ❌ | free, but **must be signed to install at all** | Later — see §5 |
| WiX / MSI | ✅ | ✅ `.msi` | usually ✅ | free | Enterprise shape; heavier for no gain here |
| Squirrel / Velopack | ⚠️ minimal | ✅ | ❌ | free | Optimised for auto-update, which we do not have yet |

**Inno Setup**, because it is the only one that gives exactly what was asked
with no new constraints: a real wizard, one file, no administrator prompt, a
Start-menu entry, an optional desktop icon, and an entry in Add/Remove
Programs that uninstalls cleanly.

**Per-user install (`PrivilegesRequired=lowest`) is a deliberate choice.**
Installing into `%LOCALAPPDATA%` avoids the UAC prompt entirely, which matters
for a student on a university laptop who may not be an administrator on it. The
cost is that the app is installed for one account rather than the machine, which
for a personal notebook is the right default anyway.

## 3. What was built

- **`packaging/windows/openote.iss`** — the Inno Setup script. It installs
  everything from the staged build directory **by wildcard**, so adding a
  bundled DLL later (a new native dependency) needs no change here. That was a
  requirement: the packaging must not become something that breaks every time
  the app grows.
- **`.github/workflows/release.yml`** — the Windows job now produces the
  installer *in addition to* the zip. The zip stays: it is the answer for
  anyone who cannot or will not run an installer (locked-down machines, USB
  sticks, people who want to inspect it first), and it costs one line to keep.

The wizard covers: licence page, install location, Start-menu folder, optional
desktop shortcut, "launch Openote" on finish, and a proper uninstaller. It also
refuses to install over a running copy rather than leaving a half-updated
directory.

## 4. The honest part: code signing

**This is the one thing a nicer installer cannot fix by itself**, and it is
worth stating plainly before anyone is surprised by it.

- **Windows.** An unsigned installer triggers **SmartScreen**: *"Windows
  protected your PC — unknown publisher"*, with the Run button hidden behind
  "More info". This is not a bug in the packaging; it is Microsoft's reputation
  system, and a brand-new certificate does not clear it either — reputation
  accrues per-certificate over downloads and time. An OV code-signing
  certificate is roughly **US$200–400/year**; an EV certificate (which clears
  SmartScreen immediately) is more and requires a hardware token.
- **macOS.** The `.dmg` is ad-hoc signed, which is not the same as notarised.
  Users get *"cannot be opened because the developer cannot be verified"* and
  must right-click ▸ Open once. Clearing that needs an **Apple Developer
  Program** membership (**US$99/year**) plus a notarisation step in CI.
- **Linux.** No equivalent problem. AppImage just runs.

**Recommendation:** ship unsigned for now and say so in the README, with the
one-line instruction for each platform. Revisit when there are enough users
that the friction costs more than the certificate. Spending ~$300/year to
remove a "More info" click for a handful of early users is the wrong trade;
spending it when a hundred people a month bounce off it is obviously right.

The install instructions must therefore *tell the truth* rather than pretend
the warning will not appear — a user who is warned about the warning treats it
as expected, and a user who is not treats it as malware.

## 5. Deliberately not done yet

- **Auto-update.** A real feature with real failure modes (a broken update that
  cannot self-repair is worse than no update), and it wants a signed build
  first so the updater can verify what it fetched. Revisit with signing.
- **MSIX.** Attractive for one specific reason — it is the packaging that would
  let Windows *schedule* notifications, which
  [v0.5 §1](v0.5-dates-and-reminders.md) had to design around. But it cannot be
  installed at all unsigned, so it is gated on the same decision as §4, and it
  would still leave Linux without scheduling. Not a reason to change the
  reminder architecture.
- **Winget / Chocolatey / Homebrew / Flatpak.** Each is a submission process
  and an ongoing obligation, and each mostly wants a stable signed release to
  point at. Worth doing once v1 is out; noise before then.
- **Per-machine (admin) install option.** Easy to add to the same script if a
  lab or school ever asks for it. Nobody has.

## 6. The download page

`site/index.html` — one file, no build step, no dependencies, published to
GitHub Pages by `.github/workflows/pages.yml`. It exists for a concrete
reason: getting a build onto a Linux VM or to a friend on a Mac should be a
URL, not a walk through GitHub's releases UI.

- It reads the **latest release from the GitHub API at load time**, so a new
  release appears on the site without republishing it. If that call fails — or
  no version has been tagged yet — the buttons fall back to the releases page
  and the copy says which is likelier.
- It **detects the visitor's OS** and moves that card first.
- It carries the same honest warning copy as the README, expanded per platform.
- **No third-party requests.** No Google Fonts, no analytics, no CDN. A page
  for a local-first app that says "nothing is uploaded anywhere" should not
  phone home to render its own headline.

**Hosted as a Cloudflare Worker** (changed 2026-08-06, from GitHub Pages — the
owner already runs Cloudflare and owns the domain). The move is not just a
change of host: it moves the GitHub-API call off the visitor's browser and onto
the edge, which removes the unauthenticated API's 60-requests-per-hour-**per-IP**
ceiling and a cross-origin round trip before the download buttons resolve. See
`site/worker.js`; the page still falls back to calling GitHub directly, so it
keeps working opened from disk or served from anywhere.

## 7. The name and the domain

`openote.com` is taken; `openote.org` is free. **Recommendation: keep the name
and take the .org.**

Renaming is not a cheap change at this point — "onote" is the *file extension*,
which is the project's central promise ("an open format you own"), and it is
also the Rust crate, the FFI symbol prefix, the SQLite `application_id`, the
installer's product GUID and every document here. Changing it would churn all
of that to solve a problem the .org does not have.

And `.org` is the right register anyway. It reads as a project rather than a
product, which is what this is — no account, no server, no company. Several
peer projects a switcher would compare against sit on `.org` for the same
reason. If the `.com` ever becomes available cheaply it is worth grabbing as a
redirect, not as the canonical address.

*(`openote.app` is a reasonable second choice — Google's `.app` TLD enforces
HTTPS, which is a small genuine benefit — but it costs more and reads more
commercial. Only worth it if `.org` were gone.)*
