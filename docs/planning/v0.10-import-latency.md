# Openote v0.10 — why the app still stalls during import, and the plan

> **Document status:** v1.0 · plan, no code yet · 2026-08-06
> **Owner:** Eric · **Related:** [v0.9 performance](v0.9-performance.md) · [v0.10 storage](v0.10-storage.md)

## 0. The report

> *"The UI still locks up. Visually it updates with the popup, however
> interactions with the page aren't completed until the import is finished."*

Accurate on both halves, and the split — paint works, interaction doesn't —
is itself the diagnostic.

## 1. What is actually happening

### 1.1 Measured

A probe importing a synthetic 40-page notebook (20 images × 400 KB, text and
ink besides) through the shipped batch writer, on the fast dev container:

| | |
|---|---|
| batches (4 pages each) | 10 |
| median batch | **57 ms** |
| p90 / max batch | 136 ms |
| whole write phase | 615 ms |

That is the *friendly* case: small images, Linux, warm disk, no antivirus. A
real notebook with 2–5 MB photos on Windows — where every flush pays Defender
tax — plausibly runs **200–800 ms per batch**, for minutes.

### 1.2 The mechanism

The v0.9 rework yields between batches with `await Future.delayed(Duration.zero)`.
That buys **one event-loop turn**, not a frame budget. Two consequences:

- **Paint survives.** The engine's frame callbacks are scheduled events; a
  vsync that lands in the gap gets its frame. Hence "visually it updates" —
  the progress card animates.
- **Interaction starves.** A click is not one event; it is a conversation:
  pointer-down, pointer-up, gesture-recognizer resolution, the handler, a
  state change, a rebuild, a paint — and for anything real (clicking into a
  text box, switching pages) an async continuation that reads the database.
  Every leg of that conversation must fit into one of the slivers between
  batches, and each sliver is followed immediately by the next 57–136 ms
  chunk. The legs queue; the interaction completes when the import does.
  Which is the report, verbatim.

### 1.3 What a batch spends its time on

In descending order, all on the UI thread:

1. **fsync'd op-log writes.** `OpLogStore.writeBlob` is
   `writeAsBytesSync(flush: true)` per image, and every op append is
   open → write → `flushSync` → close. An fsync is the single most expensive
   thing a UI thread can be asked to do, and the blob double-store
   (see the storage plan) means each image's bytes are written — and synced —
   **twice** inside the batch.
2. **SQLite inserts** — page JSON and blob bytes into the container
   (WAL, `synchronous=NORMAL`, so cheaper than the log writes, but multi-MB
   inserts are still tens of ms).
3. **`restackFlows`** — TextPainter measurement per imported box. Genuinely
   UI-thread-bound (text layout needs the framework), but small next to 1–2.
4. JSON encodes of every page.

## 2. Options

### Option A — pace by time, not by page count *(small; a day)*

Replace "4 pages per batch" with a time budget: write until ~8 ms have
elapsed, then `await SchedulerBinding.instance.endOfFrame` — which, unlike a
zero-delay timer, doesn't continue until a frame has actually been produced —
plus one extra event-loop turn for input.

- **Gets:** the common case feels alive; the gap between chunks is a real
  frame, every frame.
- **Cannot get:** atomicity of the indivisible steps. A single 5 MB image is
  one `writeBlob` + one SQLite insert; you cannot split an fsync. Image-heavy
  pages still hiccup 50–200 ms each.
- **Risk:** low. Same code path, different pacing.

### Option B — take the fsyncs off the synchronous path *(medium; 1–2 days)*

The op-log writes don't have to be synchronous *or* inside the batch:
`dart:io`'s async file APIs run on internal worker threads. Restructure the
batch to do SQLite work synchronously, collect the log writes, and `await`
them (async, flushed) between chunks.

- **Gets:** removes the single biggest cost from the blocking span. Combined
  with A, batches shrink to "SQLite + measurement" — likely single-digit ms
  for text pages, tens for image pages.
- **Cost:** the recorder's calls become awaitable on the import path, and the
  log lands *after* the container commit rather than beside it — acceptable
  in shadow mode, but it is a loosened ordering and the docs must say so.
- **Risk:** medium-low. Ordering reasoning, no new architecture.

### Option C — a writer isolate *(the real fix; 2–4 days)*

Move the entire write phase off the UI thread. The import target is a **brand
new notebook** — no other code holds its SQLite handle, its log files, or any
in-memory state — so a second isolate can own it outright:

1. Main isolate: pick file, read bytes, run `restackFlows` as a paced
   pre-pass over the parsed structure (TextPainter cannot leave the main
   isolate; the measurement is the cheap part, and Option A's pacing applies
   to it).
2. Writer isolate: parse result in, opens its **own** SQLite connection on
   the new `.onote`, writes pages, blobs and the op log directly, streams
   progress over a port, honours cancel over the same port.
3. Main isolate on completion: registers the finished file in
   `workspace.json` (an "adopt existing file" repository call — the orphan
   recovery path is most of it already), attaches a recorder for future
   edits, shows Open.

- **Gets:** the UI thread does *nothing* during import except receive
  progress messages. Typing during a 300-page import is indistinguishable
  from typing while idle — which is the promise the feature made.
- **Preconditions, all tractable:**
  - the per-page translation (`importOneParsedPage`) must run against a bare
    `Database` instead of `AppState` — it is nearly there; it uses AppState
    only as a facade over repository calls plus two constants;
  - device identity resolved on the main isolate and passed in (the recorder
    currently reads/writes workspace settings to get it);
  - cancel/teardown = kill isolate, delete the two paths.
- **Risk:** medium. New seam, but a clean one — the isolate owns files nothing
  else has open, which is the property that makes it safe.

### What was considered and rejected

- **Parse and write in one isolate, streaming pages over a port** — same as C
  with more moving parts; C already gets the parse from the existing compute
  call.
- **Lowering fsync guarantees** (`flush: false`, `synchronous=OFF`) — buys
  speed by making the durability promise quietly false. No.

## 3. Recommendation

**C is the destination; do A's pacing first as part of it, not before it.**
A alone leaves image-heavy imports hiccuping and would need to be rebuilt
anyway; B is subsumed by C (in the writer isolate, synchronous fsyncs are
*fine* — that's the point). The one piece that stays on the UI thread either
way is the restack pre-pass, which is exactly what A's time-budget pacing is
right for.

Sequencing with [the storage plan](v0.10-storage.md) matters: if blobs become
single-copy first, every import batch halves its write volume before C even
lands. Do storage wave 1, then C.

## 4. How we'll know it worked

The existing responsiveness test (a 1 ms timer must keep firing during a
40-page import) is necessary but too weak — it passed while the user's clicks
starved. Add:

- a test that performs a **complete interaction** (tap → handler → state
  change observed) during an import and asserts it completes within N frames,
  not after the import;
- the manual headline in TESTING.md stays: type, scroll and draw during a
  real notebook's import, now with "and click into text boxes" added.
