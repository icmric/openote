# v1.0.3

Raised during v1.0.2 and bigger than a patch release, or dependent on something
in it. Nothing here is committed to this version — it is here so it is pushed
back deliberately rather than forgotten.

## Definite sums and integrals

Asked: *"feasability of solving equations with large/complex operators
(integrals, summation, limit, etc)?"*

**The first piece of work is not evaluation at all.** A `\sum_{i=1}^{n} i` from
the palette loses the operator and both limits on the way to the calculator:

```
stored tex : \sum _{i=1}^{n}i
linear     : "§i"
calculator : unexpected "§"
```

`math_linear_projection.dart` emits a placeholder for a script whose base it
cannot speak, and the same is true of `\int`, `\lim` and `\prod`. So carrying the
construct across that seam comes first.

After that, in increasing order of difficulty and decreasing order of
advisability:

1. **A definite sum or product.** `∑_{i=1}^{5} i²` = 55. Tractable, and the
   parts exist — `compileFormula` already compiles a body into a closure over a
   map of variables, so the index binds in a loop. Needs the projection fixed, an
   integer-limit check, and a cap so a mistyped limit cannot hang the UI isolate.
2. **A definite integral.** `∫₀¹ x² dx` ≈ 0.3333 by Simpson's rule over the same
   closure. Comparable work, plus a convention for the `dx` — which the
   prefilled template writes, and which the parser would have to read as a bound
   variable marker rather than two letters multiplied.
3. **A limit.** Approachable by sampling towards the point, and **not worth
   doing.** Indeterminate forms, one-sided limits and false convergence each
   produce a confident wrong number, and a limit that is quietly wrong is worse
   than one that declines to answer.

(1) and (2) make the Evaluate block genuinely useful for a calculus problem set
and neither touches the vision's non-goals. (3) and a step-by-step walkthrough
are both reversals of a stated decision, for different reasons.

## The Evaluate block, inline in a sentence

Asked: *"Difficulty of enabling solution box to be inlined with text and other
elements?"*

**Moderate, and the storage half is already done**, which is the surprising
part. `InlineAtom` holds a thing that is not text inside a text block, and it was
built to take more than one kind: its `type` is a string rather than a
`BlockType` so that an atom of a type this build has never heard of survives
being read and written back, and the payload is a block's own content shape. So
sync, undo, cut/copy/paste, the op log and every export need **no format work at
all**. `table` is simply the only value in use today.

What it costs is the dispatch, and the sites are known: the renderer in
`inline_atom_view.dart` (the real work), stepping into it with an arrow key in
`live_markdown_engine.dart`, the read-only view in `text_block_view.dart`,
Markdown export in `md_common.dart`, PDF export in `pdf_vector_export.dart` in
two places, the label in `history.dart`, and insertion — Evaluate with the caret
in a sentence should make an atom rather than a block.

Plus one real refactor: `SubstituteBlockView` reads and writes `block.content`
directly and would need a binding instead. `InlineTable`'s `TableBinding` is the
template and `blockAtomHost` is the bridge that already exists.

**The focus machinery is the part that would have been hard and is not any
more** — an atom holding `TextField`s inside a paragraph is exactly what
`inline_table.dart` solved, and `core/focus_claim.dart` means a field inside a
paragraph no longer loses the caret.

This is [v1.0.2 #3](v1.0.2.md#3-one-way-to-hold-a-piece-of-content)'s principle
applied to one more type, and the two are cheaper together than apart.

## Flashcards, rebuilt as a box

**Decided.** Asked on GitHub ([#16](https://github.com/icmric/openote/issues/16)):
multi-line cards, with lists, code, images and formulas — *"would be incredible for
review sessions"*. The owner's decisions:

- **Edited directly on the card**, not in a dialog: *"more intuitive, clean, and
  shows actually what it looks like rather than the user just guessing. It also
  keeps it aligned with the rest of the app."*
- **Each side is, more or less, a regular box**, so it behaves the same and has the
  same abilities: *"i dont want to have to maintain a seperate maths, code, and
  image handler just for flashcards."*
- **Maths first.** Code and images if they are not much harder; tables only if they
  come easily.
- **Markdown export: the raw Markdown of each side**, open to suggestions (below).

### Why rebuild, rather than extend `?[front](back)`

The format is one line of Markdown with brackets for edges, which rules out
multi-line by construction and makes code, images and display maths fight the
delimiters. And it is wrong today, not only limited — measured during v1.0.2:

- **A card's schedule is its line number.** `Flashcard.id` is `blockId:line`, and
  only tagged lines are carried across when lines move. One line typed above two
  cards hands the first card the second's schedule. v1.0.2 bug 16 is the stopgap;
  this is the fix.
- **A `)` in an answer is not a card at all.** `?[Derivative of x squared](f(x) = 2x)`
  yields zero cards, silently. MCP's `create_flashcards` works round it by rewriting
  `(` to `[` in every answer it writes.

### The shape: an inline atom whose two sides are text

The inline table already solved "an object that is not text, living in a
paragraph", and a card fits it almost exactly. The reference stays in the
paragraph's text — `![Flashcard: What is osmosis?](onote://atom/<id>)` — and the
payload sits beside it in the same block:

```jsonc
"atoms": {
  "<id>": {"id": "<id>", "type": "card",
           "content": {"front": "<markdown>", "back": "<markdown>", "w": 420, "h": 160}}
}
```

What that gives for nothing, because the table needed it first:

- **A permanent id**, so the schedule follows the card through any edit.
- **No delimiters.** The sides are JSON strings, so brackets are only characters.
- **Each side is the app's own Markdown dialect** — the same text a box holds — so
  every renderer that draws a box draws a side: inline and display maths, code
  fences, `![](sha256:…)` pictures, lists, multi-line.
- **A size of its own**, `w`/`h` in the payload. This was v1.0.2's "a flashcard has
  no size of its own", which needed a format decision in the Markdown line; here it
  needs none, which is what the inline table's column widths were pointing at.
- **Sync, undo, cut/copy/paste, `read_page` and `append_blocks`** already carry atoms.
  An older build keeps one it does not understand and shows its alt text, which is
  a better failure than today's.

### Editing on the card: two boxes, not two handlers

The requirement — *a side is a regular box* — is also the cheapest way to build it.
**Each side is a real paragraph editor**, hosted in the card the way an inline
table hosts its cells, so a side gets maths, code, pictures, the toolbar, the
shortcuts and spell check from the code that already does them for every box, and
anything a box learns later a card learns with it. `inline_table.dart` is the
template: a `TableBinding` lets an atom's content be read and written like a
block's, `blockAtomHost` bridges it, and `core/focus_claim.dart` is why a field in
a paragraph no longer loses the caret.

Two questions specific to cards:

- **Flip versus edit.** A tap turns a card over today. Editing a side has to win
  without losing the flip: probably edit the side you are looking at, with the
  turn on its own control — as the block form already does with its edit button.
- **Tables inside a side** — the nesting the owner allowed *"if it's easy"*. A side
  being a box makes it possible; a table in a sentence in a card in a sentence is
  the first three-deep case the focus machinery would meet. Decide once the rest
  works.

### Moving existing cards across

Convert `?[front](back)` lines to card atoms **on page open**, the way tables were
converted — `table_conversion.dart` proves the result before it writes and refuses
rather than half-converting. **Carry each schedule from `blockId:line` to the new
id at the moment of conversion**, the one moment both are known. The old
`BlockType.flashcard` blocks (`blockId:0`) convert the same way.

### Markdown export

Raw Markdown, as suggested, with one refinement so it reads as a card everywhere:

- **A card whose two sides are single lines of plain text** exports as
  `?[front](back)`, as today — so it comes back into Openote, and into older
  builds, as a card.
- **Anything richer** exports as a `<details>` block with the question as its
  summary and the answer's raw Markdown inside:

  ```markdown
  <details><summary>What is the discriminant?</summary>

  $$\Delta = b^2 - 4ac$$

  </details>
  ```

  GitHub, Obsidian and most Markdown viewers render that as click-to-reveal, which
  is the nearest thing Markdown has to a flashcard, and every one shows the answer's
  Markdown as Markdown. A multi-line *question* does not fit a summary, so a card
  with one exports both sides inside, under bold "Question" and "Answer" labels.

### What it costs, and what to build it beside

Bigger than a patch release. It touches the same places as [the Evaluate block,
inline in a sentence](#the-evaluate-block-inline-in-a-sentence) — the renderer,
stepping in with an arrow key, the read-only view, Markdown and PDF export, the
history label, insertion — so the two are cheaper built together than apart. On
top of those: the study panel drawing a rich side (it uses `inlineSpans` today,
inline formatting only), the conversion, and MCP (`create_flashcards`, the block
schema, `read_page`).

## Version-history rollback

Only if [v1.0.2](v1.0.2.md#decisions-taken) picks building rollback over
removing the surface. Recorded so the design does not have to be rederived.

**Rollback needs no new storage.** The op log is a complete, ordered, never-
compacted history of every block that has ever existed, and `block.set` carries
the whole block with its device, sequence, Lamport clock and timestamp. A page
as it stood at any past moment is a replay of the log up to a time. What is
missing is the projection and the UI, not the data.

1. **Replay to a point.** `SyncRecorder` already replays the whole log to build
   `Materializer` state; replaying to a bound is the same code with a predicate.
   The work is making it cheap enough to do interactively on a big log — the
   same problem `warmRecorder` already solved once by moving a replay off the UI
   thread.
2. **Show it per block.** `block_authors` already holds device, Lamport, seq and
   `changed_at` per live block, so the per-paragraph attribution asked for is
   largely computed already. What it cannot show is what the block used to
   *say*; that comes from the replay.
3. **Put it back as an ordinary edit** — write the old content as a new
   `block.set`. **Never rewrite the log.** Rolling back is appending the past,
   not deleting the present, which keeps one writer per file and means a
   rollback syncs like any other change and can itself be undone.

Two caveats. **A rolled-back page can reference bytes that are gone** once the
forget op exists, so rollback and collection have to agree: a forgotten image
restores as the stand-in, not as a hole, and the UI should say which. And
**granularity is block-level**, which has been accepted — *"even if its just per
paragraph or whatever"* — so word-level blame is off the table.

## Hand a copy of something to somebody

> *"It would be nice to be able to export a copy of a page, section, section
> group, or entire notebook and share it with someone. Its a copy frozen in
> time, however being able to email or otherwise send it to someone could prove
> helpful. Would ideally need to be something which the receiving user could
> just double click and it auto populates a new notebook with the content."*

One file, emailable, that the recipient double-clicks. A frozen copy rather than
a shared notebook: no sync, no device registry, no way for either side to see
the other's later edits.

**Most of this already exists.** A page's content is Page JSON; a section or a
group is a `nodes` subtree plus the pages under it; and blobs are
content-addressed, so the set to include is whatever those pages reference.
`export/open_export.dart` already walks exactly that and writes it to a folder.
What is missing is a single-file container and an import that reads one.

Four things to settle, and the first is the real decision:

- **What the receiving end does with it.** The ask is "auto populates a new
  notebook", with a preference for not creating one. Those pull in opposite
  directions: importing *into* an existing notebook needs a target chosen, and a
  rule for what happens when it collides with what is there. Creating a new
  notebook needs nothing and is honest about being a copy. **Recommend: create
  one, say so, and offer "put it in an existing notebook instead" as a second
  step** — which is also the easier half to build and the one that cannot go
  wrong in a way that loses somebody's existing page.
- **Every id is minted fresh on arrival.** Data model §2 rule 3 already requires
  it for paste and import, and it is what stops a shared copy from colliding with
  the original if it ever travels back. Links *inside* the shared selection are
  rewritten to the new ids through the same id-map; links pointing outside it
  become dangling, which is correct and should render as such rather than being
  silently dropped.
- **It is not a `.onotebook`.** A notebook folder carries a device registry and
  op logs, and handing those to somebody else means handing them a device
  identity. A share file should carry content and nothing about who wrote it —
  which is also what makes it safe to email.
- **Say what travels and what does not.** Ink and pictures travel, because blobs
  are included. A page window pointing at a page that was not shared cannot, and
  the recipient should see a tombstone saying so rather than an empty box.

Worth shipping beside multiple-notebooks-open below, since dragging between two
open notebooks is the same operation without the file.

## Several notebooks open at once

Raised on GitHub: OneNote keeps more than one notebook open in the sidebar, and
Openote opens exactly one. Two reasons to want it, and the second is the stronger
one: seeing two notebooks at once, and **dragging a page or a section from one to
the other**, which today means export and re-import.

**One notebook open at a time is load-bearing in more places than it looks.**
`AppState.notebookId` is a single value that the canvas, the sidebar, the search,
the planner, the study deck and every recorder lookup read. Opening a second is
not a sidebar change; it is making "the current notebook" a property of what you
are looking at rather than of the application.

What that touches, as a scoping sketch rather than a plan:

- **The recorders already are per notebook** (`_recorders` is a map keyed by
  notebook id), which is the half that would have been hardest and is done.
- **The container handles likewise** — `Repository` holds one per open notebook
  already.
- **`AppState.notebookId` is the problem.** Every read of it has to become "which
  notebook is this widget showing", and the sidebar has to render more than one
  tree.
- **Cross-notebook drag needs the id-minting rule above**, because a page moved
  between notebooks is a copy-then-delete unless both notebooks agree about ids,
  and they do not.

## Drag a page out of Openote as a PDF

> *"I would like to be able to drag and drop a page, section, or section group
> into another application and have that turn it into a pdf before pasting it
> into said application. So i could drag and drop a page directly into here or
> an email and have it be readable by anyone."*

Dragging **out** of a Flutter desktop app is the unknown here, and it should be
answered before anything else is designed: `super_drag_and_drop` is the package
that claims it, and whether it can offer a file promise — where the receiving
application asks for the bytes only once the drop lands — decides the shape.
Without a promise, every drag would have to render the PDF up front, which for a
section group is seconds of work on the chance somebody drops it somewhere.

The rendering half needs nothing new. `export/pdf_vector_export.dart` already
produces a searchable vector PDF of a page, and printing already walks a
selection of pages. So this is a platform-integration question wearing a feature's
clothes.

Two things to decide once the drag mechanism is known: what a drag onto a
**file manager** should produce versus a drag into an **email** (probably the same
PDF, but Windows and macOS describe those differently), and whether a drag with
no PDF-capable target falls back to plain text or refuses.

## Signing the builds, and the warnings on all three platforms

Flagged by the owner for investigation, not designed. Three different
problems wearing one word.

### Windows — "Windows protected your PC"

SmartScreen, and it is about **reputation**, not identity. An unsigned
installer always shows it. An OV certificate (~$200–400/yr from a reseller,
and since mid-2023 it must live on a hardware token or in a cloud HSM, which
complicates CI) starts at zero reputation too and earns its way out over
downloads and time — so the warning fades rather than disappearing on day
one. An **EV** certificate gets immediate SmartScreen trust and costs more
again.

"The Microsoft developer program" is a separate thing and worth being precise
about: a Partner Center / Microsoft Store developer account is a one-off ~$19
and does **not** sign anything for you. What it buys is a route into the
Microsoft Store, and a Store-distributed app is signed by Microsoft and has
no SmartScreen prompt at all. That is a real option here — the app is already
MSIX-able in principle — but it means Store packaging, Store review and the
Store's own update channel instead of ours.

### Linux — "the developer is unknown"

Not the same class of thing, and not something to register for. There is no
central identity to apply to. What the message means depends on where it came
from:

  * **GNOME Software / Discover installing a local `.deb` or `.rpm`** says it
    because the package is unsigned and from no configured repository. The fix
    is a signed repository (an apt/dnf repo with a GPG key we publish) — then
    it is trusted the way any third-party repo is, and `apt`/`dnf` update the
    app, which is also the answer to "why is there no in-app update here".
  * **A Flatpak** would be the other route: published on Flathub, signed by
    Flathub's own infrastructure, sandboxed, and updated by the system. For a
    desktop app this is probably the lowest-friction Linux answer, and it
    costs a manifest and a review rather than money.

Either way: a build-side gap, not a missing registration, and the fix is a
distribution channel rather than a certificate.

### macOS — the $99, and whether there is a way round it

There is no free certificate that removes the warning. Apple issues Developer
ID certificates only to paid Apple Developer Program members, and since
Catalina an app also has to be **notarised** — uploaded to Apple, scanned,
and stapled — before Gatekeeper will open it without the "cannot be opened
because the developer cannot be verified" dialog. Notarisation needs the same
membership.

So the honest answer to *"surely not every little app pays"*: the ones that
do not are distributed the way this one is, and their users right-click ▸
Open, or run `xattr -d com.apple.quarantine`, the first time. That is the free
path, and it is what the download page should explain rather than pretend
away. Homebrew casks are the other common dodge — `brew install --cask` does
the quarantine removal for the user — and getting listed there costs nothing
but a PR to homebrew-cask.

**If any of this is done, do the cheap ones first:** a Homebrew cask and a
Flathub manifest cost time rather than money and remove the friction for the
two platforms where it is worst, before spending anything on Windows.

## Self-hosted sync on Cloudflare D1 and R2

A sync target that is not somebody else's Drive folder, hosted per user on a
free tier. Sketched, not designed.

The shape that fits the existing transport: ops are append-only rows keyed by
`(device, seq)`, which is what makes one-writer-per-file work and translates
directly to a table with that primary key. Pulling is "rows after my watermark",
which is one indexed query.

**Blobs go in R2, not D1.** D1 is SQLite with a row-size ceiling and a database
ceiling; blobs are content-addressed and immutable, which is exactly what object
storage is for, and R2 has no egress charge.

**The real cost is setup, not money.** A free tier covers a student's notebook
comfortably. What it does not cover is a person who has never seen a terminal
creating an account, a database, a bucket and an API token. Anything in this
direction has to answer that before it answers anything about schemas — the
reason the current transport is "point it at a folder you already have".

Still to decide: authentication (a token in the workspace, as MCP does, or
something per-device), whether a worker is needed at all or the client can talk
to D1 directly, and what happens when a free tier is exceeded mid-edit.

## Web AI clients

Spec 14 §8's table says ChatGPT's website and the Gemini app cannot reach a
local server because their connectors run server-side. That is still true for
the website, and the **desktop** apps are a different question — the ChatGPT
desktop app now reads `~/.codex/config.toml`, which Openote already writes.

**Not yet confirmed by a human: that the desktop app picks the entry up.** It
is on the backlog's verification list. Test it before believing it; the table
has been wrong in this direction before.

Microsoft Copilot is the worst fit of the three — its extensibility story is
Graph connectors and declarative agents, both of which run in Microsoft's cloud
and neither of which can see `127.0.0.1`.

**The zero-setup answer most people would actually use** is not an MCP client at
all: it is the user pasting a page into whatever chat they already have. Worth
remembering before building anything here, because the ceiling on this work is
how many people own a desktop AI client *and* will connect it.
