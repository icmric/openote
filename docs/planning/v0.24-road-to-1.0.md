# v0.24 — the road to 1.0

> **A whole-project review, and what 1.0 should mean.** Written 2026-09-02.
> Everything numeric below was measured on the tree, not recalled: **2,751
> Dart tests pass (49 skipped)**, **78 Rust tests pass**, and `flutter
> analyze` reports **0 errors and 0 warnings**. 80,352 lines of `lib`, 55,717
> of `test`, across 199 test files.
>
> **Since it was written, three of its findings have landed** — the welcome
> flow (§ below), the translation foundation plus the always-on chrome
> (§1), and the per-keystroke chrome rebuild (§2, 62.7 ms → 18.7 ms). Each
> section says where it now stands. **§0 is new**: the owner asked what is
> worth BREAKING while the format can still be broken, and the answer is one
> specific thing.

The owner's framing, verbatim: *"I don't think we are quite at a 1.0 release,
but I want us to get ready for one too, there are a couple more changes I want
to make before then but nothing major, it's something that I think is probably
only maybe 3-4 minor revisions away already."*

That estimate is right. Nothing found in this review is a rewrite, and nothing
found is a defect that would make 1.0 embarrassing. What is missing is a
handful of things a 1.0 is *expected* to have, and one performance property
worth knowing about before the app meets a slower machine than the one it was
written on.

---

## What the review found first: this codebase is in good order

Worth stating plainly, because the rest of this document is a list of things
to fix and that reads more alarming than the tree deserves.

- **Zero `TODO`, `FIXME`, `HACK` or `XXX` markers in `lib`.** Zero stray
  `print(` calls. No deprecated Flutter APIs. That is unusual at 80k lines.
- **Colour discipline is essentially complete.** 68 raw `Color(0x…)` literals
  exist; 40 are the palette in `theme/onote_theme.dart` — which is where they
  belong — and most of the remaining 28 are tag colours, syntax highlighting
  and ink, none of which are theme surfaces.
- **The performance engineering that is there is real, and it is the right
  kind:** the markdown renderer caches its built subtree on `(text, style,
  dark)`, the canvas culls to the viewport, `docRevision` is deliberately not
  bumped on keystrokes so block elements survive typing, and the root
  `MaterialApp` already memoises itself against everything but a theme
  change — with a comment saying exactly why. Someone measured before
  writing that.
- **The test suite is a real one**, not coverage theatre. Tests reproduce
  reported bugs through the real shell, and several carry the user's own
  words as the specification.

## 0. What is worth breaking now — one thing, and it is measurable

The owner, verbatim: *"we can afford to forgo backwards compatibility at the
moment being a prerelease preview, but we won't be able to get away with that
after our 1.0 release"*.

**The good news first, because it changes the shape of the question.** Almost
nothing here needs to break, and that is not luck. The format was designed for
additive evolution and — unusually — the implementation actually honours it:

- Unknown fields on a block round-trip verbatim (`Block.unknownFields`,
  `Block.rawType`), with tests in `model_roundtrip_test.dart`,
  `paste_fidelity_test.dart` and `templates_test.dart` that name the
  format-freeze promise by hand.
- New op kinds are additive, and the op log has a real **envelope gate**:
  `Materializer.apply` refuses any op whose `v` is beyond this build or whose
  payload is encrypted, collects them in `unsupported`, and the notebook goes
  **read-only** rather than being written on top of a history it has only half
  read. Its doc comment already names `v: 2` carrying the structured
  `{nodes:[…]}` model as the intended use.
- Node ordering is an opaque, lexicographically sorted string
  (`a` + a zero-padded millisecond), so a fractional index later writes
  different strings into the same field with no format change at all.
- Blobs are content-addressed by sha256. That is not going to want changing.

So the structured-text migration (Data Model §5.1), Loro, live collaboration
and blob GC can all land after 1.0. Each is either additive or already has its
escape hatch built and tested.

### The one that cannot wait: every autosave rewrites the whole block

Measured, on this tree, by driving real autosaves through `AppState` and
weighing the `.oplog` afterwards:

| block being edited | bytes of op log **per autosave** |
|---|---|
| 411 characters | **752** |
| 2,193 characters | **2,534** |

Linear in the block's size, plus about 340 bytes of envelope — because
`SyncRecorder.page` emits `block.set`, and `block.set` carries the **entire
block**. An autosave fires 700 ms after you stop typing, so a single character
added to a 2,000-character paragraph costs ~2.5 KB of permanent, replicated
log. That is roughly **2,500× write amplification**, and it is paid again on
every pause in a sentence.

This is not a new class of problem here and it has a fix in the same function.
Ink already gets a per-stroke diff, added because recording an erase gesture as
a whole `block.set` was "50–1000× write amplification" — the comment says so.
**Text never got the same treatment.**

Two caveats, so this is not oversold. The 64.56 MB log recorded in
[v0.13](v0.13-op-log-compaction-review.md) was **63.14 MB of inline ink**, and
that has since been converted to bytes; the text share of a real log today has
not been measured on the owner's own notebooks, and should be before anything
is built. And compaction — the other way to attack log size — was
[designed twice and rejected twice](v0.13-op-log-compaction-review.md); do not
reopen it without answering every kill-shot there.

### Why it is a pre-1.0 decision specifically

A finer-grained text op — call it `block.patch` — is a new op *kind*, and new
kinds are supposed to be additive. **For this one, they are not.** An old build
meeting an unknown kind *skips* it and carries on, which is right for an op
whose effect is optional and wrong for an op that carries an edit: the page
materialises stale, and the only signal is `verifyPage` downgrading itself to
"inconclusive rather than incomplete". Nothing tells the person their sentence
is missing.

The correct way to ship it is therefore on a `v: 2` envelope, which every build
already in the world refuses by putting the notebook read-only — safe, honest,
and exactly what that gate was built for. But it means a device on an older
release can no longer write to a shared notebook.

So the question is not *whether* the escape hatch works. It is **when to spend
the one envelope bump**: now, while the population of logs is small and the
users are the owner and a handful of others, or after 1.0, when spending it
means telling everyone their other machine has gone read-only until they
update.

### Recommendation

**Do it, and do it before 1.0 — but measure first, and treat it as its own
piece of work.**

1. **Measure the split on a real notebook.** Add up the `.oplog` bytes by op
   kind on the owner's own notebooks. If `block.set` on text blocks is not a
   large share today, stop here and revisit when it is.
2. **If it is, build `block.patch` the way `_diffInk` was built**: common
   prefix and suffix on `content.text`, emitted only when it pays, falling
   back to `block.set` otherwise, written at `v: 2`.
3. **Say so in the format spec's changelog**, which already has the shape for
   it, and in the release notes: an older Openote can read a v2 notebook but
   will not write to it.

Everything else on the "should we break it" list — the structured text model,
the CRDT, per-user encryption (the `enc` field is reserved and gated already)
— can wait, and waiting is the right call for all of them.

### One thing that is not a format question but is a release question

`flutter build linux --release` reaches out to the network at CMake **configure**
time: `media_kit_libs_linux` downloads `mimalloc-2.1.2.tar.gz` from GitHub and
checks its MD5. It works on the CI runners, and it cannot work on a machine
without access to `codeload.github.com` — verified here, where the fetch is
blocked and the build stops before compiling a line. Not something this project
chose, and not worth fighting upstream over, but worth knowing before someone
tries to build a release on a locked-down machine, and worth a line in whatever
build instructions ship with 1.0.

## Ranked, with evidence

### 1. Other languages — the foundation now exists; the migration does not

**Status: started in this revision.** `flutter_localizations`, `l10n.yaml`,
`lib/l10n/app_en.arb`, the generated `L` class checked in under
`lib/l10n/gen`, delegates on all three `MaterialApp`s, and the welcome flow
converted end to end as the proven pattern. `test/l10n_test.dart` guards it.

**What remains** is mechanical and large. Suggested order, by how much a
non-English speaker is blocked without it:

1. ~~the welcome flow~~ **done**
2. ~~the command bar, object row and navigator~~ — **done**: the chrome that is
   on screen for the whole session, ~200 messages, including three real ICU
   plurals and the numbers (word count, badges, zoom) that a language formats
   its own way
3. the notebook manager and sync dialog — the two places someone is trying to
   get their notes in or out, and the two most expensive to guess at.
   `sync_dialog.dart` alone holds 89 string literals
4. settings, the shortcut overlay (which means `keyboard_map.dart`, 86
   strings held as `const` data), the planner and study panels
5. **the model layer**, which is easy to forget because it is not a screen:
   the `label` getters on `TagKind`, `TouchDrawing`, `PaperSize` and friends
   are still English in `lib/model`. They need a `String label(L)` shape
   rather than a getter
6. error and failure surfaces last: they are the least seen and the most
   sensitive to a bad translation

A surface at a time, adding the file to `_converted` in `test/l10n_test.dart`
as each one lands, so a finished file cannot quietly grow a new literal. Note
that converting a screen breaks every test that mounts it under a bare
`MaterialApp` — `L.of(context)` throws without the delegates. New tests should
mount through `testApp` in `test/support/app.dart`.

**Do not machine-translate into the repository.** Adding a language is
`lib/l10n/app_<code>.arb` + `flutter gen-l10n`, with no Dart to change — which
means a native speaker can contribute a language without touching code, and
that is the point of doing it this way. Seeding `app_es.arb` with unreviewed
output would put words in front of users that nobody has read.

**One thing the migration must not lose:** the welcome flow's illustrations
are *painted*, not written, and deliberately contain no text. Keep new
illustrations that way. A diagram with a word in it is a diagram that needs
re-drawing per language.

### 2. Every keystroke rebuilds the entire shell — **fixed**

*Shipped. Kept here because the measurements are the reason, and because the
mechanism is now available for the next surface that needs it.*

`AppShell.build` wraps the whole application — sidebar, command bar, object
row, breadcrumb, canvas — in a single `ListenableBuilder(listenable: app)`,
and `AppState.markDirty()` calls `notifyListeners()`. `markDirty()` runs on
**every keystroke** (`text_block_view.dart:287`), and it has to: the comment
there is right that the auto-width measurement happens in the parent build, so
suppressing the notify would make boxes stop growing as you type.

Measured on the existing `ui_perf_probe` notebook (3 sections × 30 pages, 40
realistic blocks on the open page, 1500×950), median of nine frames, **debug
build**:

| after `markDirty()` | one frame |
|---|---|
| 40-block page, navigator expanded | **63 ms** |
| same, navigator collapsed to the rail | 46 ms |
| empty page, navigator expanded | 39 ms |

Read those as a shape, not as milliseconds a user will feel — debug builds run
several times slower than release for widget work, so the real figure is
plausibly 10–20 ms. But the shape is the finding: **~39 ms of it is chrome
that cannot have changed.** Typing does not alter the sidebar, and the sidebar
is the single most expensive thing rebuilt per character.

That first reading was half right and half wrong, and the correction is worth
keeping. Attributing the cost by stubbing each region out in turn:

| region | of a 62.7 ms frame |
|---|---|
| command bar | **31.6 ms** |
| object row | **15.2 ms** |
| navigator | 2.3 ms — already memoised by hand, and the memo works |
| everything else | 13.6 ms |

The navigator was never the problem; collapsing it looked like a saving
because that changes what is laid out, not what is built.

**The fix was not "stop notifying"** — that breaks auto-width. `lib/ui/memo.dart`
generalises the technique the navigator already used, and the same frame now
measures **18.7 ms**. Two pieces: `MemoBuild` for a `State` whose subtree is
worth caching, and `MemoBuilder` for a leaf that must also listen for itself,
because a widget inside a memoised parent is no longer rebuilt by it — the word
count, the study and planner badges and the tag button each subscribe on their
own account, with their own keys.

The failure mode of memoising is a value the subtree renders but the key does
not list: it goes stale and paints only when something else invalidates the
memo. `test/chrome_memo_test.dart` reads the source of each memoised widget,
finds every `app.<member>` it touches, and fails unless that member is keyed or
declared an action; then it proves through the real widgets that the memo hits,
releases, and leaves the live parts live. Both guards were checked against a
mutation before being trusted.

One trap worth recording: the first attempt made the bar *slower* (67.5 ms),
because `MemoBuild` invalidated on `didUpdateWidget` — and a parent that
rebuilds constructs a fresh child every frame, which is the whole situation the
memo exists for. Widget fields belong in the key like everything else.

**Other timings, for the record** (same probe, debug): first build 1,064–1,121
ms, page switch 223–349 ms, section change 223–234 ms. First build is a
one-time cost against a splash screen. Page switch is the number to watch if
it ever gets worse.

### 3. `app_state.dart` is 8,895 lines

Already the top item on [the standing backlog](v0.4-and-beyond.md#1-what-to-do-next),
where it was recorded at 8,755. It has grown since. The other files over 1,000
lines — `repository.dart` (3,821), `sidebar.dart` (2,289),
`sync_dialog.dart` (2,149), `app_shell.dart` (2,096) — are large but not
pathological; `app_state.dart` is a different category.

This is **not** a 1.0 blocker. A god object nobody outside the project has to
read does not hurt a release; it hurts the sixth contributor. But it is the
thing most likely to make the *next* feature slower to write than the last
one, and it interacts with finding 2 — a split state would make scoped
rebuilds natural rather than bolted on.

### 4. Type, radius and icon-size tokens are half-adopted

`theme/tokens.dart` defines `OnoteType`, `OnoteRadius`, `OnoteIcon`,
`OnoteSpace`, `OnoteMotion`. Adoption, counted across `lib`:

| token | used | raw equivalent still in the tree |
|---|---|---|
| `OnoteType` | 121 | 401 × `fontSize:` |
| `OnoteRadius` | 41 | 99 × `BorderRadius.circular` |
| `OnoteIcon` | 41 | 164 × a literal `size:` on an `Icon` |

The visible cost is drift: `fontSize: 13` and `fontSize: 12.5` sitting in
adjacent dialogs, corner radii that do not match between two cards on the same
screen. Nothing is broken, and no user will file a bug about it.

**Correction, 2026-09-02: this is not the mechanical change it looks like, and
it should not be bundled with the translation pass.** `OnoteType.ui` carries
`height: 18 / 13`; a bare `TextStyle(fontSize: 13)` inherits whatever line
height the theme gives it. So swapping one for the other moves line boxes,
which moves row heights, which is exactly the sort of thing that made the
command bar's trailing cluster overflow before it learned to compact. It is a
**visual** change and belongs in a pass where someone can look at the result on
a real window — not in a diff that can only be checked by an analyzer.

### 5. Screen readers — **the first version of this finding was wrong**

It said "121 `Tooltip`s against 6 uses of `Semantics`", and inferred from the
ratio that the app is unusable with a screen reader. That inference does not
survive contact with the framework or with a measurement.

A `Tooltip` **is** a semantic label — Flutter's own `Tooltip` wraps its child
in `Semantics(label: message)`, and `IconButton` builds one from its `tooltip:`
argument. So the 121 tooltips are 121 labels. Scanning `lib` for an
`IconButton` with no `tooltip:` at all finds **three**, and all three are
already wrapped in a `Tooltip` by their parent.

Measured directly, by turning the semantics tree on under a real `AppShell`
with one text block on the page: **22 labelled nodes**, and the block's own
words are among them — a screen reader can read the notes.

What is genuinely missing is narrower and worth naming precisely:

- **Handwriting and equations have no textual alternative.** Ink is a custom
  painter and an equation renders as glyph boxes; neither says anything. An
  equation at least has its LaTeX, which is a real answer waiting to be
  attached.
- **No landmark or heading structure**, so there is no way to jump between the
  navigator, the toolbars and the page other than by walking through
  everything. The F6 region ring already knows what those regions are.

Neither blocks 1.0. Both are worth a line in the release notes, and the
equation one is small enough to be worth doing.

### 6. The documentation says things that are no longer true

`ROADMAP.md` carried a status line dated 2026-08-17 claiming *"1,564 Dart (16
skipped) + 74 Rust tests"*. The real figures are 2,754 and 78. The header is
updated; the body deserves the same pass.

**Correction to this section as first written.** It went on to say that the
roadmap's "next" list was stale in two specific places — blob GC and the
inline-math caret — and *both of those claims were wrong*. They are recorded
here rather than quietly deleted, because a review that invents staleness is
worse than one that misses it:

- **Blob GC is genuinely unbuilt.** `store/media_gc.dart` exists and is
  thorough, but it sweeps **videos**; `findOrphanFiles` finds stray notebook
  files in the workspace. Neither is the blob lifecycle
  [ADR-0007](../adr/ADR-0007-blob-lifecycle.md) designs, whose own amendment
  says the grace-period reasoning "is unchanged and still unbuilt". The
  roadmap is right.
- **The inline-math caret: measured, and neither document was right.** On
  `a $x^2$ b`, eight presses of ArrowRight from the start of the block give
  offsets `1, 2, 3, 3, 3, 3, 3, 3`. So ADR-0004's *"the caret still walks the
  source character by character"* is out of date — arrowing into the equation
  hands over to the equation editor, exactly as
  [v0.20](v0.20-one-equation-editor.md) intended, and the contents are not
  walked at all. But criterion 3 is not met either: **the opening `$` is still
  a character the caret steps onto** (2 → 3), which is one keypress that moves
  nothing the student can see, since the marker is hidden in the live view.
  One step, in one place. Fix it and update the ADR's table, which is where
  the stale claim originates.

Also still true, and still recorded as a known defect in `ROADMAP.md`: the two
root PDFs (`Openote-Brand-and-Style-Guide.pdf`,
`Openote-Product-and-Design-Overview.pdf`) are stale, have no source in the
repository, and predate both the navigator rework and the current style guide.
For a 1.0 they should be regenerated or deleted. Shipping a brand guide that
contradicts the app is worse than shipping none.

### 7. macOS and Linux have never been run by a human

Carried from the standing backlog, unchanged, and the single largest unknown
in this list. Three platforms build and ship; one of them has been used. No
amount of test coverage substitutes for opening the app on the other two.

**This is a 1.0 blocker.** Not because a bug is likely — because "1.0 on three
platforms" is a claim, and it is currently an untested one.

**Two things were done about it here, and neither closes it.** A Linux release
build was attempted and stops before compiling: `media_kit_libs_linux` fetches
mimalloc from GitHub at CMake configure time, and this machine's egress policy
blocks it (§0). And the Linux half of `SecretStore` — which carried the same
"not verified by running it" note as the macOS half — **is now verified**, on
a machine without libsecret-tools, which is the case the promise exists for
and the default on a minimal desktop: write returns false, read returns null,
delete returns true, nothing throws, and nothing is written to a file.
`github_token_storage_test.dart` asserts both branches and says which one it
took, so a developer with libsecret installed exercises the round trip.

That is one never-run path, run. The window, the native library loading and
the packaging still need a human at a real machine.

## What 1.0 should mean

A version number is a promise. The one worth making here is narrow and
keepable:

> **1.0 means: the file format is stable, the three platforms it claims are
> platforms it has been used on, and nothing it does with your notes is
> reversible only by hand.**

Not "feature complete", not "no known bugs". The format promise is the one
that matters most in this project and it is already the one the CHANGELOG
singles out.

Against that, the checklist:

| | |
|---|---|
| Format freeze declared and documented | not yet |
| macOS build opened by a human | **no — blocker** |
| Linux build opened by a human | **no — blocker** |
| Translation foundation | **done** |
| Always-on chrome translatable | **done** |
| At least one language beyond English | not required for 1.0; state it plainly |
| First-run experience teaches the canvas | **done** |
| Analyzer clean, suite green | **yes** |
| Accessibility | better than first reported; two named gaps, neither blocking |
| Brand/design PDFs regenerated or removed | not yet |
| Per-keystroke chrome rebuild | **done** — 62.7 ms → 18.7 ms |

## Suggested order, three revisions

- **v0.24 — translation.** ~~The always-on chrome~~ (done, with the scoped
  rebuild alongside it). Next: the notebook manager, the sync dialog, settings
  and the shortcut map. Adds a second real language only if a native speaker is
  available to write it.
- **v0.25 — the op-log decision** (§0). Measure the split by op kind on the
  owner's real notebooks; if text is a large share, ship `block.patch` at
  `v: 2` while the bump is cheap. The `app_state.dart` split fits here too, and
  a revision with no user-visible change is the safest place for both.
- **v0.26 — the platform pass.** Actually run macOS and Linux. Expect this to
  find things; leave room for them. Regenerate or delete the root PDFs, freeze
  the format, write the release notes — including the honest paragraphs about
  languages and screen readers.

Then 1.0.

## Languages

*Referenced from `l10n.yaml`, `lib/l10n/l10n.dart` and `lib/l10n/app_en.arb`.*

- **English (`app_en.arb`) is the template and the source of truth.** Every
  message carries an `@` entry with a `description`; `test/l10n_test.dart`
  fails without one. A translator sees the string and nothing else, so the
  description is where "this is a button", "this is a Windows menu path" and
  "this is a file extension, do not translate" have to live.
- **Never build a sentence by concatenating fragments.** Word order is not the
  same everywhere. Use a placeholder and declare it.
- **Adding a language:** copy `app_en.arb` to `app_<code>.arb`, translate the
  values (leave the `@` entries out — they belong to the template), run
  `flutter gen-l10n`. Nothing else. `kOnoteLocales` is generated from the
  files present, so there is no list to update and no locale that can be
  offered with nothing behind it.
- **A missing translation falls back to English**, which is the right
  behaviour for a part-translated app and is asserted in
  `test/l10n_test.dart`.
- **Converting a surface:** move its strings into `app_en.arb`, take
  `L.of(context)` once at the top of `build`, and add the file to `_converted`
  in `test/l10n_test.dart` — that last step is what stops the file regressing.
