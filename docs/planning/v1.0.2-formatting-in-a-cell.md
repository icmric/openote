# v1.0.2 — the formatting buttons, inside a table cell

> Reported during the v1.0.1 pass: *"I have noticed that the text options have
> greyed out now when editing in a table. If i manualy write md in there that
> gets interpreted and works great, but i cant use hotkeys for it nor the
> buttons, so not ideal."*
>
> Deferred deliberately, not forgotten. Markdown typed into a cell works, so
> there is a full workaround, and this is **not a regression** — before tables
> moved into the paragraph they were their own block type, and
> `canFormatText` requires a text block, so the buttons were grey for a table
> then too.

## Why they are grey, which is not a bug

`AppState.canFormatText` returns false while something inside the paragraph
holds the keyboard:

```dart
if (activeSession?.inlineChildFocused ?? false) return false;
```

It has to today. `wrapSelection` acts on `activeEditor.controller`, which is
the **paragraph's** field — the cell is a separate `TextField` with its own
controller. Without the gate, Ctrl+B in a cell would bold the sentence outside
the table, or queue a pending style that fires on the next word typed out
there. The grey-out is that gate being honest: the command genuinely cannot
reach the field the caret is in.

## What the fix needs

1. **A formatting target that can be the cell.** While a cell holds the
   keyboard the table registers its controller — and a way to write it back,
   because setting `controller.text` does **not** fire `TextField.onChanged`,
   so the value never reaches `_write` and the edit is lost on the next
   rebuild. `_onLink` (Ctrl+K in a cell) already does exactly this and is the
   template: mutate the controller, then `_write(_data.withCell(r, c, ctl.text))`.
2. **Route the inline commands through it.** `wrapSelection`, `applyTextColor`
   and `toggleTextColor` each call `_commitActiveEditor()` in several branches;
   all of those become the target's own commit.
3. **Split the gate, because the answer differs by command.**
   - *Inline* — bold, italic, underline, strike, inline code, highlight,
     colour — belongs in a cell.
   - *Line-level* — headings, lists, quote — does not. A cell is one line of
     prose; the same reasoning already turns fences off in
     `WrapSelectionFormatter(autoCloseFences: false)`.

   So `canFormatText` keeps its meaning and a second predicate covers the
   inline half.
4. **The no-selection case.** Ctrl+B with nothing selected queues a pending
   mark keyed on `pendingMarkBlockId`, and it is applied by
   `_PendingStyleFormatter`, which the paragraph's field has and a cell's does
   not. Either the cell gains that formatter and the queue gains a way to name
   a cell rather than a block, or pressing a chord with no selection stays a
   no-op in a cell.

   **Do not ship 3 without 4 decided.** A toolbar that works with a selection
   and silently does nothing without one is worse than one that is honestly
   grey.

## Worth checking while in here

`toggleTagOnSelection` and `insertTextAtActiveCursor` read `activeEditor` the
same way and will have the same blind spot. Neither has been reported, because
neither is reachable from a cell today.
