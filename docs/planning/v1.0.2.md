## 1. The accessibility tree, and the focus it moves

The Windows engine cannot apply the semantics updates this app produces:

```
[ERROR:flutter/shell/platform/common/accessibility_bridge.cc(114)]
Failed to update ui::AXTree, error: 335 will not be in the tree and is not the new root
```

It prints constantly in normal use. We treated it as console noise for months.
It is not. Three things follow:

1. **Screen readers cannot use the editor.** If the tree will not build there
   is nothing for Narrator or NVDA to read. Openote is for students, some of
   whom need this, so the honest status today is that it does not work.
2. **It moves the caret.** Having lost track of the tree, the bridge reports
   `didLoseAccessibilityFocus` for whatever node it thinks went away, and
   `TextField` answers that by unfocusing the field — which, for a paragraph
   containing a table, throws the caret out of the cell. v1.0.1 refuses that in
   `_ParagraphFocusNode` (`live_markdown_engine.dart`). **The refusal is
   correct on its own terms** — a field that contains fields is not finished
   just because accessibility focus moved into one of them — so it stays
   whatever happens here.
3. **The window loses and regains focus.** From a trace on 2026-09-30, after
   the refusal was in place:

   ```
   VIEW unfocused → PRIMARY -> Root Focus Scope
   VIEW focused   → VIEW unfocused → VIEW focused → PRIMARY -> paragraph
   VIEW unfocused → PRIMARY -> Root Focus Scope
   ```

   `ViewFocusState.unfocused` makes Flutter park focus on the root scope
   (`widgets/view.dart`, the only caller of `requestScopeFocus` in the
   framework). This is why the caret can still be seen to leave and come back.
   Whether it shares the cause above is **unproven**.

**Why it is not quick.** The check that fails is in the engine, in C++, at
runtime, on Windows — `flutter test` has no accessibility bridge, so the whole
suite is blind to it by construction and every hypothesis costs a rebuild and a
manual reproduction. It may also not be ours: the same error has upstream
reports with unrelated triggers (tooltips inside scrolling lists; a `Slider` in
a pushed route).

**Two prime suspects, both load-bearing architecture.**
- The command bar disables ~18 tooltipped `IconButton`s in a single frame
  whenever `canFormatText` goes false, which is *exactly* when the caret enters
  a cell. Tooltips in a rebuilding list are a known trigger shape.
- A paragraph is an `EditableText` whose spans contain more `EditableText`s.
  `RenderEditable.assembleSemanticsNode` does support placeholder children, so
  this is not unsupported outright — but it is a rare shape, and the atom span
  geometry (one `WidgetSpan` for the first code unit, the rest as hairline
  text) is rarer still.

**Where to start, in order.**
1. Get a minimal reproduction outside Openote — a `TextField` whose spans hold
   a `TextField`, plus a row of tooltipped buttons that disable together. If
   that alone prints the error it is upstream, and the work becomes "file it,
   then find the smallest thing we can change here".
2. Otherwise bisect ours: wrap candidates in `ExcludeSemantics` one at a time
   until the error stops. That names the subtree; it is not the fix, because
   excluding a subtree from semantics is giving up on reading it.
3. Then decide what correct semantics for a table in a sentence looks like —
   a design question, not only a bug fix.

**Do not** "fix" this by turning semantics off. That trades a visible bug for
an invisible one and closes the door on screen readers.

### Also here: nothing in the app reads the platform text scale

`grep` for `textScaler` across `app/lib` returns **nothing** — the app neither
reads it nor pins it. So every width Openote measures for itself is measured at
100% while the widgets draw at whatever Windows is set to. `tableColumnWidths`,
`tableNaturalWidth` and `TextBlockView.autoWidth` all take a `TextStyle` and no
scaler, so with text scaling turned up every table column and auto-sized box is
measured too narrow, in proportion to how much text is in it.

Eric is at 100%, so this is **latent, not live**. It is still wrong, and it is
the same population as the rest of this section: somebody who turns text
scaling up is usually somebody who needs it. Threading a `TextScaler` through
is easy in the two widget call sites; the awkward one is `AppState`, which has
no `BuildContext`. Worth a test that pumps at a scale other than 1.0 — there
are currently none.

## 2. The formatting buttons, inside a table cell

Reported: *"the text options have greyed out now when editing in a table. If i
manualy write md in there that gets interpreted and works great, but i cant use
hotkeys for it nor the buttons."*

**Not a regression**, and not a malfunction. `AppState.canFormatText` returns
false while something inside the paragraph holds the keyboard:

```dart
if (activeSession?.inlineChildFocused ?? false) return false;
```

It has to today, because `wrapSelection` acts on `activeEditor.controller` —
the **paragraph's** field. Without the gate, Ctrl+B in a cell would bold the
sentence outside the table, or queue a pending style that fires on the next
word typed out there. Before tables moved into the paragraph they were their
own block type, and `canFormatText` requires a text block, so the buttons were
grey for a table then too. Markdown typed into a cell works, so there is a full
workaround.

**What the fix needs.**
1. **A formatting target that can be the cell.** While a cell holds the
   keyboard the table registers its controller — and a way to write it back,
   because setting `controller.text` does **not** fire `TextField.onChanged`,
   so the value never reaches `_write` and the edit is lost on the next
   rebuild. `_onLink` (Ctrl+K in a cell) already does this and is the template:
   mutate the controller, then `_write(_data.withCell(r, c, ctl.text))`.
2. **Route the inline commands through it.** `wrapSelection`, `applyTextColor`
   and `toggleTextColor` each call `_commitActiveEditor()` in several branches;
   all of those become the target's own commit.
3. **Split the gate, because the answer differs by command.** *Inline* — bold,
   italic, underline, strike, inline code, highlight, colour — belongs in a
   cell. *Line-level* — headings, lists, quote — does not; a cell is one line
   of prose, the same reasoning that already turns fences off in
   `WrapSelectionFormatter(autoCloseFences: false)`.
4. **The no-selection case.** Ctrl+B with nothing selected queues a pending
   mark keyed on `pendingMarkBlockId`, applied by `_PendingStyleFormatter`,
   which the paragraph's field has and a cell's does not. Either the cell gains
   that formatter and the queue gains a way to name a cell, or the chord stays
   a no-op in a cell.

   **Do not ship 3 without 4 decided.** A toolbar that works with a selection
   and silently does nothing without one is worse than one that is honestly
   grey.

**Worth checking while in here:** `toggleTagOnSelection` and
`insertTextAtActiveCursor` read `activeEditor` the same way and have the same
blind spot. Neither has been reported because neither is reachable from a cell
today.

## 3. One way to hold a piece of content, not two

Reported: *"dragging and dropping an image onto the page seems to insert it the
old way images were handled where they cannot be inlined with text … if i drag
an image in, i cant then cut it and paste it into a text box, it will cut but
attempting to paste it into a text box results in nothing happening."*

And the principle to build to, which is wider than images: *"I only want 1
single unified way of managing any type of data on the page, i dont care if the
user creates it in an existing box with other types of content, drags and drops
something in, or any manner of things, we should only have one unified way of
managing any given type of content which must be uniform across any possible
application of it."*

**What is actually happening.** `dropFilesOntoCanvas` (`media_drop.dart`)
already tries the new shape first:

```dart
landed = insertImageIntoTextAt(app, bytes, mime, where, dark: dark) != null ||
         insertImageBytes(app, bytes, mime, where) != null;
```

`insertImageIntoTextAt` splices `![](sha256:…)` into a text box at the drop
point. It returns null when the drop **misses every text box**, and then the
fallback makes a standalone `BlockType.image`. So there are exactly two ways in
today, and the second is reached by dropping on empty canvas. Ctrl+V at a
caret, a drop onto a box, and Insert ▸ Image all already produce the inline
form.

That also explains the cut-and-paste failure: an image BLOCK on the clipboard
is a block, and a text box has nothing to do with one.

**The shape of the fix is already proven here.** This is the table story again,
and `table_conversion.dart` is the template, including the part that matters
most — it proves the result before it writes, and refuses rather than
half-converting.

1. A drop that misses every text box makes a **text block whose content is the
   inline reference**, not an image block. One way in.
2. Convert existing `BlockType.image` blocks to text blocks holding an inline
   reference, on page open, with the same read-back-and-compare proof
   `tableBlockAsText` uses. Note what the block knew that the reference cannot
   ask for — the table conversion lost column widths exactly this way, and an
   image block knows its own size and position.
3. Cut/copy of a picture then produces something a text box can paste.
4. Then audit the rest of the principle: every other content type should be
   checked for a second path in. Video, PDF, attachments and tables each have a
   drop path and an insert path.

Sizeable, and worth doing as one piece rather than image-first.

## 4. Undo after a toolbar format is load-bearing on a rebuild

Found while fixing the flashing menu, and **not** fixed.

`EditableTextState.didUpdateWidget` disposes its whole selection overlay
whenever `contextMenuBuilder` is not the same object as last build. Openote's
builders were inline closures — new objects every build — so that happened
constantly. v1.0.1 stopped the *trigger* (see `block_view.dart`'s `_setHover`),
but the builders are still closures, so any other rebuild still churns.

The trap: making the builders stable — the obvious and otherwise correct fix —
**breaks `marker_chord_test`'s "a letter chord is never mistaken for a
marker"**. Select a word, Ctrl+B from the chord, Ctrl+Z:

- with the churn, the text goes back to `hello world`;
- without it, it stays `**hello** world`.

Probed: the controller is the **same object** before and after, so the app's
own undo never ran — `app.undo()` would have replaced the block and with it the
controller. It is the field's own `UndoHistory` that used to hold the pre-bold
value and now does not. **So undo after a toolbar format currently depends on
that overlay churn happening.**

Checked and not the explanation: not a throttle (a 900 ms flush does not help);
not `shouldChangeUndoStack` (`EditableText`'s predicate reads only the
selection's validity and the composing region, never focus or the overlay); not
a stray edit (the diff was exactly two hunks).

**Where to start.** Find what the overlay dispose/recreate does that puts a
value on `UndoHistory`'s stack — `_createSelectionOverlay`,
`TextSelectionOverlay.dispose`, and `undo_history.dart`'s `_push` / `initState`
/ `didUpdateWidget`. Fix that, *then* make the builders stable. In that order:
the identity fix is right and small, and landing it over a hidden undo
dependency would trade a visible annoyance for a silent one.

## 5. ~~Two blobs repaired on every single launch~~ — shipped in v1.0.1

Google Drive renames extensionless files, so a notebook on Drive re-repaired
the same picture files on every launch and accumulated copies up to `(8)`.
Blob filenames now end `.blob`, which Drive leaves alone, and verified-identical
copies are removed. Pulled forward into v1.0.1 because it was costing real
users disk and bandwidth every time they opened the app. See the
[File Format Spec](../specs/10-file-format-spec.md) for the two-spelling rule,
and `OpLogStore.tidyRenamedCopies` for the two checks that make deleting a copy
safe.

Confirmed in the field on 2026-10-01: the first open migrated 3 blobs and
removed 62 redundant copies, and a full relaunch afterwards repaired nothing —
so the rename has stopped rather than merely been survived.

**Still open from it:** OneDrive, Dropbox and iCloud have not been checked for
the same renaming behaviour. The residual on Drive itself is only time: the
relaunch above was minutes later, not days, so a notebook left for a week is
the last thing nobody has watched.

## 6. Opening a notebook from a cloud folder locks the whole app up

Found on 2026-10-01 by installing the v1.0.1 draft on a second computer and
opening a notebook that had not been made "Available offline" in Google Drive:
*"It doesnt sync properly, granted it is a large notebook, however the whole
app will just entirley lock up, ive left it for a minute or two and it didnt
start doing anything again."*

Only reachable by someone already using Openote on more than one machine, so
the population is small and committed — but a frozen window with no
explanation is the worst thing the app can do, and this is how a second device
is introduced to it.

### The lock-up is ours, not Drive's

The open path reads synchronously, on the UI isolate:

| | |
|---|---|
| `op_log.dart:427` | each `.oplog`, `readAsBytesSync` |
| `op_log.dart:352` | `manifest.json`, `readAsStringSync` |
| `op_log.dart:123` | each blob, `readAsBytesSync` |
| `op_log.dart:222`, `:291` | re-hashing during the proof |

Against a files-on-demand placeholder each of those blocks until the cloud
client has finished a network download. Drive being slow is Drive's problem;
freezing the window for minutes while it happens is this app's choice of
blocking I/O on the thread that draws. A large notebook multiplies it by the
number of files.

Note `blobProofPatience` already retries at 3 s and 15 s for bytes that have
not arrived — the design anticipated slow cloud files. What it did not
anticipate is that the *read itself* would hang rather than fail.

### It can be detected, so it does not need an unconditional popup

Eric: *"ideally see if we can tell if the folder is set of offline access, but
if not just always have a popup."* The first is possible, at least on Windows.

A dehydrated placeholder carries file attributes that say so, and they can be
read **without opening the file** — so the check costs nothing and cannot
itself hang. The ones to look at are `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`,
`FILE_ATTRIBUTE_RECALL_ON_OPEN` and `FILE_ATTRIBUTE_OFFLINE`, via
`GetFileAttributesW` in `kernel32`; take the exact values from the Win32
headers rather than from this document. There is precedent for the call style
in `platform_open.dart`, which already does `DynamicLibrary.open('shell32.dll')
.lookupFunction<…>` for `ShellExecuteW`.

macOS and Linux have no equivalent worth relying on, so those keep the
unconditional warning.

### Order to do it in

1. **Warn on OPEN, not only on move.** v1.0.1 added a dialog after *moving* a
   notebook into a cloud folder, which is the wrong half of the problem for
   this: a second device *joins* an existing folder and sees nothing. Reusing
   `_offlineAccessDialog` there is small, and it is the only part a user would
   notice immediately.
2. **Check the attributes and only warn when it is actually a placeholder** —
   so somebody who did set offline access is not nagged, which is what makes
   the warning worth reading when it does appear.
3. **Stop blocking the UI isolate.** The real fix, and the larger one: the
   open path's reads belong off the drawing thread. Until then, warning is the
   best that can be done, and an informed freeze is still a freeze.
4. **Consider refusing rather than freezing** when step 2 says the folder is
   dehydrated and the notebook is large. A dialog saying "this will not work
   until you turn on offline access" is kinder than a window that never comes
   back.

## 6a. ~~The maths fixes~~ — shipped, 2026-10-02

Four things, in the order they were reported.

**The "evaluate at value" field bounced the caret back.** Two claimants, not
one. Both the paragraph (`live_markdown_engine`) and the equation editor
(`MathField`) claim the keyboard in a post-frame callback registered from
their own `build`, each written as a one-off — *the host decides THAT a block
is being edited, but the field only exists after this build* — and each
therefore a standing claim, because the app rebuilds constantly. Fixing the
first left the second: *"if im in a maths equation (any maths equation, even
one not linked to that evaluator) it still has the same issue."* The guard is
now shared, in `core/focus_claim.dart`, and asks whether the keyboard is
actually going spare rather than who owns the block — which it has to,
because `substitute`, `flashcard` and `board` are not in
`BlockView._editableType`, so tapping one of their fields never changes
`editingBlockId` at all.

The second half of that report — *"the original one i was editing before
still seems to stay selected"* — had a different cause: a tap on a
`TextField` is won by the field's own recognizer, never reaches
`BlockView._tap`, and so nothing ended the other block's session. The
substitute's field now does what that tap would have. **Note for the next
field added to a non-editable block**: it needs the same handoff, and the
guard alone will not give it.

**Multi-variable substitution.** `MathExpr` was always
`double Function(Map<String, double>)` — the core has taken a map since the
grapher was built — so the cost was in the wrapper, not the maths.
`compileFormula` finds its own names by running the formula, binding the name
it complains about, and running it again. Nothing but `x` had ever worked:
`F=m*a`, `v=u+a*t`, `A=l*w`, `c=sqrt(a^2+b^2)` and even `y=3T+1` were all
refused. `CompiledFormula` is deliberately separate from `CompiledMath`
because a curve is a function of one variable by definition.

**Still open from it:** a graph still refuses `y=3x+c`, which is correct for a
curve — but with named bindings it could plot one once `c` has a value, and
that is a real feature rather than a bug. Not attempted.

**Discoverability, and the toolbar it exposed.** *"We are also hiding this
option in a menu, making it hard to find, anoying to get to, and basically
impossible to just stumble across, which is how most people learn about these
features."* Evaluate is a labelled button beside Graph. It cost 90 px of a
row that had none, which is what forced §6b.

## 6b. ~~The toolbar~~ — shipped, 2026-10-02

**Tab transitions were inconsistent** because of `Widget.canUpdate`. The key
sat on the `SingleChildScrollView` inside an unkeyed `ScrollConfiguration`,
and an `AnimatedSwitcher` compares only its direct child — so Home, Draw and
Page all presented the same unkeyed widget and swapped in place, while Insert
and the equation carried a key at the top and animated. That is exactly the
seam the report described. Worth remembering as a general trap: **a key on the
wrong side of a wrapper is invisible to the switcher above it**, and
`pumpAndSettle` cannot tell a transition that never happened from one that has
finished. The test pumps half a duration and counts the switcher's children.

**The Equation badge was a one-way trip.** Tapping a tab mid-equation sets
`_tabbedAwayFrom` and nothing could clear it. It presses now.

**The equation row folds its far doors** instead of taking a door off. Round
four's door-per-kind was an explicit request, so paying for Evaluate and for
a `Calculus` door by removing one would have undone it. The doors sit in a
`Flexible`, which is how the strip learns its exact remaining width without a
table of measured constants — and why the equation face is no longer inside a
horizontal scroll view, since that axis offers its child infinity.

Measured: 8 doors at ≥1440 px, 7 at 1366, **6 at 1280** with Functions and
Subjects behind the fold, 2 at 900, and no overflow at any width. **That is a
real trade**: before this, all eight fitted at 1280 and Evaluate was in a
menu. The fold keeps them browsable under their own headings, and the search
box is beside it.

**Still open from it:** the quick chips and the doors remain two kinds of
control on one row. The rule is now consistent — a maths glyph inserts, a word
opens a drawer, and `∑ ∫` was the only exception — but whether four
bare-chip shortcuts earn their 148 px at all is a question for whoever next
runs out of width.

## 7. Board items cannot be deleted, edited or opened

*"No way to delete items after creating them on the board, should be able to
edit, delete, and maybe open them up to be able to include/see more details
like in trello."*

A board item is create-only today. The three verbs are not equal work: delete
and edit are the gap that makes the feature feel broken, and a detail view —
a card you open, with more than fits on the board — is a feature of its own and
should not hold up the first two.

## 8. Flashcards cannot be resized on their own

Only the whole box resizes, so a card cannot be given the room its content
needs. Compare the inline table's column handles, which solved the same shape
of problem.

## 9. A page window's selected region cannot be changed after it is drawn

Draw the region once and that is what you get; there is no way to adjust it
afterwards short of deleting the window and starting again.

## 10. A page window cuts off a long page, with no way to see the rest

There appears to be a maximum height on the window, and because the window
cannot be resized (9), anything further down the source page can never be
reached. Worth checking whether the right answer is resizing, scrolling inside
the window, or both — a window onto a long page that silently stops partway is
the worst of the three.

## 11. Touch navigation is rough

Two concrete faults:

- **Sliding a finger over a box selects its text** instead of scrolling the
  page. The page should win unless the gesture started as a selection.
- **A pinch with one finger over a box misbehaves.** Two fingers always mean
  pan and zoom, which is already the stated rule for the trackpad.

Related, and already written down: the stylus-conditional palm rejection in
the roadmap's known defects was verified by unit tests on the decision
function and **never tried on real touch hardware**.

## 12. Pen barrel buttons do not switch tools

Pressing the button on a stylus should reach for the eraser (or whatever it is
bound to) and does nothing. Listed in the roadmap's v0.7-era queue as
outstanding; still outstanding.

## 13. Version history and edit tracking are not in the UI

The op log is an append-only history of every change, so the data to show this
exists by construction — which makes its absence from the interface the whole
of the gap. Worth scoping what "history" means first: a page's past states, a
notebook timeline, or per-block attribution for shared notebooks.

## 14. Solving equations with large operators, and a worked-through solution

Asked, 2026-10-02: *"feasability of solving equations with large/complex
operators (integrals, summation, limit, etc)? Wolfram alpha style solution
walk through?"*

**Two questions with very different answers**, so they are separated here.

### The walkthrough is a documented non-goal, not a gap

`evaluate.dart`'s own header says it, and the Product Vision says it above
that:

> Deliberately a **calculator, not a CAS**: arithmetic, powers, roots, trig,
> logs, factorials, constants, and a few common functions. No symbolic
> algebra, no step-by-step, no equation solving — those are a genuinely deep
> well (Vision §9 keeps "a math solver" as a non-goal).

[Vision §9](../00-product-vision.md): *"**A math solver or CAS.** Like
OneNote's underlying editor, we make it easy to write complex equations
beautifully. We do not commit to solving them in v1. (This keeps us out of a
very deep well…)"* — and the same document lists Microsoft paywalling
"solving and step-by-step math" as one of the reasons this app exists, which
cuts both ways: it is the strongest argument for eventually doing it, and the
clearest statement that it is a product decision rather than an oversight.

So this one is not an estimate, it is a reversal, and worth making
deliberately. A Wolfram-style walkthrough needs symbolic differentiation and
integration, simplification, and step generation with human-readable
justifications — a different class of software from a few hundred lines of
numeric recursive descent, and the part students notice is the quality of the
*steps*, which is where almost all of the work is.

**There is a much cheaper thing that is not a CAS and may be most of what was
wanted.** The solver already knows a formula's structure and the numbers put
into it, so it could show the substitution rather than only the answer:

```
v = u + a·t
v = 2 + 3 × 4
v = 2 + 12
v = 14
```

That is a worked solution for every formula the Evaluate block already
handles, with no symbolic algebra anywhere. It is not free — `MathExpr` is a
closure, so there is no tree to walk at evaluation time and a tracing
evaluator would have to be built beside it — but it is bounded, and it serves
the student the walkthrough was asked for on behalf of.

### Evaluating a definite sum or integral: the limits are discarded today

Measured rather than estimated. A real `\sum_{i=1}^{n} i` from the palette
projects to the linear form the calculator reads as:

```
stored tex : \sum _{i=1}^{n}i
linear     : "§i"
calculator : unexpected "§"
```

The operator and **both of its limits are dropped** by
`math_linear_projection.dart`, which emits a placeholder for a script whose
base it cannot speak. Same for `\int`, `\lim` and `\prod`. So the first piece
of work is not evaluation at all — it is carrying the construct across that
seam.

After that, in increasing order of difficulty and decreasing order of
advisability:

1. **A definite sum or product.** `∑_{i=1}^{5} i²` = 55. Genuinely tractable,
   and the parts exist: `compileFormula` already compiles a body into a
   closure over a map of variables, so the index is bound in a loop and
   accumulated. Needs the projection fixed, an integer-limit check, and a cap
   so a mistyped limit cannot hang the UI isolate.
2. **A definite integral.** `∫₀¹ x² dx` ≈ 0.3333 by Simpson's rule over the
   same closure. Comparable work, plus a convention for the `dx` — which the
   prefilled template now writes, and which the parser would have to treat as
   a bound variable marker rather than two letters multiplied.
3. **A limit.** Approachable by sampling towards the point, and **I would
   advise against it.** Indeterminate forms, one-sided limits and false
   convergence all produce a confident wrong number, and a limit that is
   quietly wrong is worse than one that declines to answer.

Worth noting what each tier buys: (1) and (2) make the Evaluate block
genuinely useful for a calculus problem set, and neither touches the
non-goal. (3) and the walkthrough are both reversals of a stated decision,
for very different reasons.

## 15. The Evaluate block, inline in a sentence

Asked, 2026-10-02: *"Difficulty of enabling solution box to be inlined with
text and other elements? Not as high of a priority, but would be nice to have
the consistency as ideally id like all things to be able to share a box, even
if they cant be on the same line on the box"*

**Moderate, and the storage half is already done** — which is the surprising
part. `InlineAtom` holds a thing that is not text inside a text block, and it
was built to take more than one kind:

> `type` is *"the string rather than `BlockType` because an atom of a type
> this build has never heard of must survive being read and written back"*,
> and the payload is *"a Block's own shape, so it rides through
> `Block.toJson` and `fromJson`, the op log's `block.set`, `read_page`,
> `append_blocks` and the open-folder export with no new schema anywhere."*

So sync, undo, cut/copy/paste, the op log and the exports need **no format
work at all**. `type: 'table'` is simply the only value in use today.

What it costs is the dispatch, and the sites are known:

| | |
|---|---|
| `inline_atom_view.dart:139` | `if (atom.type != 'table')` → the renderer. The real work. |
| `live_markdown_engine.dart:981` | stepping into it with an arrow key, which currently targets a cell |
| `text_block_view.dart:208` | the read (not-editing) view |
| `md_common.dart:174` | Markdown export |
| `pdf_vector_export.dart:252, 483` | PDF export, two places |
| `history.dart:126` | the label in page history |
| — | insertion: Evaluate, with the caret in a sentence, should make an atom rather than a block |

Plus the one real refactor: `SubstituteBlockView` reads and writes
`block.content` directly, and would need to go through a binding instead.
`InlineTable`'s `TableBinding` (read/write closures over the atom host) is the
template, and `blockAtomHost` is the bridge that already exists.

**The focus machinery is the part that would have been hard and is not any
more.** An atom holding `TextField`s inside a paragraph is exactly the
problem `inline_table.dart` solved — `_atomFocus`, `inlineChildFocused`, and
the keyboard-claim guard in `core/focus_claim.dart`. §6a's fix means a field
inside a paragraph no longer loses the caret to it.

Related: this is **§3's principle applied to one more type** (*"only one
unified way of managing any given type of content"*), and doing the two
together would be cheaper than doing them apart — §3 step 4 already says to
audit every type for a second path in. A substitute block that can be inline
or standalone, with one way in, is that audit's answer for this type.

# Investigations — raised, not scheduled

Two directions raised on 2026-10-01. Neither is committed to v1.0.2; they are
here because this is the current version's document and they will move to
whichever one picks them up. Both are architecture, not bug fixes.

## A. Cloudflare D1 + R2 for sync, **self-hosted per user**

Clarified 2026-10-01: Eric would not host this. Each user sets up their own
Cloudflare account, which makes it *"more of a power user feature rather than a
normal user feature"*. That changes the economics completely, and it retires
the main objection recorded here first time round.

**The free tiers are per ACCOUNT, so they are one person's budget, not
everyone's.** Per user, per month:

| | D1 free | R2 free |
|---|---|---|
| Storage | 5 GB | 10 GB |
| Writes | 100,000 rows/**day** | 1M Class A |
| Reads | 5M rows/day | 10M Class B |
| Egress | — | free |

100,000 row writes a day is a great deal of typing *for one person*. So the
earlier worry — that a row per op would exhaust the tier — only applies if this
were centrally hosted. It is not. Beyond the free tier a heavy user pays cents:
50 GB in R2 is **$0.75/month**.

This also lines up with a promise already made rather than bending it: the
README says *"cloud-optional sync — bring your own backend"*. Self-hosted is
exactly that.

### Still put blobs in R2, not D1

That part was not about scale, it was about price and shape: **$0.015/GB-month
versus $0.75** — 50× — and free egress, which is the entire cost of a feature
whose point is other people fetching your pictures. D1 holds the index and the
share tokens; R2 holds op-log segments and blobs. The logs are already
append-only files, so they are object-shaped, not row-shaped.

### The real cost is setup, not money

Which is what makes it a power-user feature, and where the design effort
belongs. An account, a D1 database, an R2 bucket and a deployed Worker is a lot
to ask of a student. Cloudflare's one-click "Deploy to Cloudflare" flow can
provision a Worker with its bindings from a repository, which would reduce this
to: press a button, authorise, paste the resulting URL and token into Openote.
Worth prototyping the *setup* before the sync, because if setup is miserable
nobody reaches the feature.

### What still needs deciding

- **It needs its own ADR**, beside
  [ADR-0006](../adr/ADR-0006-sync-transport-and-text-model.md) rather than
  amending it — folder transport stays first-class.
- **Share links are the most dangerous thing the app would ship.** A public URL
  to a student's notes, with no account on the other side. Unguessable tokens,
  revocation, expiry, and an in-app list of what is currently shared, before
  any of it is switched on.
- **Licensing is clear**: a Worker is separate from `onote_core`, so
  [ADR-0005](../adr/ADR-0005-licensing.md)'s Apache-2.0 constraint is untouched.

## B. Web AI clients — and the spec's own revisit condition has been met

[The external API spec](../specs/14-external-api-mcp.md) §9 says, of its client
table dated 2026-08:

> | ChatGPT app | ❌ impossible today | its connectors run on OpenAI's servers,
> which cannot reach `127.0.0.1` on the user's machine |
>
> *Revisit if either vendor ships* …

**Revisit now.** As of 2026 the ChatGPT **desktop app** can add MCP servers
directly — Settings ▸ MCP servers ▸ Add server, choosing **STDIO or Streamable
HTTP** — in Codex mode / ChatGPT Work, which run locally. Openote's server is
already Streamable HTTP on `127.0.0.1` with a bearer token, which is exactly
that shape.

So this may need **no backend, no Cloudflare and no new code** — just a row in
that table and possibly a one-click button beside the Claude Code and Gemini
CLI ones.

### Correction, 2026-10-01

I wrote above, from third-party write-ups, that the free tier cannot add a
custom MCP server and that Developer Mode is Plus and above. **Eric has the UI
in front of him and it is there** — a custom MCP integration under plugins. His
screen beats my sources; treat the plan-gating claim as unreliable.

**But the question that decides this is not whether the UI exists.** It is
whether *that* surface runs on his machine or on OpenAI's. A connector
configured in the ChatGPT **website** is invoked server-side, and OpenAI's
servers cannot route to `127.0.0.1` on a laptop — no UI changes that. The
desktop app's own MCP settings, in the modes that run locally, can.

So the UI existing moves this from "impossible" to "unknown", not to "works".
The test below is unchanged and still the thing that settles it.

### Test it before believing it

Ten minutes, free, no infrastructure, and it decides how much of the rest
matters:

1. Enable the API in Openote's settings; note the port and bearer token.
2. ChatGPT desktop ▸ Settings ▸ MCP servers ▸ Add server ▸ Streamable HTTP,
   pointing at `http://127.0.0.1:<port>/mcp`.
3. **The thing to watch for is the token.** The spec's original objection was
   that "the UI carries no auth header". If the desktop app's MCP form cannot
   set an `Authorization` header, that is the blocker — and the question becomes
   whether to allow a loopback client to authenticate another way, which is a
   security decision and not a small one.
4. Note *which mode* works. Standard Chat mode still appears to be remote-only;
   local is Codex mode / ChatGPT Work. "Works in ChatGPT" and "works in the
   mode students actually use" are different claims.

### Microsoft Copilot: the worst fit of the three

Asked because some students get it free through university and most Openote
users are on Windows. Checked, and the answer is no in practice:

- M365 Copilot takes MCP servers through **Copilot Studio** (Streamable HTTP
  transport) or **federated connectors** — both **remote HTTP**, so `127.0.0.1`
  is unreachable, same wall as before.
- Both are **admin surfaces**. Copilot Studio needs licensing and tenant
  administrator rights; a student on a university tenant has neither.
- Even when a connector registers, **invocation is up to Copilot's own
  orchestrator** — Microsoft's documentation says tool discovery succeeding does
  not mean the server will be called for a given prompt.

So free-through-university Copilot is effectively closed to this. Not worth
effort before ChatGPT desktop is tested.

### Gemini

Remote-only for the app; Gemini **CLI** already works and has a button. Since
mid-2026 a personal account can paste a custom MCP URL into Spark's Connected
Apps, which is still a public endpoint and so still needs A.

### The zero-setup answer most people would actually use

None of the above helps someone on a free tier who will not install or
configure anything — which is most students. For them the honest answer is not
MCP at all:

- **"Copy this page for AI"** — one button, Markdown to the clipboard. Works
  with every assistant on every platform, free tiers included, nothing to set
  up. Openote already renders Markdown; this is close to free to build.
- **Export a page or section** and attach the file, which already works today.
- **Share links**, if A ships: a read-only URL is readable by every web
  assistant, because they can all fetch a URL. No connector, no OAuth, no paid
  plan.

### Order

1. Test ChatGPT desktop against the existing local server. Free, and it may
   close the whole question.
2. "Copy for AI" — cheapest real win for the largest number of people.
3. A, if the self-hosted setup can be made tolerable; share links then cover
   every web client at once.
4. Per-client connector listings last, if ever.
