enough to be actionable. Anything that turned out bigger than a patch release is in
[v1.0.3](v1.0.3.md).

**A ⚑ marks an item we may not be able to fix.** The cause is outside the app, or
below it, or not yet understood — so the deliverable is a degradation that explains
itself rather than a repair. Those are still worth shipping: a slow open that says
why, and offers the one control that helps, is a different product from one that

## Decisions taken

**A notebook is a folder, and the folder is what you share.** `.onotebook/` —
`manifest.json`, `ops/`, `blobs/` — is already a complete notebook:
`Repository.adoptLogDirectory` opens one with no `.onote` at all, and each
device makes its own container. So copying that one folder already carries
everything. What makes it not feel that way is that the app presents the
`.onote` as the notebook and the directory as plumbing, when the truth is the
other way round. **Nothing moves on disk.** The work is presentation: name the
folder as the notebook, make "share this notebook" hand over the folder and
"open a notebook" take one, and retire the file-format spec's §2 promise that a
`.onote` is self-contained, which has been false since v0.17 Step 6.

Moving the container *into* the folder would be worse, not better: one writer
per file is the invariant the whole transport rests on, and two devices sharing
one `cache.onote` in a replicated folder breaks it. A cache per device would
keep the invariant at the price of every device replicating every other
device's copy of the largest file in the notebook.

**Deleted media is deleted — both video and images.** Consistency beats a size
threshold: a rule that collects some media and keeps others is a rule nobody
can predict, where "deleted means deleted" is one sentence and always true.
What remains is a lightweight stand-in (a blurhash), and a `blob.forget` op is
how it travels between devices without rewriting the log.

**The stand-in carries the displayed geometry, not the image's own.** A block's
`w`/`h` are the user's layout. A placeholder sized from the natural dimensions
would reflow the page the moment something was forgotten, which is the one
thing a tombstone must never do.

Three things still to settle on that: deletion must stay undoable for as long
as undo claims it is, so collection cannot be immediate; a device that was
offline when another forgot learns on the next pull and collects then, which
should be stated rather than discovered; and a forgotten image is **not**
restorable — it stays a grey rectangle. That is the trade.

**Version history: decide between removing the surface and building rollback.**
The two statements on it agree —

> *"At the moment the version history thing is basically useless … it would only
> be helpful as an overview actually showing what was edited and when by who,
> with the option to roll back. If we cant roll back then there isnt any point
> really in keeping version history."*

> *"I personaly basically never used the version history stuff in onenote … So
> long as its robust and that image will appear on the other device and not be
> overwritten i am happy."*

— and point somewhere neither says outright. Sync here is one person, two
machines and a backup, not a shared document; nobody needs to know who changed
what, because the answer is always "I did". So:

1. **Remove the surface.** Undo already covers "I deleted that by accident",
   and covers it better, because it is instant and in the right place.
2. **Build rollback.** Feasible — the op log holds every change — and weeks of
   work for a feature its commissioner never used in the product he is
   replacing.
3. **Leave it.** A list that shows changes and cannot act on them. The worst of
   the three: it costs a surface, it is maintained, and it is already called
   useless.

**The op log is not version history and stays either way.** It is how sync
merges and where blobs live beside. Removing the surface does not touch
`.onotebook/`.

## The demo notebook

The asset is `app/assets/demo/demo.onote`, edited in Openote rather than in
Dart. Open it from a copy, never where it sits — opening a `.onote` makes its
folder that notebook's live log directory, which is how the repo started
collecting notebooks and how the demo's own handwriting was lost to a
`flutter clean`.

- **The ink is broken.** Eight blocks whose blobs are gone. Nothing should ship
  with unresolvable references in the one notebook guaranteed to be opened by
  strangers.
- **The MCP instructions cannot be followed in a browser**, where there is no
  local server to connect to.
- **Put Maths before Revision.** It is the stronger showcase and the one most
  likely to decide a maths student.
- **Drop the opening superlative.** "The most feature rich, open-source note
  taking app around" is unprovable and invites scepticism in the first line.
  The sentence after it — import your whole OneNote notebook and lose nothing —
  is concrete and checkable.
- **"Solving single variable equations" is on its way to being wrong**: the
  solver is multi-variable now, and the Maths page solves πr² for `r`.
- **"No changes here will be saved" repeats the status bar.** Defensible for a
  visitor arriving cold, but worth deciding rather than letting it drift.

# Detail

## 1. The accessibility tree

The Windows engine cannot apply the semantics updates this app produces, and
prints so constantly in normal use:

```
[ERROR:flutter/shell/platform/common/accessibility_bridge.cc(114)]
Failed to update ui::AXTree, error: 335 will not be in the tree and is not the new root
```

This was treated as console noise for months. Two things follow. **Screen
readers cannot use the editor** — if the tree will not build there is nothing
for Narrator or NVDA to read, and Openote is for students, some of whom need
it. And **it moves the caret**: having lost the tree, the bridge reports
`didLoseAccessibilityFocus`, and `TextField` answers by unfocusing — which for
a paragraph containing a table throws the caret out of the cell.
`_ParagraphFocusNode` refuses that, and the refusal is correct on its own terms
whatever happens here. The window also loses and regains view focus, which
parks Flutter's focus on the root scope; whether that shares the same cause is
unproven.

**Why it is not quick.** The check that fails is in the engine, in C++, at
runtime, on Windows. `flutter test` has no accessibility bridge, so the suite is
blind to this by construction and every hypothesis costs a rebuild and a manual
reproduction. It may not be ours — the same error has upstream reports with
unrelated triggers.

**Two suspects, both load-bearing architecture.** The command bar disables ~18
tooltipped `IconButton`s in one frame whenever `canFormatText` goes false, which
is exactly when the caret enters a cell, and tooltips in a rebuilding list are a
known trigger shape. And a paragraph is an `EditableText` whose spans contain
more `EditableText`s; `RenderEditable.assembleSemanticsNode` does support
placeholder children, so this is not unsupported outright, but the shape is rare
and the atom span geometry rarer still.

**Order to work in.**

1. Reproduce it outside Openote — a `TextField` whose spans hold a `TextField`,
   plus a row of tooltipped buttons that disable together. If that alone prints
   the error it is upstream, and the job becomes filing it and finding the
   smallest thing we can change here.
2. Otherwise bisect: wrap candidates in `ExcludeSemantics` one at a time until
   the error stops. That names the subtree. It is not the fix, because excluding
   a subtree from semantics is giving up on reading it.
3. Then decide what correct semantics for a table inside a sentence looks like.
   A design question, not only a bug.

**Do not fix this by turning semantics off.** That trades a visible bug for an
invisible one and closes the door on screen readers.

## 2. Formatting inside a table cell

> *"The text options have greyed out now when editing in a table. If i manualy
> write md in there that gets interpreted and works great, but i cant use
> hotkeys for it nor the buttons."*

Not a regression and not a malfunction. `AppState.canFormatText` returns false
while something inside the paragraph holds the keyboard, and it has to today,
because `wrapSelection` acts on the *paragraph's* controller. Without the gate,
Ctrl+B in a cell would bold the sentence outside the table. Markdown in a cell
works, so there is a full workaround.

1. **A formatting target that can be the cell.** While a cell holds the
   keyboard the table registers its controller — and a way to write it back,
   because setting `controller.text` does not fire `onChanged`, so the value
   never reaches the write path and the edit is lost on the next rebuild. Ctrl+K
   in a cell already does this and is the template: mutate the controller, then
   write the cell.
2. **Route the inline commands through it.** `wrapSelection`, `applyTextColor`
   and `toggleTextColor` each commit the active editor in several branches; all
   of those become the target's own commit.
3. **Split the gate, because the answer differs by command.** Bold, italic,
   underline, strike, inline code, highlight and colour belong in a cell.
   Headings, lists and quote do not — a cell is one line of prose, which is the
   same reasoning that already turns fences off there.
4. **Decide the no-selection case.** Ctrl+B with nothing selected queues a
   pending mark keyed on the block id, applied by a formatter the paragraph's
   field has and a cell's does not. Either the cell gains it and the queue gains
   a way to name a cell, or the chord stays a no-op.

**Do not ship 3 without 4 decided.** A toolbar that works with a selection and
silently does nothing without one is worse than one that is honestly grey.

**Worth checking while in here:** `toggleTagOnSelection` and
`insertTextAtActiveCursor` read the active editor the same way and have the same
blind spot. Neither has been reported because neither is reachable from a cell.

## 3. One way to hold a piece of content

> *"I only want 1 single unified way of managing any type of data on the page, i
> dont care if the user creates it in an existing box with other types of
> content, drags and drops something in, or any manner of things."*

`dropFilesOntoCanvas` already tries the new shape first: it splices
`![](sha256:…)` into a text box at the drop point, and falls back to a
standalone `BlockType.image` only when the drop **misses every text box**. So
there are exactly two ways in, and the second is reached by dropping on empty
canvas. Ctrl+V at a caret, a drop onto a box, and Insert ▸ Image all produce the
inline form already. That also explains the paste failure: an image block on the
clipboard is a block, and a text box has nothing to do with one.

The fix is the table story again, and `table_conversion.dart` is the template —
including the part that matters most, which is that it proves the result before
it writes and refuses rather than half-converting.

1. A drop that misses every text box makes a **text block whose content is the
   inline reference**, not an image block.
2. Convert existing image blocks on page open, with the same read-back-and-
   compare proof. **Note what the block knew that the reference cannot ask
   for** — the table conversion lost column widths exactly this way, and an
   image block knows its own size and position.
3. Cut and copy then produce something a text box can paste.
4. Audit the rest of the principle. Video, PDF, attachments and tables each have
   a drop path and an insert path.

Worth doing as one piece rather than image-first.

## 4. Undo after a toolbar format

`EditableTextState.didUpdateWidget` disposes its whole selection overlay
whenever `contextMenuBuilder` is not the same object as last build. Openote's
builders are inline closures, so that happened constantly. v1.0.1 stopped the
*trigger*, but the builders are still closures, so any other rebuild still
churns.

The trap: making the builders stable — the obvious and otherwise correct fix —
breaks `marker_chord_test`. Select a word, Ctrl+B from the chord, Ctrl+Z: with
the churn the text goes back to `hello world`, without it it stays
`**hello** world`. The controller is the same object before and after, so the
app's own undo never ran; it is the field's own `UndoHistory` that used to hold
the pre-bold value and now does not. **So undo after a toolbar format currently
depends on that churn happening.**

Checked and not the explanation: not a throttle, not `shouldChangeUndoStack`
(its predicate reads only the selection's validity and the composing region),
not a stray edit.

**Where to start.** Find what the overlay dispose/recreate does that pushes a
value onto `UndoHistory` — `_createSelectionOverlay`,
`TextSelectionOverlay.dispose`, and `undo_history.dart`'s `_push`, `initState`
and `didUpdateWidget`. Fix that, *then* make the builders stable. In that order:
landing the identity fix over a hidden undo dependency would trade a visible
annoyance for a silent one.

## 5. Opening a cloud notebook freezes the app

Found by installing on a second computer and opening a notebook that had not
been made available offline in Google Drive. Only reachable by someone already
using Openote on more than one machine, so the population is small and
committed — but a frozen window with no explanation is the worst thing the app
can do, and this is how a second device is introduced to it.

**The lock-up is ours, not Drive's.** `op_log.dart` reads synchronously on the
UI isolate in four places: `readDevice` for each `.oplog`, `readManifest`, the
blob reads, and the re-hashing in `blobBytesMatch` and `tidyRenamedCopies`.
Against a files-on-demand placeholder each blocks until the cloud client has
finished a network download, multiplied by the number of files. Drive being slow
is Drive's problem; freezing the thread that draws while it happens is this
app's choice. Note that `blobProofPatience` already retries at 3 s and 15 s for
bytes that have not arrived — the design anticipated slow cloud files. What it
did not anticipate is the *read itself* hanging rather than failing.

**Decided: measure the symptom, not the cause.** Rather than asking the operating
system whether a folder is a placeholder, watch how fast pages are actually
arriving. When they are arriving far slower than normal, say so and offer the fix:

> Pages are loading slowly. Enabling "Available offline" on this folder will make
> it much faster.
>
> **[ Open the folder ]  [ Cancel ]**

Three reasons this is the better shape. It works on **all three platforms**, where
the attribute check was Windows-only and macOS and Linux have no equivalent worth
relying on. It cannot be wrong in the annoying direction — nobody who is having a
fast time is ever told to change a setting. And it needs no FFI, no `kernel32`, and
no exact attribute values taken from the Win32 headers.

It also makes **no promise the app cannot keep.** The underlying cause is that
`op_log.dart` reads synchronously on the UI isolate, and whether that gets fixed is
open — so the honest deliverable here is a slow open that explains itself and hands
over the one control that helps, not a fast one.

What to settle while building it:

1. **What "far slower than normal" is.** Needs a baseline the app already knows —
   time per log file, or per blob read — and a threshold well clear of a merely
   large notebook on a slow disk. Erring high is correct: a dialog that fires on
   an ordinary open is worse than no dialog.
2. **Say it once.** Per notebook, per session. A dialog that returns every time
   something is slow is a dialog people learn to dismiss without reading.
3. **"Open the folder" is a plain reveal-in-file-manager**, which
   `core/platform_open.dart` already does. Openote cannot toggle the setting
   itself — that belongs to the sync client — so the button's whole job is to get
   the person to where the setting is.
4. **Keep the existing warning on *move*.** It fires before anything is slow and
   is still the right moment to mention it.

Still worth doing independently, and the only real fix: **take those reads off the
UI isolate.** Until then an informed freeze is still a freeze.

## 14. What the AI dialog can honestly say

All three of these are cheap, and together they replace an inference with
evidence:

- **"Set up in ‹client›"** — what the icon means today, in those words.
- **"Listening on port N"** — the server either bound or it did not.
- **"Last request: ‹when›"** — one timestamp written where requests are
  handled. This is the one that answers *is anything talking to me*.

Separately, and worth a line in the dialog: an MCP client connects **once, at
session start**, and does not retry. A session that began while Openote was
closed stays disconnected for its whole life however healthy the server later
becomes. That is the client's behaviour, not something this app can fix, but
"it says connected and my AI cannot see it" is otherwise unexplainable from
inside the app.

## 18. Backups

### A target with `keep: 0` is not a backup, and never says so

`MirrorTarget.isBackup` is `keepVersions > 0`, and one number silently switches
three behaviours:

| | mirror (`keep: 0`) | backup (`keep > 0`) |
|---|---|---|
| copies the log directory | yes | yes |
| copies the `.onote` container | **no** | yes |
| timestamped snapshots | no | yes |
| pruned | **no** | yes, to `keep` |

So a `keep: 0` target copies the ops and blobs and deliberately skips the
notebook itself, while the feature is described to the user as backing up. The
code's reason is sound in its own terms — the container is rebuildable, it is
the largest file, and it is rewritten on every save — but "rebuildable" is a
claim about a tool that does not exist yet, and a copy you cannot open is not a
backup.

**Stop having two behaviours behind one number.** Say which one a target is, in
the UI, in its own words. If a mirror still skips the container, the UI has to
say it is not something you can restore from.

### Copies accumulated inside copies — fixed

`mirrorNotebook` walked the source recursively without asking whether the
destination was inside it. Three generations of one log directory had nested
themselves in the demo asset folder. Now refused in both directions with
`p.isWithin`, checked at run time rather than when the target is chosen, because
a notebook can move afterwards. Covered by `test/mirror_overlap_test.dart`.

Still true and still by design: `_prune` runs only for backups, so a mirror
grows for ever. Defensible for a true mirror; not defensible when the same
folder has also accumulated timestamped snapshots nobody prunes.

### A container copied on its own loses its handwriting, silently

Ink lives in `blobs/<sha256>` beside the log directory, not in the container,
since v0.17 Step 6. So copying a `.onote` by hand — or with `VACUUM INTO`, which
is what `snapshotContainer` does — produces a notebook whose ink references
resolve to nothing. Measured on the demo asset: eight ink blocks, eight
`blob_refs` rows, zero rows in `blobs`, and no `blobs/` directory anywhere.

`refillContainerBlobs` already fixes this — it puts the bytes back into the
container's own table, so a container refilled and then vacuumed is genuinely
self-contained. **Any route that hands someone a single `.onote`** — backup to
file, "copy this notebook", the demo asset — **should refill first, or say
plainly that handwriting and pictures will not travel with it.** Silently
producing a file that looks complete and is not is the worst of the three
options.

### There is no restore

No code reads a backup back. Restoring means knowing that a notebook is a
container plus a log directory plus a blobs folder, and copying the right three
things to the right places by hand — and getting it wrong loses handwriting
without a word.

> *"Ideally just click a button and have a default space for backups already
> set, but give them the option to save elsewhere."*

- **A default location**, so backups exist for people who never open the dialog.
  The workspace folder is the wrong default: same disk, same folder a sync
  client is already churning. The platform's own documents or backup location is
  the right shape.
- **One button**, and its counterpart: a list of what has been backed up, with a
  restore that takes one of them.
- **Restore must be whole.** Container, logs and blobs, checked — the
  `missingBlobs()` machinery exists and should run as part of the restore rather
  than being discovered later as a grey page.

## 19. Blocks arriving in the wrong shape

### An agent over MCP cannot see what the app can do

Asked to write code, ChatGPT reached for a Markdown fence; asked for a table, it
wrote a Markdown table — both while connected over MCP, with native `code` and
`table` blocks available.

This is the cost of [spec 14 §2](../specs/14-external-api-mcp.md)'s rule, and
the rule is still right: the file format is the API, so a new block type is
API-visible the day it exists and nobody updates a second schema. But
discoverability was never part of it. `tools/list` describes `append_blocks` as
taking block JSON without saying which types exist, and an agent that cannot see
a `table` type does the reasonable thing and writes Markdown.

Fixes, in increasing order of cost — the first is probably enough:

1. **Name the types in the tool description**, generated from `BlockType` so it
   cannot drift. One sentence per type about what it is for.
2. **Say it in `append_markdown`'s description too** — prefer `append_blocks`
   with a `table` or `code` block over Markdown that only renders as text.
3. **Convert on the way in.** A fenced block or a GFM table arriving through
   `append_markdown` becomes the native block. Attractive and the most work, and
   it has to not surprise someone who genuinely wanted literal Markdown.

**Separately, a wide Markdown table is cut off, not scrolled.** That is silent
content loss whoever wrote it — worse than the discoverability problem, and
independent of MCP.

### Some routes still insert the old kind of block

Dragging an image in produces a standalone block rather than an inline
reference (#3). Take the census while fixing that one: for every content type,
list every route in — drop, paste, Insert menu, right-click, importer, MCP — and
check they all land on the same shape. The ones already known to differ are
images, and tables before they were converted.

## 23. Auto-capitalisation

The owner: *"We currently dont have any sort of auto capitalisation, is there
any way to implement something like that easily but also helpfully where its
not annoying for people (i.e. ctrl + z undoes it but doesnt remove the rest,
and doesnt redo it when they continue typing, but still does it again next
sentence)?"*

Yes, and the design is small — but one part of the ask cannot be built the way
it is written, so it is written out here before it is promised.

**What is easy.** The rule is a pure function of the text before the caret:
capitalise a letter typed at the start of a line, or after `.`, `!` or `?`
followed by a space. That is the same shape as `applyPendingMarks` — a string
in, a string and a caret out — so it is specified and tested without a widget
tree, and it hangs off the formatter the field already runs.

Four exceptions earn their place, because each one is a wrong capital somebody
would have to go back and fix:

  * not after `e.g.`, `i.e.`, `etc.`, `vs.`, `Dr.`, `Fig.`, `No.` or a single
    initial — a full stop inside an abbreviation is not the end of a sentence;
  * not after a decimal point (`3.14`) or a version (`v1.0.2`);
  * not inside a code span or a code block, where case is meaning;
  * not when the letter typed is the second character of a word already begun,
    which is what makes it a *sentence* rule rather than a word one.

**What cannot be built as asked.** *"Ctrl+Z undoes it but doesnt remove the
rest"* needs an undo step smaller than this app has. Undo is a snapshot of the
page, taken per edit burst (`AppState.pushUndo`), so the smallest thing Ctrl+Z
can take back is the whole burst of typing — not one letter of it. Giving the
substitution its own entry means either a character-level undo stack in the
editing session or a one-shot "undo just the last automatic change", which is
a feature in its own right and the thing to size separately.

**What replaces it, and is better.** Remember the one offset the last capital
was applied at, and do not apply it there again. Then correcting it by hand is
the escape hatch: lowercase the letter back and it stays lowercase, while the
next sentence still gets its capital — which is the *behaviour* the Ctrl+Z
request was reaching for, reached by the key people actually press when they
disagree with an automatic change. It costs one field on the editing session
and no new undo machinery.

A switch in Settings beside the spell-check one, on by default, and off is
honoured without a restart.

**Not in this release unless the owner says so.** It changes what typing does,
which is the one thing nobody asked to have changed, and a patch release that
also fixes five reported bugs is a bad place to find out. The code is a day
with its tests; the decision is the slow part.

## 24. Highlight in a colour

Found while fixing #17, not reported: **text colour is a split button with a
full picker, and the highlighter is a single hard-coded yellow.** `==x==` has
one colour in the grammar and one in each renderer. For an app whose owner
says *"Colour is a really important thing to me that we get right"*, and whose
students highlight to triage a reading list, one yellow is half a feature.

The shape is already decided by the colour span beside it:
`{{=RRGGBB text}}`, mirroring `{{#RRGGBB text}}` — same length rules, same
optional alpha, and the second character is what tells the two apart, so no
branch ordering changes. `==x==` stays and means the default yellow, because
it is in notes already and it is what every other Markdown tool understands.

Then: one branch in `md_syntax`, a `backgroundColor` in each renderer (both
now recurse, so highlight-plus-bold comes free), an `applyHighlightColor`
mirroring `applyTextColor` including its re-colour-rather-than-nest cases, the
split button, the same strip in `md_common` that `{{#` already gets on export,
and a row in the dialect table of the data-model spec.

Half a day, almost all of it pattern-matched off work that is already here.
Held back only because it is an addition and this release is carrying five
fixes to reported bugs.

## 11. The pen's buttons

Reported three times, by two people, and answered twice by reasoning about
what Windows probably sends. The answer is in the engine we ship with:

```cpp
// flutter/shell/platform/windows/flutter_window.cc, Flutter 3.44.8
if (pointerInfo.pointerType == PT_PEN) {
  POINTER_PEN_INFO penInfo;
  if (windows_proc_table_->GetPointerPenInfo(pointerId, &penInfo)) {
    pressure = penInfo.pressure;
    rotation = penInfo.rotation;
  }
}
...
OnPointerDown(x, y, device_kind, touch_id, WM_LBUTTONDOWN, rotation, pressure);
```

`penFlags` is not read anywhere in that embedder — no barrel, no eraser, no
inverted — and the button is hard-coded to the left mouse button. So a barrel
press could not reach Dart, and no arrangement of `kPrimaryStylusButton` /
`kSecondaryStylusButton` / `kSecondaryButton` in `ink_ops.dart` was ever going
to find one. `grep -rn "PEN_FLAG" <sdk>/engine/src/flutter/shell/platform/windows/`
returns nothing.

Upstream fixed it in flutter/flutter#183369 (merged 3 June 2026, reverted the
next day, re-landed as #187629): pen events carry a real button bitmap and an
inverted pen reports itself. It is not in 3.44.8 and arrives with an upgrade.

**What shipped instead.** `windows/runner/pen_buttons.cpp` reads the same flags
off the window messages on their way past — the runner's window procedure is
ours — and sends them over a channel. It only observes: no message is
consumed, nothing is synthesised, and where the pen cannot be identified the
app behaves exactly as before. The Draw tab chooses what a side press does
(eraser, Select, nothing); the tail always erases.

**Windows has two ways of delivering a pen and the hook watches both**, since
which one a machine uses is a driver setting rather than a fact:

  1. **Windows Ink on** — `WM_POINTER*`, buttons in
     `POINTER_PEN_INFO::penFlags`, with
     `POINTER_INFO::pointerFlags & POINTER_FLAG_SECONDBUTTON` as the fallback
     upstream's own patch keeps for when `GetPointerPenInfo` fails.
  2. **Windows Ink off, or a vendor driver in mouse mode** — the driver
     synthesises the mouse itself, no `WM_POINTER` message exists at all, and
     the barrel arrives as a real `WM_RBUTTONDOWN`. Identifiable because
     `GetMessageExtraInfo` carries the pen signature, which is the test the
     engine itself uses to tell a pen from a mouse.

That second path also delivers a context-menu gesture at the same moment, so
one of the two gives way: the menu, unless the button is set to "nothing", in
which case a menu is the most useful thing a barrel press can do.

**And one meaning whichever route it arrives by.** `penGestureErases` takes
the setting, `penGestureSelects` is its other half, and both ask
`penGestureHoldsButton` — which is about the hardware. Without that the
setting would have applied only to the Windows channel, and a barrel press on
Linux would have gone on erasing whatever it was set to.

**Measured on the owner's pen, 2026-10-19, once the hook was on the right
window.** This is the first evidence any of it rests on:

| what they pressed | what arrived |
|---|---|
| nothing, hovering or touching | `0x0` |
| the button their driver maps to **barrel button** | `0x1` — hovering *and* touching |
| the button their driver maps to **eraser** | `0x2` (`PEN_FLAG_INVERTED`) — **hovering only**; `0x0` while touching |

So **Windows does report which button is which**, in its own vocabulary: a
button mapped to the eraser comes through as "the pen is inverted", because
that is how Windows models an eraser. Which settles the owner's ask — *"id
ideally like them to be what they are defined at a system level to be"* — for
the eraser half: it erases, full stop, and no setting has anything to add.

The barrel is the half that needs a setting, because "barrel button" is not an
action: it is Windows' name for a generic secondary press. OneNote lassoes
with it, so that is the default here, with Select, Eraser and Nothing beside
it. Before this, the default sent both buttons to the eraser — *"both barrel
buttons in my case map to the eraser"* — which is exactly what the two
colliding on one meaning looks like.

**Still open.**

  * **The eraser button reports nothing while the pen is touching**, and
    pressing it mid-stroke makes the pen momentarily register as lifted:
    *"it will have a small missing spot, it doesnt matter how long i hold the
    button down for, it seems to pretty much do it once per frame."* Windows
    is ending the pointer and starting a new one, which is also why the flag
    goes. `PEN_FLAG_ERASER` (`0x4`) is documented as the in-contact
    counterpart of `INVERTED` and is read already, but this pen does not send
    it. Nothing in the app can stitch the stroke back together without
    guessing that an up-then-down a frame apart was not one — which is the
    kind of inference this project has rejected twice. Worth a measurement
    pass of its own before anything is built.
  * **A button pressed mid-stroke still switches tools under the gesture.**
    The pointer routing is chosen at build time from `app.tool`, so a press
    while the pen is already down swaps the handlers under a live gesture and
    leaves the wet stroke behind. Press-then-draw is the ordinary way round
    and works; mid-stroke presses are already broken by Windows ending the
    pointer (above), so both want the same measurement pass.
  * **Unconfirmed on hardware.** Every test is of the Dart half — the channel
    message, the setting, the tool coming back when the button is let go.
    Nothing here has touched a digitiser. Settings › Pen and touch test is
    the instrument for confirming it, and for the first report that does not
    match.
  * **Two side buttons cannot be told apart.** Windows has one
    `PEN_FLAG_BARREL`, so a pen with two of them reports both through it. The
    tail is separate. Nothing can be done about this below the driver.
  * **OS pen shortcuts are a different thing entirely.** What Windows Settings
    calls "pen shortcuts" — single click, double click, press and hold on a
    Bluetooth pen — never arrive as pointer messages at all, so a button
    mapped there is not a button this can see. If the diagnostic shows nothing
    for a press, that is the likely reason, and the fix is to map the button
    in Openote rather than in Windows.
  * **Remove this once the engine reports buttons.** Two sources for one fact
    is one too many: when a Flutter with #187629 is in, the runner hook goes
    and `ink_ops.dart` reads the bits it was always written for.
